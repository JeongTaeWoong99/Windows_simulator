DateTime.UtcNow ×4 · const GatherSpeedMultiplier · GameTable 정적

문제

순수 코어가 받는 now 주입이 User에서 끊긴다 — AssignWorkStation·RefreshWorkStationSpeed는 DateTime.UtcNow를 내부 생성하고, 생성자는 ISession을 요구한다. 그래서 재화 생성 경로(SettleWorkStation → GainItem) 전체가 테스트 불가.

해결

IClock(스케치가 SmokeTest.cs:11에 이미 있다) · 패킷 송신 · DB 큐를 생성자 주입으로 바꾸고, now를 못 받던 두 메서드에 인자를 뚫는다. GatheringScheduler.Tick도 clock·유저 소스를 받으면 같은 seam에 얹힌다.

  • 레버리지: seam 3개로 441줄이 열린다
  • 지역성: 시각 버그가 User 안에 갇힌다
  • 테스트: 재화 생성 경로 최초 커버
  • 기획 규칙 "속도 변경 직전 정산" 검증 가능

문제

신규 유저 정책(기본 캐릭터·DefaultSlotCount)·채취 시작 시각·응답 전송이 전부 SQL 옆에 있고, Apply()가 User.Login()을 직접 불러 seam이 무너졌다. 도메인 메서드 WorkStation.Unlock이 있는데 리포지토리가 new WorkStationSlot으로 우회한다. 밴/삭제 계정은 판정만 하고 응답을 안 보내 클라이언트가 무한 대기한다.

해결

리포지토리는 LoginData 결과 객체를 반환하는 데서 멈춘다. 신규 지급·슬롯 개설·시작 시각·다음 단계 호출은 로직 스레드의 User 쪽 플로우가 맡는다. 정책이 순수 코드가 되므로 DB 없이 테스트된다.

  • 지역성: 신규 유저 정책이 한 곳에 모인다
  • 리포지토리 인터페이스가 "데이터 왕복"으로 좁아진다
  • 밴 응답 누락 같은 침묵 실패가 드러난다
  • 테스트: 지급 규칙을 DB 없이 검증

삭제 테스트 통과: PickOne을 지우면 복잡도가 WeightedPicker 한 곳으로 집중된다 — pass-through가 아니라 진짜 중복이었다는 증거.

문제

가중치 0 제외·음수 거부·합 오버플로 검사가 채취 드롭에는 적용되고 가챠에는 적용되지 않는다. 난수원이 하드코딩이라 시드 고정 테스트도 불가. 덤: TrySpend 호출자가 프로덕션에 없어 가챠에 재화 소모가 없다(재화 모듈 전체가 dead code).

해결

GachaEntry는 이미 Weight를 가지므로 WeightedPicker.From(pool, e => e.Weight) 한 줄로 대체. 합산-지급 루프는 User.GainItems로 통합. 재화 소모는 기획 확정(가챠 비용) 후 TrySpend를 같은 자리에 붙인다.

  • 레버리지: 추첨 인터페이스 1개, 소비자 3곳
  • 가챠가 기존 테스트 200줄을 공짜로 얻는다
  • 중복 구현 2벌 삭제

문제

"프레임워크는 게임을 모른다"(CLAUDE.md의 경계 규칙)를 스스로 어긴다 — DB 실행 정책이 네트워크 lib 안에 있어 게임 코드 3곳이 lib을 using한다. Entity.Post가 LogicExecutor.Instance에 못 박혀 어떤 Entity 생명주기도 동기 검증이 안 된다. 실행기 예외는 Console.WriteLine 후 삼켜져 Apply가 영영 안 불린다 — 로그인 무한 대기의 근원.

해결

DBExecutor·LogicExecutor를 WSGameServer로 옮기고 IJobScheduler seam을 게임 쪽에 둔다. Lib은 이미 onRecvCallback을 받으므로 Lib 쪽 변경은 거의 없다. 옮기는 김에 실패 훅(OnError)을 뚫어 침묵 실패를 없앤다. 어댑터 2벌(실제 스레드/인라인)이 seam을 정당화한다.

  • Lib 경계 규칙 회복
  • 테스트: Entity 생명주기를 인라인으로 검증
  • DB 침묵 실패 제거의 발판

6 · "정산 → 속도 변경" 불변식을 타입으로 만든다

Speculative in-process
User/WorkStation/WorkStationSlot.cs · User/WorkStation/WorkStation.cs · User/User.WorkStation.cs

문제

"속도를 바꾸기 직전에 반드시 정산한다"(소급 지급 방지 — 게임기획코어 6장에도 있는 규칙)가 주석과 호출 순서로만 지켜진다. ApplyWorkSpeed를 먼저 부르는 새 호출자가 생기면 컴파일은 통과하고 재화만 샌다.

해결

ApplyWorkSpeed를 공개 인터페이스에서 내리고 WorkStation.SettleAndApplySpeed(now, resolver) 원자 연산 하나로 접는다. 인터페이스에서 메서드가 하나 줄고, 불변식이 구현 안으로 들어간다 — 전형적 깊어지기.

Before — 호출자가 순서를 안다

slot.ConsumeJudgeCount(now) // ① 먼저
slot.ApplyWorkSpeed(speed) // ② 반드시 뒤에 — 주석만이 지킨다

After — 모듈이 순서를 안다

ws.SettleAndApplySpeed(now, slot => resolver(slot))
// 정산과 적용이 한 호출 — 어길 방법이 없다
  • 인터페이스 축소: 메서드 −1
  • 소급 지급 버그 계급 제거
  • 현재 호출자 2곳뿐 — 급하지 않다

부수 발견 — 아키텍처 이전에 고칠 것들

리뷰 중 나온 버그급 항목. 위 후보들과 별개로 우선 처리 대상.

  • AddItemRepository.Key가 대입되지 않아 영구 0 — 모든 아이템 저장이 DB 채널 0으로 몰리고 같은 유저의 다른 작업과 직렬화가 깨진다 (InventoryRepository.cs:10).
  • DB 실행기가 예외를 삼켜 Apply 미도달 — 실패 시 로그인 무한 대기, 실패 패킷 없음 (MikaExecutor.cs:47-55).
  • 트랜잭션 0건 — 동시 접속 시 중복 계정 가능, 신규 지급 INSERT 부분 실패 시 반쪽 유저 (AccountRepository.cs:24-46, LoginRepository.cs:66-114).
  • Disconnect() check-then-act 경합 → OnDestroy 2회 = 종료 정산 중복 가능 (MikaServerSession.cs:56-61, Entity.cs:27-30 멱등 가드 없음).
  • 가챠에 재화 소모가 없다 — TrySpend 호출자 0. 기획(가챠 비용) 확정 필요 항목이라 임의 구현 금지 대상.
  • 드롭 테이블 없는 산업은 판정 횟수를 소진한 뒤 스킵 — 그 판정분 보상이 영구 소실 (WorkStation.cs:64,70-74).
  • const GatherSpeedMultiplier = 6.0 — 재화 6배 배수가 컴파일 타임 상수. 되돌리려면 재컴파일 (Global.cs:26).
  • 밴/삭제 계정 응답 미전송 — 조용히 무한 대기 (AccountRepository.cs:57-68).

Top recommendation

1 · User 모듈을 세션·시계·DB 큐에서 떼어낸다

테스트 0%인 코드의 경계선이 정확히 ISession / DateTime.UtcNow / *.Instance가 처음 등장하는 지점과 일치한다 — seam 3개를 열면 재화가 생성되는 모든 경로(정산·지급·배치·속도)가 한꺼번에 테스트 가능해진다. 레버리지가 가장 크고, 후보 2(로그인 플로우 회수)와 후보 6(불변식 타입화)의 선행 조건이기도 하다. IDummyClock 스케치가 테스트 프로젝트에 이미 있어 방향도 합의돼 있다.
