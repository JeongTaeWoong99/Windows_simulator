# 서버 구조 평가 — 2026-08-06

> 대상: `MikaNetwork.Lib` · `MikaProtocol` · `WSGameServer` 전체 (테스트 프로젝트 포함 참조)
> 방법: 전수 정독. 축은 **결합도·응집도 / 테스트 용이성 / 확장성 / 유지보수성 / 코드 이해도**.
> 목적: "DI를 넣으려는데 계속 막힌다"의 **원인 지점을 특정**하고, 비즈니스 로직 구조를 확정하기 위한 판단 자료.
> 용어(모듈·인터페이스·깊이·seam·어댑터)는 [2026-08-01 리뷰](2026-08-01-서버아키텍처리뷰.md)의 표를 그대로 쓴다.

## 0. 한 줄 요약

**코드는 "생성자 주입 관례"와 "전역 도달(`*.Instance`·static) 관례가 반반 섞인 상태다.**
`User` 아래(순수 코어)는 이미 주입·인자 관통으로 깨끗하게 열려 있는데,
`User` 위(진입점·수명주기·조립)는 전부 전역 도달이다. **DI가 막히는 느낌의 정체는
"두 관례의 경계선을 넘나들 때마다 벽을 만나는 것"이고, 그 벽은 정확히 4곳이다**(4장).
결론부터: **DI 컨테이너를 넣지 말고, 전역 도달을 진입점 껍데기까지 밀어내는 명시적 조립으로 가라**(5장).

## 2. 파트별 상세

### 2-1. MikaNetwork.Lib

#### 잘 된 것 (유지할 것)

- **`ISession` 이벤트 계약** (`ISession.cs`) — Received/Connected/Disconnected + Send/Disconnect.
  전송 계층이 게임을 모르는 경계가 인터페이스 하나로 서 있다.
- **훅으로 뚫은 로그 정책** — `MikaPacketManager.Dispatching`·`UnknownReceived`,
  `MikaServer.Connected`. "Lib은 로그를 모른다, 호스트가 채운다"는 원칙이 실제로 지켜진다
  (`PacketLogger.Attach`가 유일한 채우는 곳 — 찾아갈 파일이 하나).
- **`MikaPacketManager.Register<T>`** (`MikaPacketManager.cs:33`) — "역직렬화는 네트워크 스레드,
  실행은 로직 스레드"를 클로저 한 겹으로 고정. 타입 소거가 깔끔하다.
- **`MikaServerSession`의 멱등 Disconnect** (`MikaServerSession.cs:72`) — `Interlocked.Exchange`
  가드와 그 이유가 주석으로 남아 있다. `LastReceivedAt` 갱신 위치(바이트 수신 = 생존 증거)도 정확.
- **`MikaServer.DisconnectIdle`** (`MikaServer.cs:85`) — 세션 목록·시각·임계값을 전부 인자로 받는
  static 순수 함수 + `IHeartbeatSession` 최소 인터페이스. **소켓 없이 테스트되는 설계의 모범.**
  이 패턴이 이 저장소의 "정답 관례"다 — 아래 문제들은 전부 이 관례에서 벗어난 곳에서 생긴다.

#### 문제

**P1. `MikaExecutor.cs` — 라이브러리 경계 3중 위반 (✕, 최우선)**

`DBExecutor`·`LogicExecutor`(`MikaExecutor.cs:17,69`)는:

1. **위치 위반** — "스레딩 모델"은 호스트 정책인데 프레임워크 안에 산다. 게임을 모르니 Lib에
   둘 수는 있지만, 문제는 **싱글턴이라 호스트가 개수·구성을 선택할 수 없다는 것**이다.
   로직 스레드를 2개로 파티션하고 싶어지는 순간(유저 수 증가) 라이브러리를 고쳐야 한다.
2. **수명 위반** — `Singleton<T>`(`Singleton.cs:5`)로 전역 도달 가능. 이것 때문에
   `Entity.Post → LogicExecutor.Instance`(`Entity.cs:47`)가 가능해졌고, 그 결과
   **`Entity.Create()/Destroy()`를 타는 모든 흐름(Login 전체)이 테스트 불가**가 됐다
   (2026-08-03 로그 "남은 것" 항목이 정확히 이것).
3. **로그 위반** — `Console.WriteLine`(`MikaExecutor.cs:53,99`). Lib은 로그 정책을 갖지
   않는다는 원칙을 **자기 자신이 깬다**. job 예외는 훅(`Action<Exception>?`)으로 뚫어야 맞다.

부수 결함: `DBExecutor.Start(int channelCount = 0)`의 기본값 0이면 `Post`의
`id % _channelCount`가 **DivideByZeroException**(`MikaExecutor.cs:38`). Start 전 Post도 동일.
degenerate 기본값이므로 기본값을 없애거나 최소 1로 강제해야 한다.
`MikaExecutor` 클래스 자체는 빈 껍데기(`MikaExecutor.cs:7`) — 죽은 코드.

**P2. static 훅의 프로세스 전역성 (△)**

`MikaPacketManager.Dispatching`·`UnknownReceived`가 **static 필드**다(`MikaPacketManager.cs:23,29`).
인스턴스가 여럿이어도(서버+더미클라) 훅은 하나를 공유한다. 지금은 "별도 프로세스라 안 겹친다"는
주석 전제로 버티지만, **같은 프로세스에서 서버 2개를 띄우는 통합 테스트를 쓰는 순간 깨진다.**
인스턴스 필드로 내리고, 호환이 필요하면 static은 기본값 폴백으로만 남기는 게 맞다.

**P3. 소소한 것**

- `MikaServer.Send(int sessionId, ...)`(`MikaServer.cs:50`) — SessionId는 `long`인데 `int`로 받는다.
- `SessionManager.Sessions`가 `ConcurrentDictionary`를 그대로 공개(`MikaSessionManager.cs:29`) —
  외부가 임의로 Add/Remove 가능. `IReadOnlyCollection` 노출이면 충분하다.
- `ReceiveLoop`의 잘못된 크기 프레임은 조용히 `return`(`MikaServerSession.cs:153`) —
  악성/버그 프레임이 왜 끊겼는지 호스트가 알 수 없다. `UnknownReceived`류 훅 후보.

#### MikaSourceGen — 별도 평가

`[PacketHandler]` → 등록 코드 생성 + MIKA001 누락 경고는 **드리프트를 컴파일 타임에 잡는
좋은 투자**다. 하지만 `ExtractHandler`가 **`m.IsStatic`을 요구**한다(`PacketHandlerGenerator.Handlers.cs:16`).
이 한 줄이 의미하는 것: **모든 패킷 진입점은 static이어야 한다** → static 메서드는 주입받을
생성자가 없다 → 핸들러는 의존을 전역(`UserManager.Instance`·`GachaService.Instance`)에서
가져올 수밖에 없다 → **staticness가 호출 그래프를 타고 위로 전파된다.**
"ClientPacketHandler의 static이 이상하다"는 감각의 근원이 여기다. 핸들러가 이상한 게 아니라
**제너레이터의 계약이 호스트의 조립 방식을 결정해 버린 것**이다. (해법은 5장 — 제너레이터를
고치는 것보다 싼 방법이 있다.)

### 2-2. MikaProtocol

**가장 건강한 모듈.** 패킷 정의(`MikaPacket.cs`) · Info DTO(`PacketInfo.cs`) · 결과 코드
(`PacketEnum.cs`)가 역할별 파일로 나뉘고, 주석이 계약(대역 할당, "Ok 아니면 payload null",
스냅샷/델타 구분)을 명시한다. `PacketId` enum + `[Packet]` 특성이 단일 원본이고
소스젠·분석기가 드리프트를 잡는다. Unity 미러링도 단방향이 지켜진다.

관리 대상 2가지:

1. **`MikaSessionPacketExtensions.SendPacket`이 확장 메서드(static)** (`MikaSessionPacketExtensions.cs:25`).
   "Core는 byte[]만, 프레이밍은 Protocol이" — **계층 분리 자체는 옳다.** 문제는 static이라
   `Mock<ISession>`이 가로챌 지점이 없다는 것이고, 이건 이미 정확히 진단해서
   `IClientChannel`로 풀었다(`IClientChannel.cs:6-24` 주석이 그 기록). 즉 **이 확장 메서드는
   "고칠 것"이 아니라 "직접 호출하지 말 것"이다** — 게임 로직은 `IClientChannel.Send`만 보고,
   확장 메서드 직접 호출은 껍데기(핸들러의 NotLoggedIn 응답 등)에만 남긴다. 지금 상태가 그렇다. 유지.
   `Sent` 훅이 static인 것은 P2와 동일한 관리 대상.
2. **`EGlobalRarity` ↔ `GameData.GlobalRarity` 1:1 캐스팅 계약** (`PacketEnum.cs:35`) —
   주석 + `PacketEnumTest`로 고정돼 있으면 충분하다. 값 대역 관례(1~99 공통…)도 좋다.

`IPacket`이 빈 마커 인터페이스인 것은 제네릭 제약용으로 정당하다.

### 2-3. WSGameServer

#### (a) 순수 코어 — ◎, 손대지 말 것

`WorkStationSlot`·`WorkSpeed`·`WeightedPicker`·`DropTable`·`Inventory`·`CurrencyWallet`은
시각·난수를 인자/주입으로 받고 전역을 보지 않는다(예외 1건 아래). 테스트가 목 없이 돌고,
"속도 변경 전 반드시 정산" 같은 기획 규칙이 테스트로 고정돼 있다(2026-08-03 로그의 red 확인).
**이 계층의 관례 — `now` 인자 관통, `IClock` 미도입 — 는 확정으로 못 박아라.**
리팩토링하다가 이 계층에 인터페이스를 "정리 차원에서" 추가하고 싶어질 텐데, 어댑터가
2개 생기기 전까지는 하지 않는 게 맞다(어댑터 1개 = 가설상의 seam).

예외 1건: `WorkStation.Settle`의 `catalog ??= DropTableCatalog.Instance`(`WorkStation.cs:59`) —
순수 코어에 전역 폴백이 박혀 있다. 호출자(`User.SettleWorkStation`)가 이미 `_dropTables`를
항상 넘기므로 기본값을 지우고 필수 인자로 바꿔도 깨지는 곳이 없다. 지워라.

#### (b) User 도메인 — ○, seam은 열렸는데 잔여 전역 2개

**잘 된 것:** `User` 생성자가 `IClientChannel`·`IDBQueue`·`DropTableCatalog?`를 받는다
(`User.cs:42`). 어댑터가 각각 2개씩(운영 + Fake) 있으므로 **진짜 seam**이다.
partial 분할(WorkStation/Inventory/Currency/Character/DB)도 관심사별로 응집돼 있고,
"Row는 User partial까지, 코어에는 도메인 객체만"(`User.DB.cs:31-36`) 경계가 명문화·준수된다.

**잔여 전역 2개가 "80% 주입, 20% 전역" 상태를 만든다:**

1. **`Entity` 상속** — `User`의 수명주기(Create/Destroy)가 `Entity.Post →
   LogicExecutor.Instance`(`Entity.cs:47`)에 직결. 그래서 `TestUserBuilder`는 `Create()`를
   **우회**하고(주석에 명시), `Login()` 전체 흐름·`OnCreate → AccountRepository` 경로는
   여전히 테스트 0이다. 또한 `OnDestroy` 시그니처가 고정이라 `Disconnect(DateTime now)`를
   한 겹 갈라야 했다(`User.cs:105` 주석) — **상속이 시각 인자 관통 관례와 충돌한 비용**이다.
   덧붙여 `Entity.Post(ulong id, Action)`은 `id`를 버린다(`Entity.cs:45-48`) — C++
   JobSerializer(키별 직렬화)의 흔적인데 지금은 단일 로직 스레드라 의미가 없다. 죽은 파라미터.
2. **`User → UserManager.Instance` 역참조** — `Login()`이 `JoinUser(this)`를,
   `Disconnect()`가 `LeaveUser(this)`를 직접 부른다(`User.cs:81,126`).
   User↔UserManager **양방향 결합**이라, User를 테스트하려면 전역 UserManager의 상태가
   오염되고(테스트 간 간섭), UserManager를 교체할 수도 없다.

`Entity`의 실제 서브클래스는 **User 하나뿐**이다. 추상 클래스 + 가상 메서드 3개
(OnCreate/OnDestroy/OnUpdate — OnUpdate는 사용처 없음)가 제공하는 것에 비해,
"base 시그니처 고정"·"실행기 전역 직결"·"테스트 우회" 비용이 더 크다.
**상속이 아니라 조합으로 바꿀 후보 1순위다**(5장).

#### (c) 진입·조립 — ✕, 이번 평가의 핵심 결함

**조립 지점(composition root)이 없다.** 현재 배선은:

```
Program.cs      ── ServiceCollection에 GameServer 하나 등록 (장식)
GameServer.Run  ── 싱글턴 7개를 순서대로 Initialize (진짜 조립)
NetworkManager  ── MikaServer·ClientPacketManager를 필드 초기화로 직접 생성
UserManager     ── CreateUser 안에서 SessionClientChannel·DBManager.Instance·UtcNow를 직접 조립
ClientPacketHandler ── static이라 UserManager.Instance·GachaService.Instance로 도달
```

문제를 축별로:

- **결합도**: `.Instance` 도달이 WSGameServer에만 23곳. 의존 그래프가 생성자에 드러나지 않아
  "누가 누구를 쓰는지"를 코드 전수 검색으로만 알 수 있다. **DI를 넣으려 할 때 막히는 직접 원인** —
  컨테이너에 등록하려고 보면 생성자가 아무것도 안 받는데 몸통이 전역을 부르고 있어서,
  등록해도 아무것도 주입되지 않는다.
- **순서 결합**: `GameServer.Run`(`GameServer.cs:10-34`)의 초기화 순서 제약
  (LoadAll → 카탈로그 / Attach → Listen / Listen → Watchdog)이 **주석으로만** 존재한다.
  순서를 바꾸면 컴파일은 통과하고 런타임에 어긋난다. 생성자 인자로 바꾸면 순서가 타입으로 강제된다.
- **종료 경로 부재**: `Console.ReadLine()` 후 그냥 프로세스 종료. `DBExecutor.Stop`·
  `LogicExecutor.Stop`·`GatheringScheduler.Stop`이 존재하지만 **아무도 부르지 않는다.**
  종료 시점에 DB 큐에 남은 저장 작업(마지막 정산 포함)이 유실될 수 있다.
- **`Program.cs`의 DI 컨테이너**(`Program.cs:13-19`)는 `GameServer` 하나만 등록 — 현재로선
  `new GameServer().Run()`과 동일하다. **이 장식이 "DI를 하고 있다"는 착시를 만든다.**
  지우거나, 진짜 조립 지점으로 승격하거나 둘 중 하나다(권고는 후자 아님 — 5장).

`SessionUserExtensions.GetUser`(`SessionUserExtensions.cs:11`)도 같은 부류다 —
확장 메서드라 `UserManager.Instance` 외에 도달할 방법이 없다. "Session에 User 역참조를
두지 않는다"는 설계 자체는 옳고, 문제는 static 진입점에서 매니저를 찾는 방법뿐이라는 것.
핸들러가 인스턴스 문맥을 얻으면(5장) 이 확장 메서드는 자연히 그 문맥의 메서드가 된다.

- `GachaService`는 상태가 없는데 `Singleton<T>`다(`GachaService.cs:12`).
  검증·조립·응답만 하므로 사실상 함수 묶음 — 싱글턴일 이유가 없고,
  `GachaPoolCatalog.Instance` 도달(`GachaService.cs:27`)만 주입으로 바꾸면 그대로 테스트 가능해진다.
- `UserManager.JoinUser`의 `TryAdd` 3연발(`UserManager.cs:109-111`)은 반환값을 버린다 —
  부분 실패 시 매핑 3개가 어긋난 채로 진행된다. LeaveUser는 값 일치 오버로드로 신중하게
  지우면서(주석까지 있다) Join은 검사하지 않는 비대칭.

#### (d) DB·Repository — ○~◎

- **`IRepository`의 2단계 계약**(ExecuteAsync = DB 스레드, 읽기/쓰기 · Apply = 로직 스레드,
  상태 반영)은 스레드 규율을 타입으로 표현한 좋은 설계다. `LoginRepository`(`LoginRepository.cs`)의
  "Row 수집까지만" 규율, `Key`로 유저별 직렬화도 명료하다.
- `DBManager`는 `IDBQueue` 구현 + 커넥션 팩토리 주입(`DBManager.cs:14`)으로 두 층의 seam이
  잘 갈라져 있다(주석의 "커넥션이 아니라 큐를 자른다" 구분이 정확하다).
  흠은 `DBExecutor.Instance`·`LogicExecutor.Instance` 직결(`DBManager.cs:54,62`) —
  실행기가 주입되면 DBManager 자체도 통합 테스트 가능해진다.
- Repository가 `User`를 직접 들고 `Apply`에서 `User.OnLoginDataLoaded`를 부르는 구조는
  Repository→User 결합이지만, 콜백 계층을 하나 더 파는 비용 대비 현재 규모에서 이득이 없다. 유지.

#### (e) 스케줄러·감시자 — ○

`GatheringScheduler.Tick(now, users)`·`SessionWatchdog.Sweep(now)` 모두
"타이머는 시각·대상만 만들고 본체는 인자로 받는 static/인스턴스 함수" 패턴으로 검증 가능하게
돼 있다. 남은 것은 타이머 콜백 안의 `UserManager.Instance.All`·`LogicExecutor.Instance`뿐 —
조립이 바뀌면 함께 주입으로 바뀐다. 두 타이머를 합치지 않은 근거(주기·관심사 상이)도 문서화돼 있다.

## 4. "DI가 계속 막히는" 진짜 이유 — 초크포인트 4개

네가 열거한 증상(Extensions Session, ClientPacketHandler static, Entity 상속)은 전부
아래 4개 중 하나로 환원된다. **이 4개 밖에서는 이미 DI가 잘 되고 있다**(User seam 3개가 증거).

| # | 초크포인트 | 증상 | 원인 | 판정 |
|---|---|---|---|---|
| 1 | **소스젠의 static 핸들러 강제** (`PacketHandlerGenerator.Handlers.cs:16`) | ClientPacketHandler가 static이라 아무것도 주입 못 받음 → 몸통이 `*.Instance`로 도달 → 그 아래 서비스도 전부 싱글턴이어야 함 | 제너레이터 계약이 호스트 조립 방식을 결정 | **구조적 원인 ①.** static 자체가 악이 아니라, static "몸통"이 문제. 껍데기화로 해소(5장) |
| 2 | **Entity 상속 + 실행기 싱글턴** (`Entity.cs:47`) | Create/Destroy가 전역 실행기로 직행 → 수명주기 테스트 불가, OnDestroy 시그니처 고정으로 now 인자 관통 관례와 충돌 | 수명주기 가드(좋음)와 실행기 라우팅(전역)이 한 클래스에 융합 | **구조적 원인 ②.** 서브클래스 1개뿐 — 상속을 조합으로 |
| 3 | **확장 메서드 진입점** (`SendPacket`·`GetUser`) | Mock이 가로챌 지점 없음 | static 호출은 객체를 거치지 않음 | 송신 쪽은 `IClientChannel`로 **이미 해결**. `GetUser`는 #1이 풀리면 문맥 메서드로 자연 해소 |
| 4 | **조립 지점 부재** (`GameServer.Run` 싱글턴 사슬) | 컨테이너에 등록해 봐야 생성자가 비어 있어 주입될 게 없음. 등록↔실사용 이중화만 생김 | 의존이 생성자가 아니라 몸통 속 `.Instance`에 있음 | **구조적 원인 ③.** 이게 풀려야 #1·#2를 풀 자리가 생긴다 |

**중요한 판단: Microsoft.Extensions.DependencyInjection 컨테이너는 이 서버에 맞지 않는다.**

- 서비스가 ~10개다. 컨테이너의 가치(수백 개 등록·수명 관리·스코프)가 발생하지 않는다.
- 컨테이너의 수명 개념(Transient/Scoped/Singleton)이 이 서버의 실제 수명 모델
  (**로직 스레드 감금 + 세션 수명 + 파티션 직렬화**)과 겹치지 않는다. Scoped를 세션에
  대응시키려는 순간 스레드 모델과 싸우게 된다 — 지금 막히는 느낌의 상당 부분이 이 불일치다.
- 이 저장소의 강점은 "의존이 생성자에 보인다"는 관례다. 컨테이너는 그걸 등록 코드로
  한 겹 가리는 대신 얻는 게 없다.

**필요한 건 컨테이너가 아니라 조립 지점이다.** DI의 본질(의존을 밖에서 넣는다)은
`new`를 한곳에 모으는 것으로 충분히 달성된다.

## 5. 권고 — 명시적 조립으로 가는 순서

원칙: **전역 도달을 진입점 껍데기까지 밀어낸다. 껍데기(핸들러 static 메서드·타이머 콜백·Main)만
전역을 알고, 그 아래는 전부 생성자 인자다.** 각 단계는 독립 커밋이고, 단계마다 테스트가 늘어난다.

### 1단계 — `Entity` 해체 (작다, 효과 크다)

- `Entity`를 없애고 `User`에 직접 넣는다:
  - 수명주기 가드(`_created`/`_destroyed` Interlocked)는 그대로 User로 이동 — **이 로직 자체는 좋다.**
  - `Post`는 생성자 주입 `Action<Action> postToLogic`(운영 = `LogicExecutor.Instance.Post`,
    테스트 = 즉시 실행 `job => job()`)으로.
  - `OnCreate/OnDestroy` 가상 메서드 대신 `Create(DateTime now)`/`Destroy(DateTime now)`가
    직접 본체를 부른다 — **시그니처 고정 문제가 소멸**하고 `Disconnect(now)` 갈래가 불필요해진다.
- 효과: `TestUserBuilder`가 `Create()`를 우회할 필요가 없어지고, **Login 전체 흐름
  (OnCreate → AccountRepository → Initialize → LoginRepository → Login)이 Fake 큐 위에서
  동기로 테스트 가능**해진다. 3장의 최대 공백이 닫힌다.
- `Global.AllocKey64`는 User 생성자에서 받는 인자(기본값 = 전역 호출)로 두면 충분하다.

### 2단계 — User↔UserManager 역참조 절단

- `IUserRegistry { void Join(User); void Leave(User); }`를 User 생성자에 추가.
  운영 구현 = UserManager, 테스트 = 기록만 하는 Fake.
- `Login()`의 `JoinUser(this)`, `Disconnect()`의 `LeaveUser(this)`가 주입분을 쓴다.
- 효과: 중복 로그인 시나리오(`CreateUser`의 pid 선점 해제·값 일치 삭제 — 지금 가장 미묘한
  동시성 코드)를 전역 오염 없이 테스트할 수 있다. `JoinUser`의 TryAdd 무검사도 이때 같이 고친다.

### 3단계 — 조립 지점 수립 + 핸들러 껍데기화

- `GameServer`가 진짜 조립 지점이 된다: `LogicExecutor`·`DBExecutor`·`DBManager`·
  `UserManager`·`GachaService`·카탈로그들을 **생성자 사슬로 조립**하고, 초기화 순서를
  생성자 인자 의존으로 강제한다. `Singleton<T>` 상속은 조립이 끝난 클래스부터 제거.
- 핸들러는 static 껍데기로 유지(소스젠 계약 존중)하되 몸통을 인스턴스로 뺀다:

  ```csharp
  // 조립 시점에 한 번 꽂는다 — 전역이지만 "쓰기 1회, 진입점에서만 읽기"로 규율
  public static class ClientPacketHandler
  {
      public static HandlerContext Context = null!;   // UserManager·GachaService… 보유

      [PacketHandler]
      public static void Handle_C_GachaDrawRequest(ISession s, C_GachaDrawRequest req)
          => Context.Gacha.Draw(s, req);              // 껍데기 한 줄
  }
  ```

  `HandlerContext`(이름은 자유)는 평범한 클래스라 테스트에서 Fake 의존으로 직접 조립·호출한다.
  **핸들러 분기 로직(NotLoggedIn 응답 등)이 처음으로 테스트 대상이 된다.**
  `GetUser` 확장 메서드는 Context의 메서드로 이동.
- `Program.cs`의 ServiceCollection은 제거한다(장식 유지 비용만 있다).
- 종료 경로를 이때 만든다: ReadLine 후 `GatheringScheduler.Stop → 접속 세션 정리 →
  DBExecutor.Stop`(큐 드레인) 순서. 마지막 정산 유실이 닫힌다.

### 4단계 — Lib 정리 (게임과 무관, 마지막)

- `DBExecutor`·`LogicExecutor`에서 `Singleton<T>` 상속 제거 — 평범한 클래스로.
  (3단계까지 끝나면 `*.Instance` 참조가 조립 지점 한 곳에만 남아 있어서 기계적 치환이다.)
- `Console.WriteLine` → 예외 훅(`Action<Exception>?`), `Start(0)` 기본값 제거,
  빈 `MikaExecutor` 클래스 삭제, `MikaPacketManager` 훅의 인스턴스화.
- 이 시점에 Executor를 Lib에 남길지 WSGameServer로 옮길지 결정 — 싱글턴이 아니게 되면
  "게임을 모르는 범용 실행기"로서 Lib 잔류도 정당해진다. **옮기는 것 자체는 부차적 문제다.**

### 하지 말 것

- `IClock` 도입 — 08-03에 철회한 결정 유지. 인자 관통 관례가 이미 이긴다.
- 순수 코어에 인터페이스 추가 — 어댑터 2개가 생기기 전까지 금지.
- 소스젠을 인스턴스 핸들러 지원으로 개조 — 껍데기 한 줄이면 충분한 문제에
  제너레이터+Unity 클라 양쪽 개조 비용을 쓰지 않는다. 껍데기가 10줄 넘게 불어나면 그때 재검토.
- 4단계 전에 콘텐츠 추가와 리팩토링을 한 커밋에 섞는 것 — 08-03 로그의 규율
  ("리팩터링과 동작 변경을 한 커밋에 섞지 않는다") 유지.

## 7. 맺음 — 지금 구조에 대한 종합 판단

C++에서 가져온 세 구조의 성적표:

- **Executor(스레드 파티션) 모델** — **유지할 가치가 있다.** "게임 상태는 로직 스레드 감금,
  DB는 키 파티션 직렬"은 락 없는 단순함을 주고 있고, 2단계 Repository 계약과 잘 맞물린다.
  문제는 모델이 아니라 **전역 도달로 구현된 것**뿐이다.
- **Entity 상속** — **버려라.** 서브클래스 1개, 가상 메서드 시그니처 고정이 시각 관통 관례와
  충돌, 전역 실행기 직결로 테스트 벽. 가드 로직만 회수하면 잃는 게 없다.
- **Manager 싱글턴 군** — **반은 유지, 반은 해체.** "매니저"라는 응집 단위는 좋다.
  `Singleton<T>` 상속(어디서든 도달 가능)만 벗기고 조립 지점이 들고 있는 평범한 인스턴스로 바꾼다.

이 저장소는 이미 자기 안에 정답 관례를 갖고 있다 — `DisconnectIdle`의 인자 관통,
`IClientChannel`/`IDBQueue`의 실사용 기반 최소 인터페이스, 2단계 Repository.
**리팩토링의 방향은 "새 패턴 도입"이 아니라 "이미 이긴 관례를 위쪽 계층까지 확장"이고,
그 종착지는 컨테이너 없는 명시적 조립이다.** 1~3단계가 끝나면 로그인·중복 로그인·가챠·핸들러
분기가 전부 테스트 아래로 들어오고, 그 위에서 콘텐츠를 얹으면 된다.
