# 05. 거래 (Trade)

> 상위 문서: [`게임기획코어.md`](../게임기획코어.md)
> 최종 업데이트: 2026-07-26 · 상태: **골격만 · 경제 전부 미정**

이 게임의 **유일한 경쟁 축**이자, 승패 조건이 없는 게임에서 **장기 목표를 대신하는 시스템**이다.
동시에 가장 리스크가 큰 영역이다 — 경제·수익화가 "미정"인 채로 남아 있다.

---

## 1. 확정 사항

- 모든 아이템을 **거래소**에 등록해 화폐(돈)를 얻을 수 있다.
- 이를 통해 자원을 축적하고 유저 간 경쟁이 발생한다.
- 승패 조건은 없고, 장기 목표는 자원 축적과 거래 경쟁이다.

경제/수익화(BM)는 **"아직 고려하지 않음"** 상태다.

---

## 2. 거래 방식 (제안)

> ⚠️ 전부 제안이다. 방식 선택이 이후 모든 설계를 가른다.

| 방식 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. **자유 거래소** | 유저가 가격 지정, 최저가 매칭 | 경쟁·시세 재미 최대 | 봇·시세 조작·인플레 전부 발생 |
| B. **주문서(오더북)** | 매수/매도 호가 매칭 | 유동성 좋음 | 구현·UI 복잡. 방치형 대비 과함 |
| C. **NPC 고정가 + 시세 변동** | 유저 간 직접 거래 없음, 가격만 변동 | 통제 쉬움, 봇 무의미 | "유저 간 경쟁"이 사라짐 → 확정 기획 위반 |
| D. **A + 가격 상하한** | 자유 거래 + 기준가 대비 밴드 제한 | 조작 억제하며 경쟁 유지 | 밴드 설계 난이도 |

> 권장: **D**. 확정 기획이 요구하는 "유저 간 경쟁"을 지키면서, 방치형 규모에 맞는 통제를 유지한다.
> C는 핵심 요구(경쟁)를 없애므로, 채택하려면 [`게임기획코어.md`](../게임기획코어.md) 수정이 선행돼야 한다.

---

## 3. 경제 구조

### 3.1 재화 흐름

```
[faucet]  채취 ──→ 아이템 ──→ 거래소 ──→ 화폐 ──→ ? 
                                              ↑
[sink]                                     여기가 비어 있음
```

**현재 설계의 가장 큰 구멍: 화폐 sink가 없다.**
화폐를 버는 경로(거래)는 있는데 쓰는 경로가 기획에 없다.
sink가 없으면 화폐는 무한 누적되고 가격은 계속 오른다.

sink 후보:

| sink | 설명 | 강도 |
| --- | --- | --- |
| 거래 수수료 | 등록비 + 판매 수수료 (%) | 상시·완만 |
| 특성 해금 비용 | 재료 대신/추가로 화폐 소모 | 초중반 강함 |
| 인벤토리 확장 | 용량 제한 도입 시 | 1회성 |
| 편의 기능 | 채취 슬롯 추가, 오프라인 상한 연장 | 지속 |
| 외형·꾸미기 | 위젯 스킨 등 | 후반 |

> 최소한 **거래 수수료 + 성장 비용** 두 개는 필요하다.

### 3.2 봇·다계정 대응

방치형 + 거래소 조합은 봇에게 이상적인 환경이다. (조작 없이 재화가 생성되므로)

| 위험 | 대응 후보 |
| --- | --- |
| 다계정 파밍 | 계정당 채취 상한, 계정 생성 제한 |
| 시세 조작 | 가격 밴드(방식 D), 1인 등록 수량 제한 |
| RMT | 거래 로그 감사, 이상 거래 탐지 |
| 자전거래 | 수수료를 자전거래가 손해가 되도록 설계 |

## 4. 데이터 설계 (제안)

거래소는 **테이블(정적 데이터)이 아니라 DB(동적 데이터)** 다.

| DB 테이블(제안) | 용도 | 비고 |
| --- | --- | --- |
| `trade_listing` | 등록된 판매 건 | 판매자, `ItemTID`, 수량, 단가, 등록시각, 상태 |
| `trade_history` | 체결 내역 | 시세 산출·감사 로그 겸용 |
| `user_wallet` | 화폐 잔액 | |

`Server/Shared/game.sqlite3`에 STRICT 테이블로 만들고, 모든 컬럼에 주석을 단다
(`Server/.claude/skills/sqlite-sql-creator` 규칙).

엑셀 테이블로 갈 것: 수수료율, 가격 밴드 배수, 등록 수량 상한 등 **밸런스 상수**.

## 5. 서버 / 클라이언트 책임

| 책임 | 주체 |
| --- | --- |
| 등록·취소·구매 전 과정 | **서버** (전부) |
| 잔액·재고 검증 | **서버** |
| 동시 구매 경합 처리 | **서버** (트랜잭션 필수) |
| 시세 계산 | **서버** |
| 목록·시세 차트 표시 | 클라이언트 |

> 거래는 실질 가치가 오가는 지점이다. 클라이언트 계산 결과를 어떤 경우에도 신뢰하지 않는다.
> 동시 구매(같은 매물을 두 명이 동시에)는 반드시 트랜잭션으로 막는다.
