# 게임기획코어 — Window Simulator

> 최종 업데이트: 2026-07-31
>
> **이 문서는 게임 기획의 최상위 문서이자 단일 진입점이다.**
> 게임 시스템·콘텐츠를 개발하는 모든 작업은 착수 전에 이 문서를 먼저 읽고,
> 해당 영역의 **상세 기획안**을 이어서 읽는다.
> 상세 수치·예외는 여기 쓰지 않는다. 여긴 **"무엇을 왜 만드는가"**만 담는다.

## 1. 정체성

| 항목 | 내용 |
| --- | --- |
| 한 줄 요약 | 바탕화면 위에서 자라는, **캐릭터를 배치해 굴리는** 1차 산업 방치 게임 |
| 장르 | 방치형 · 경영/수집 |
| 플랫폼 | Windows 데스크톱 (투명 창 위젯, 상시 동작) |
| 아트 | Pixel + Stylized (AI) |
| 승패 조건 | **없음.** 장기 목표는 자원 축적과 거래 경쟁 |
| 세션 형태 | 몰입형 세션이 아님. 업무·일상 중 바탕화면 한켠에서 진행 |

### 설계 원칙 (Design Pillars)

개발 중 판단이 갈릴 때 **이 4개를 기준으로 결정한다.**

| # | 원칙 | 의미 | 위반 예시 |
| --- | --- | --- | --- |
| P1 | **주의를 뺏지 않는다** | 플레이어의 주 작업은 게임이 아니다. 알림·모달·소리는 최소 | 필수 클릭 타이머, 화면 중앙 팝업 |
| P2 | **띄워만 두면 자란다** | 바탕화면에 떠 있는 동안 조작 없이 진행. **접속이 곧 플레이다** | 진행하려면 클릭·조작이 필요함 |
| P3 | ~~**하루 단위로 달라진다**~~ ❌ | **근거 폐기 — 재정의 필요** (아래) | — |
| P4 | **모든 재화는 흐른다** | 획득물은 거래소를 통해 유저 간 순환. 계정에 고이지 않음 | 거래 불가 귀속 아이템의 남발 |

> ⚠️ P1~P4는 초기 컨셉에서 **도출한 제안**이다. 기획자 확정 전이며,
> 확정 시 이 표에서 ⚠️ 표기를 제거한다.

#### P2가 재정의됐다 (2026-07-29)

~~**꺼져 있어도 자란다** — 오프라인 진행이 기본. 접속은 수확·정산을 위한 행위~~

**오프라인 진행이 폐지되면서** 이 문구가 성립하지 않는다. 대신 P2의 본래 의도는
**"쳐다보지 않아도 자란다"** 였고, 그건 그대로 유지된다.

이 게임은 **바탕화면 위젯으로 상시 동작**한다(1장 정체성). 업무 중 띄워 두면
접속 시간이 자연히 하루 대부분이 되므로, "접속 중에만"이 곧 "PC를 쓰는 동안"이다.
**클릭·조작 없이 진행된다**는 방치형의 핵심은 변하지 않는다.

| | 이전 | 현재 |
| --- | --- | --- |
| 진행 조건 | 시간이 흐르면 (접속 무관) | **클라이언트가 접속해 있으면** |
| 접속의 의미 | 쌓인 것을 수확하러 온다 | **접속 자체가 플레이다** |
| 리텐션 축 | "돌아오면 뭔가 쌓여 있다" | **"켜 둘 만하다"** ← 게임UI의 요구사항이 된다 |

> ⚠️ **복귀 유인이 사라졌다.** 오프라인 누적은 방치형의 대표적인 복귀 장치인데
> 접속 보상까지 두지 않기로 했으므로, 이제 위젯 자체가 **띄워 둘 만해야** 한다.
> → [게임 UI](게임UI/README.md)

#### ⚠️ P3가 근거를 잃었다 (2026-07-29)

P3는 **요일 로테이션**을 근거로 삼고 있었는데, 요일 시스템이 **폐지**됐다.
현재 게임에는 "하루 단위로 달라지는" 장치가 하나도 없다.

| 후보 | 성격 |
| --- | --- |
| 슬롯 재배치 | 플레이어가 원할 때 바꾼다 — **하루 주기가 아니다** |
| 캐릭터 육성 | 누적 성장 — 주기성 없음 |
| 일일 퀘스트 | 미작성 시스템. 여기에 리듬을 맡길 수는 있다 |

**P3를 되살릴지(다른 장치로), 아예 4개 원칙에서 뺄지 결정이 필요하다.**
그때까지 P3를 근거로 한 판단은 하지 않는다. → 5장 미확정

## 2. 코어 루프

```
캐릭터 배치 → 자원 채취 → 보상 → 캐릭터 + 특성 + 아이템 → 재배치 → 거래
  (슬롯)       (방치)      (희귀)        (성장)            (가속)   (축적·경쟁)
```

| 단계 | 하는 일 | 담당 시스템 |
| --- | --- | --- |
| **캐릭터 배치** | **작업슬롯에 산업을 지정하고 캐릭터를 배치** | [작업슬롯](작업슬롯/README.md) |
| 자원 채취 | **배치된 슬롯마다** 자동 진행되며 자원 획득 | [자원채취](자원채취/README.md) |
| 보상 | 자원·아이템 지급, 낮은 확률로 희귀 보상 | [자원채취](자원채취/README.md) · [아이템](아이템/README.md) |
| 성장 | 자원으로 특성·스킬 해금, 채취 효율 상승 | [특성](특성/README.md) · [아이템](아이템/README.md) |
| 재채취 | 강화된 상태로 루프 반복(가속) | [자원채취](자원채취/README.md) |
| 거래 | 잉여 자원을 화폐로 전환, 유저 간 경쟁 | [거래](거래/README.md) |

루프에 목표를 부여하는 **[퀘스트](퀘스트/README.md)** 와, 루프 전체의 속도를 규정하는
**[진행 및 성장](진행%20및%20성장/README.md)** 이 위 5단계를 가로지른다.

## 4. 콘텐츠 지도

### 1차 산업 5종 (확정)

게임의 채취 콘텐츠는 **농사 · 벌목 · 낚시 · 채굴 · 사냥** 5종이다.
각 산업은 서로 다른 고유 축을 하나씩 갖는다 — 스킨만 다른 반복이 되지 않게 하기 위함이다.

**플레이어는 작업슬롯마다 산업을 하나씩 지정한다.** 슬롯이 여러 개면 여러 산업이 동시에 돈다.
산업은 수치가 아니라 **플레이어가 느끼는 심리**로 구분한다 —
"무엇이 나오는가"가 아니라 **"왜 이걸 고르는가"** 가 산업의 정의다.

| 산업 | enum | **심리 정의** | 투자 비유 | 고유 메커니즘 | 상세 |
| --- | --- | --- | --- | --- | --- |
| **낚시** | `Fishing` ✅ | **확실한 도파민** | 소액 잦은 당첨 | 없음 ⚠️ | [낚시](자원채취/낚시/README.md) |
| **농사** | `Farming` ✅ | **안정적인 수익** | 적금 | 파종 선택 | [농사](자원채취/농사/README.md) |
| **채굴** | `Mining` ✅ | **확실한 스노우볼** | 복리 장기투자 | 깊이 누적 | [채굴](자원채취/채굴/README.md) |
| **벌목** | `Logging` ✅ | **절제하면 지속되는 수익** | 배당주 | 자원 고갈·재생 | [벌목](자원채취/벌목/README.md) |
| **사냥** | `Hunting` ❌ | **도전 · 목표 지향** ⚠️ | 적립식 목표 투자 | 사냥터 + **보스** | [사냥](자원채취/사냥/README.md) |

5개 산업이 **투자 성향 스펙트럼**을 이룬다. 슬롯이 늘어날수록
**"어떤 조합으로 채울까"** 가 이 게임의 질문이 된다.

> 주기와 실패는 전 산업 공통이지만, **희귀도 분포는 2026-07-31부터 산업별로 다르게 둘 수 있다.**
> 수치 차별화 수단은 **회당 산출 + 희귀도 분포** 둘이고, 여기에 **고유 메커니즘**이 더해진다.
> → [자원채취](자원채취/README.md) 1-1

### 작업슬롯 — 배치로 굴린다 (2026-07-29 확정)

**플레이어는 작업슬롯(`WorkStationSlot`)을 여러 개 갖는다.**
슬롯마다 **산업 1개를 지정**하고 **캐릭터 1명을 배치**하면 그 슬롯이 독립적으로 돌아간다.

| 항목 | 내용 |
| --- | --- |
| 슬롯당 캐릭터 | **1명** (확정) |
| 슬롯당 산업 | 1개 (5종 중 선택) |
| 최대 슬롯 수 | **레벨 등으로 증가** — 증가 곡선 미정 |
| 동시 가동 | **슬롯 수만큼** |

> 이 결정으로 **"산업 택 1"과 "요일 로테이션"이 폐지**됐다.
> 슬롯이 늘어나면 결국 5종을 다 돌리게 되므로, 요일 보너스는 선택을 유도할 대상이 없어진다.
> → [작업슬롯](작업슬롯/README.md)

> ⚠️ **슬롯 수가 곧 재화 생성량의 배수이고, 여기에 캐릭터 속도까지 곱해진다.**
> 슬롯마다 배치된 캐릭터가 다르므로 **실효 채취 주기도 슬롯마다 다르다.**
> 총량 = 접속 시간 × 슬롯 수 × 속도 배수 — 세 항이 전부 곱셈이다.

### ~~요일 로테이션~~ — **폐지 (2026-07-29)**

요일별 보너스 산업 · 주말 택1 ×2를 **전부 없앤다.**
슬롯 구조에서는 플레이어가 여러 산업을 동시에 돌리므로 "오늘 무엇을 고를까"라는 질문이 성립하지 않는다.

**영향:** 설계 원칙 **P3가 근거를 잃었다**(1장 참조). 효율배수에서 요일 항이 빠진다.

### ~~오프라인 누적~~ — **폐지 (2026-07-29)**

**접속 중에만 자란다.** 오프라인 진행도, 접속 보상도 없다.

| 시점 | 동작 |
| --- | --- |
| 접속 | 모든 슬롯이 **진행도 0에서** 시작한다 |
| 접속 중 | 슬롯마다 독립적으로 채취가 진행된다 |
| 접속 종료 | 완성된 판정은 지급하고, **진행 중이던 조각은 버린다** |
| 비접속 | **아무 일도 일어나지 않는다** |

> ~~경과 시간 전체가 100%로 쌓인다~~ / ~~24시간 이후 -50%~~ **둘 다 폐지.**
> 오프라인 구간이 사라지면서 감쇠·상한 논의 자체가 없어졌다.

**이 결정으로 해소된 것:**

- ⚠️ ~~무한 누적 → 복귀 시 대량 재화 유입~~ — 총량이 **접속 시간에 정비례**하므로
  시간당 산출만 정하면 경제 총량이 정해진다. 밸런싱이 크게 쉬워졌다.
- ⚠️ ~~오프라인 정산 부담이 슬롯 수에 비례~~ — 한 번에 정산할 구간이 세션 길이로 묶인다.
- ⚠️ ~~버프가 오프라인 구간에 소급 적용되는 문제~~ — 모든 속도 변경 구간을 서버가 관측한다.

> ⚠️ **대신 "접속 중" 판정이 곧 재화 생성 조건이 됐다.**
> TCP는 클라이언트가 죽어도 서버가 즉시 알지 못해, 노트북을 덮거나 랜선을 뽑으면
> 수십 초~수 분간 채취가 계속 쌓인다 — 없애려던 오프라인 진행의 뒷문이다.
> **하트비트로 끊김을 빠르게 감지해야 한다.**
> → [작업슬롯](작업슬롯/README.md) 3.3

> **PC 절전은 끊김으로 본다.** 절전 진입 시 소켓이 닫히므로 그 구간은 진행하지 않는다.

### 식별자 규칙 — DB에 저장되는 정수는 의미를 바꾸지 않는다

**한 번 DB에 쓰인 식별자는 영원히 그 뜻이어야 한다.** 엑셀을 고쳐도 이미 디스크에 적힌
정수는 아무도 다시 쓰지 않기 때문이다.

| 저장되는 정수 | 값을 정하는 주체 | 위험 | 규칙 |
| --- | --- | --- | --- |
| **enum** (`ItemType`·`CurrencyType`) | 엑셀 `EID` 컬럼 | 중간에 끼우면 **뒤가 전부 밀린다** | **뒤에만 추가한다** |
| **테이블 TID** (`ItemTID`·`CharacterTID`) | 엑셀에 직접 적는다 | 밀리지는 않는다. 대신 **폐기한 번호를 되쓰면** 옛 DB 행이 다른 것으로 둔갑 | **번호를 재사용하지 않는다** |
| **참조 전용** (`ItemRarity` — DB 컬럼 없음) | 엑셀 | 없음 | 자유롭게 바꿔도 된다 |
| **DB 발급 PK** (`t_character.character_id`) | DB (auto increment) | 없음 | — |

- **`.bytes`는 이 규칙과 무관하다.** 엑셀에서 매번 다시 생성되고 서버·클라가 같이 갱신되므로
  번호가 바뀌어도 어긋날 수 없다. **문제는 DB와 패킷 와이어다.**
- **패킷**은 클라·서버 버전이 갈릴 수 있을 때만 위험하다. 구버전 클라가 보낸 `5`를
  신버전 서버가 다른 뜻으로 읽는다. 강제 업데이트가 보장되면 무시해도 된다.

> ⚠️ **두 개의 사각지대가 있다.**
> - `DataLog`의 JSON은 enum을 **이름**으로 덤프하므로 번호를 바꿔도 **diff에 아무것도 안 나온다.**
>   안전한 경우에도 변경 사실 자체가 리뷰에서 보이지 않는다.
> - `Ref` 무결성 검사는 **엑셀 안에서 엑셀만** 검사한다. DB에 살아 있는 TID를 시트에서 지워도
>   검증은 통과하고, DB에만 참조 불가능한 고아가 남는다.

### 희귀도 (코드 확정값)

`GameData.ItemRarity` — `Common` → `Uncommon` → `Rare` → `Epic` → `Legendary` → `Mythic` 6단계.
등급별 색상까지 `Enum.xlsx`에 정의되어 있다. **드랍 확률은 미정.**

**희귀도가 아이템 분류의 유일한 등급 축이다.** 개체 변량(크기 등 개체별 수치 롤)은 두지 않는다.
"더 큰 것 / 더 좋은 것"은 희귀도가 높은 **별도 `ItemTID`** 로 만든다.
예: `붕어(Common)` / `월척 붕어(Rare)` / `대물 붕어(Epic)`.

> 이 결정으로 모든 아이템이 정상 스택되고, 정산이 단순 집계로 끝난다.

#### ~~희귀도 분포 = 전 산업 동일 · `RarityWeightTable` 단일 원본~~ — **폐지 (2026-07-31)**

**이 폐지로 되살아나는 것 — 산업 차별화 수단이 다시 생겼다.**

> ⚠️ **대가는 밸런싱 비용이다.** 5개 분포를 따로 관리하므로 의도치 않게 어긋나기 쉽다.

### ⚠️ 속도 가변이 "판정 횟수" 단위 설계와 부딪힌다

주기가 30초로 고정이라는 전제 아래, 일부 산업이 **초 대신 판정 횟수**를 단위로 삼았다.

| 문서 | 설계 |
| --- | --- |
| [채굴](자원채취/채굴/README.md) | `DescendCycles`는 초가 아니라 **판정 횟수**로 둔다 (30초 고정이므로) |
| [벌목](자원채취/벌목/README.md) | `DepletionPerCut`은 **30초 판정 1회당** 감소량. 하루 2,880회가 곱해진다 |

캐릭터마다 속도가 다르면 **빠른 캐릭터가 갱도를 더 빨리 내려가고 숲을 더 빨리 고갈시킨다.**

- 의도라면 좋은 시너지다 — "좋은 캐릭터 = 깊이 파는 캐릭터"가 되어 배치에 의미가 생긴다.
- 아니라면 이 값들을 **초 단위로 되돌려야** 한다.

**결정 전까지 두 문서의 수치를 확정하지 않는다.** 또한 문서 곳곳의 "하루 2,880회"는
전부 **기준 속도(1.0배) 기준**이라는 단서가 붙는다.

## 6. 개발 시 지켜야 할 접점

기획을 코드로 옮길 때의 **고정 규칙**이다. 상세는 [`CLAUDE.md`](../../CLAUDE.md) 참조.

| 규칙 | 내용 |
| --- | --- |
| 데이터 원본 | 밸런스 수치·테이블은 코드 상수가 아니라 `GameDesign/Excel/*.xlsx`에 넣는다 |
| 식별자 | **DB에 저장되는 정수는 의미를 재할당하지 않는다.** enum은 뒤에만 추가, TID는 폐기해도 되쓰지 않는다 (4장) |
| DB 이름 | 소유를 이름에 드러낸다 — 유저 소유는 `t_user_*`, 캐릭터 소유는 `t_character` / `t_character_*` |
| 생성물 금지 | `Server/GameData`, `Server/Shared/Data`, `GameDesign/DataLog`, Unity 미러는 직접 수정 금지 |
| 갱신 절차 | 엑셀 수정 후 `GameDesign/generate-tables.ps1` 실행, 엑셀+생성물을 같은 커밋에 |
| 권위 | 자원·재화·거래는 **서버 권위**. 클라 계산 결과를 신뢰하지 않는다 (P4·거래 경쟁 때문) |
| 진행 조건 | **접속 중에만 진행한다.** 로그인 시 진행도를 0으로 리셋하고, 오프라인 구간은 정산하지 않는다 (P2) |
| 진행도 표현 | 시간이 아니라 **작업량**으로 누적한다. 속도가 바뀌어도 자투리를 재환산할 필요가 없다 |
| 속도 변경 | 캐릭터·버프로 속도를 바꾸기 **직전에 반드시 정산한다.** 안 그러면 이전 구간에 소급된다 |
| 문서 이름 | 새 기획 문서·폴더는 **항상 한글**로 만든다. `Excel`·`DataLog`는 코드가 경로를 참조하므로 예외 |

## 7. 문서 지도

모든 기획 문서는 `GameDesign/기획/` 아래에 있다.

```
GameDesign/
├─ 기획/
│  ├─ 게임기획코어.md         ← 이 문서 (최상위 · 단일 진입점)
│  ├─ 기획평가.md             ← 설계 평가·리스크
│  ├─ 작업슬롯/README.md      ← 배치 구조 (채취의 전제)
│  ├─ 자원채취/README.md      ← 시스템별 상세 기획안
│  │  ├─ 농사/README.md       ← 1차 산업 5종
│  │  ├─ 벌목/README.md
│  │  ├─ 낚시/README.md
│  │  ├─ 채굴/README.md
│  │  └─ 사냥/README.md
│  ├─ 퀘스트/README.md
│  ├─ 특성/README.md
│  ├─ 아이템/README.md
│  ├─ 거래/README.md
│  ├─ 진행 및 성장/README.md
│  └─ 게임UI/README.md
├─ Excel/                    ← 게임 데이터 원본 (.xlsx)
└─ DataLog/                  ← 생성된 .bytes의 JSON 덤프 (리뷰용)
```

> `Excel`·`DataLog`는 `Server/ExcelGenerator/Program.cs`가 경로를 직접 참조하므로
> **이름을 바꾸지 않는다.** 기획 문서 폴더만 한글을 쓴다.

| 문서 | 역할 |
| --- | --- |
| **게임기획코어.md** (이 문서) | 최상위 진입점 — 정체성·루프·시스템 지도·확정 현황 |
| [`기획평가.md`](기획평가.md) | 기획 전체에 대한 평가·리스크 정리 |
| `<시스템>/README.md` | 시스템별 상세 기획안 |
| `자원채취/<산업>/README.md` | 1차 산업 5종별 기본 기획안 |
| [`../DataLog/*.json`](../DataLog/) | 생성된 `.bytes`의 JSON 덤프 (데이터 diff 리뷰용) |
