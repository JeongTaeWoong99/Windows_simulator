# 경매 검색 비용 (T-155 · 이슈 #71)

## 목적 / 배경
- 검색 한 번이 판매 중 전부를 리스트로 만들어 정렬하고 `FindIndex`로 커서를 찾았다. 유저당 20건 상한이라 작다고 봤지만 전체는 `유저 수 × 20`이다.
- 규칙 → `Server/docs/경매장.md` 4.5 · 범위 → `tasks/T-155-경매검색확장.md` 후속 항목

## 주요 결정 / 근거
- **거절은 메인에서만 한다**(`AuctionSearchNoCondition` 1016). 종류도 TID도 없을 때다 — Category는 종류가 있어야 뜻이 있다. 토큰을 쓰기 전에 거절해 빈도 한도를 깎지 않는다.
  경매장(`ListingIndex`)은 조건 없는 검색도 그대로 받는다 — 경매장 테스트 다수가 빈 조건으로 돈다. 호출자는 메인뿐이다.
- 종류만 고른 검색("장비 전체")은 이슈 요청대로 허용한다 — 종류별 인덱스 `_byKind`를 새로 둬서 `_all`은 안 훑는다.
- **단가 낮은순만 진짜로 한 쪽만 읽는다.** 인덱스가 `(단가, ID)` 순이라 그대로다. TID 여럿은 PriorityQueue로 k-way 병합.
  높은순은 역순으로 읽으면 같은 단가에서 ID 순서가 뒤집혀(커서 전순서가 ID 오름차순) 따로 다루지 않았다 — 다른 정렬과 함께 "범위 한 번 훑기 + 크기 pageSize+1 힙"이다. 정렬·리스트 할당은 없앴다.
- **건수 상한 1,000**(`SearchQuery.TotalCountCap`). 캐시는 안 했다 — 무효화가 엮이고, 상한만으로 단가 낮은순의 셈이 끊긴다. 다른 정렬은 어차피 범위를 다 보니 세는 비용은 덤이다.
- TID 인덱스로 고르면 분류 필터가 빠지므로 `Matches`에 분류 검사를 더했다.

## 후속 작업 / 주의사항
- 클라: `AuctionSearchNoCondition` 문구 · `TotalCount == 1000`이면 "1,000건 이상" 표시.
- 단가 낮은순이 아닌 정렬은 여전히 범위 전체를 훑는다. 종류 하나에 매물이 수만 건이 되면 정렬 키별 인덱스를 본다.
