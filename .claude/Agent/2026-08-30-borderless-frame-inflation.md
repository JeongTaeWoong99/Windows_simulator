# 보더리스 창이 프레임 두께만큼 부풀어 두 증상을 만들던 문제

## 목적 / 배경

빌드 테스트에서 **증상 두 개**가 보고됐다.
① 시작할 때 창이 화면 밖으로 내려가 있다. ② 크기를 '작업표시줄 맞춤'으로 뒀는데 위젯 바가
작업표시줄보다 크다. → 관련 로그: [[2026-08-30-taskbar-fit-scale]] · [[2026-08-30-window-position-restore]]

**둘은 같은 뿌리였다.**

## 진단 경로 (이 방법을 기억할 것)

1. PlayerPrefs 를 레지스트리에서 읽어 **계산 입력값**을 확보 —
   `Window.WidgetSlotHeight = 87`, `Window.PosY = 695`, 유니티가 저장한 창 크기 `1342x792`.
   ⚠️ `WidgetSlotHeight` 는 REG_QWORD 로 들어오므로 `[BitConverter]::Int64BitsToDouble` 로 읽는다.
2. 작업표시줄 높이를 `SPI_GETWORKAREA` 와 `GetMonitorInfo` **양쪽**으로, **두 모니터 모두** 측정
   → 전부 60px 동일. **입력은 정상**임을 먼저 배제했다.
3. 손계산: `배율 = 2×60/87 = 1.379` → 창은 **745x1324(16:9)** 여야 하는데 실제는 **792x1342**.
   16:9 가 깨져 있다는 점이 결정적 단서였다 — 우리 코드는 16:9 만 만든다.
4. 차이 **47x18** 을 스타일별로 재현: `AdjustWindowRectExForDpi(1324x745, WS_OVERLAPPEDWINDOW, dpi=120)`
   → **정확히 1342x792**. 원인 확정.

## 주요 결정 / 근거

- **원인** — `ClientSizeToOuterSize` 가 `GetWindowLong` 으로 스타일을 묻는데, 스타일 교체 직후
  유니티 기본 `WS_OVERLAPPEDWINDOW` 가 돌아오는 순간이 있다. 창은 보더리스라 그 부풀린 외곽이
  **곧 클라이언트**가 되어 렌더 영역이 47px 커졌다.
  - 위젯 바도 비례해 커짐(60 → 63) = 증상 ②
  - 저장 좌표 695 + 커진 792 = 1487 > 1440 = 증상 ①
- **고친 방식 — 보더리스면 OS 에 묻지 않는다.** `_isTitleBar` 가 꺼져 있으면 입력을 그대로 반환한다.
  🔴 최적화로 오해해서 "일관성 있게 항상 OS에 묻자"로 되돌리지 말 것. 타이틀바 상태는 우리가
  정하는 값이라 OS 조회보다 신뢰할 수 있고, 이 단락이 사고 자체를 원천 차단한다.
- **실측 보정을 2회로.** 한 번만 돌던 것이 `GetClientRect` 의 반영 지연을 만나면 `dx=dy=0` 으로
  보여 **어긋난 크기를 그대로 통과**시켰다. 차이가 0이면 즉시 빠져나오므로 정상 경로의 비용은 같다.
- **보정 결과로 저장 좌표를 갱신한다.** 없으면 클램프된 좌표가 저장에 반영되지 않아 다음 실행에서
  같은 어긋남을 반복한다.

## 후속 작업 / 주의사항

- **저장값은 지울 필요 없다** — 크기가 745로 바로잡히면 `WidgetSlotHeight=87` → 위젯 60px(= 작업표시줄),
  `PosY=695` + 745 = 1440(= 모니터 바닥)으로 **저장값 그대로 정확히 맞는다.** 확인 완료.
- ⚠️ **남은 설계 취약점** — 저장하는 것이 절대 좌표라 "바닥에 붙임"이라는 의도를 담지 못한다.
  창 크기가 바뀌면 클램프로 밀릴 뿐 바닥 정렬이 유지되지 않는다. 모서리 기준 **오프셋**
  (앵커의 세로/가로 성분에 맞춰 `full.bottom - rect.bottom` 등)으로 저장하면 크기가 변해도
  의도가 보존된다. 이번엔 범위를 넓히지 않으려 하지 않았다.
- 에디터·빌드 두 경로 컴파일 오류 0. 동작 확인은 빌드 후 수동.
