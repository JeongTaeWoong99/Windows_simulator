# 경매장 서버 — 즉시구매 (T-094)

## 목적 / 배경
- 사용자가 준 범용 경매장 설계(별도 서버 · outbox · gRPC · 메모리 검색)를 우리 서버 구조에 맞춰 다시 짜고 끝까지 구현했다.
- 설계 근거·흐름·복구는 `Server/docs/경매장.md`, 플레이어 규칙은 `GameDesign/design/trade/README.md` 4장 — 여기는 결정·지뢰만.

## 주요 결정 / 근거
- **사용자 확인(2026-09-23):** 스택 매물은 통째로만 · 검색은 메인 중계(원안의 경매장 직통 REST+서명 토큰 대신) · 서버 간 전송은 설정으로 h2c/mTLS(기본 h2c) · 등록비 만료 환급/취소 미환급.
- **장비는 잠금 + 메모리에서 제거, 자원은 에스크로.** 메인은 메모리가 원천이라 잠긴 장비가 메모리에 남으면 판매자 쪽 저장이 팔린 행을 덮는다. 로그인 적재도 `auction_trade_id = 0`만 읽는다.
- **경매장에서 나오는 것은 전부 우편.** 골드 저장이 확정 잔액 덮어쓰기라, 구매자 트랜잭션이 판매자 골드를 올리면 판매자 메모리의 다음 저장이 덮는다. 반환도 우편이라 창고 가득 참을 흡수한다.
- **장비 우편은 개체(`equip_ids`)** — 기존 `equip_tids`는 받을 때 새로 만들어 인챈트가 사라진다. 받을 때 잠금을 풀고 창고 칸을 준다(`UnlockEquipAsync`, 이미 풀렸으면 false라 재수령해도 복제 없음).
- **골드 hold를 즉시구매부터 둔다** — Reserve 응답 대기 중 가챠로 같은 골드를 쓰는 것을 막는다. `CanAffordGold`/`TrySpendGold`가 hold를 뺀 값으로 본다. 입찰이 그대로 재사용한다.
- **거래 전이는 전부 `WHERE state = 1`** — 정산·반환·재전송이 겹쳐도 한 번만. 매물 ID = 메인 `trade_id`라 등록 멱등 키가 공짜로 생긴다.
- **Confirm(성공)은 경매장 종착 상태도 덮는다** — 메인이 이미 판 사실이다. 예약 타임아웃 뒤 늦게 와도 Sold.
- 수치는 전부 테스트값(`AuctionRules`). 우편 템플릿 TID 3~7은 `MailCatalog.LoadAll`이 없으면 기동을 멈춘다.

## 후속 작업 / 주의사항
- 클라 화면은 T-088. 입찰은 미착수(`Server/docs/경매장.md` 9장).
- `UserMailTest.접속_중인_유저에게_보내면_그_유저의_우편함으로_도착한다`는 **작업 전 커밋에서도 6번 중 3번 실패하는 기존 불안정 테스트**다(전역 `UserManager` 공유 — T-020). 경매 변경과 무관.
- 실측 때 `Server/Shared/game.sqlite3`에 테스트 계정을 넣었다가 백업으로 되돌렸다 — 커밋된 DB에는 DDL만 있다.
- 경매장 DB(`auction.sqlite3`)는 실행 폴더에 생긴다. 백업은 WAL 3파일을 함께(`-wal`·`-shm`) 다룬다.

## 업데이트 (2026-09-24) — 독립 리뷰 반영
- 리뷰 5건 전부 실재 확인 후 수정 → `Server/docs/경매장.md` 6장 "메인 쪽 함정" 표. 요지: 대사 커서 · 우편 도착 중복 무시 + 적재 병합 · DB 실패 세션은 종료 정산 저장 안 함(`User._dbFailed`, 경매 밖 기능에도 적용됨) · 예약 ID 충돌 거절 · 정산 실패 분기에서 잔액 복원.
- ⚠️ `OnMailsArrived`는 이제 새로 들어온 수를 돌려준다. 판매 중 건수 감소는 새 우편일 때만 한다.
