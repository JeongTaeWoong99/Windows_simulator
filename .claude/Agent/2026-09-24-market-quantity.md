# 거래소 — 자원 수량 구매 · 시세 (T-091)

## 목적 / 배경
- 사용자가 로스트아크 느낌을 원했다 — 자원은 거래소(원하는 수량을 최저가부터, 여러 판매자에 걸쳐), 장비는 경매장(즉시구매). **입찰은 두지 않는다.**
- 앞선 경매장 작업은 `2026-09-24-auction-server.md`. 규칙은 `GameDesign/design/trade/README.md` 4장, 서버 흐름은 `Server/docs/경매장.md` 4.4장.

## 주요 결정 / 근거
- **매물이 남은 수량을 들고, 예약은 별도 테이블(`t_reservation`)** — "구매 1건 → 매물 여러 개 × 수량". Reserved 상태를 저장하지 않고 진행 중 예약(구매 status 0) 합으로 판정한다. 경매장 즉시구매도 같은 예약 테이블을 쓴다(매물 전체 수량을 한 줄로).
- **전부 아니면 없음**(사용자 승인 기본값) — 부분 체결을 허용하면 hold·환불·우편이 전부 부분 처리로 번진다.
- 메인 정산은 거래마다 `count >= 수량` 조건부 차감이고, 한 줄이라도 어긋나면 **예외로 트랜잭션 전체 롤백** 후 별도 트랜잭션에서 잔액 복원 + Confirm(실패).
- 판매자 대금은 판매자별로 한 통(한 판매자의 여러 매물 합산). 판매 중 건수는 **다 팔린 매물만** 뺀다.
- 경매장 DB 스키마가 바뀌어 `PRAGMA user_version = 2`로 판을 박았다 — 옛 `auction.sqlite3`는 기동이 멈춘다(개발 DB는 지우면 된다).

## 후속 작업 / 주의사항
- ⚠️ SQLite `UPDATE ... SET a = x, b = CASE WHEN a - q ...`의 식은 **갱신 전 행 값**을 본다 — `Confirm`·`SettleMarketAsync`가 이것에 기댄다.
- 대사는 이제 전역 가드가 아니라 거래별로 거른다 — outbox `purchase_id` + 거래의 마지막 `purchase_id`. 확정이 순서대로 나간다는 전제다.
- 클라 화면은 T-088에 거래소 항목을 더했다. 묶음 단위(10개씩)는 두지 않았다.
