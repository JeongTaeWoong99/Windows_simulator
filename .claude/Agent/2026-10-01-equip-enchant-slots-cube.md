# 장비 인챈트 개편 (#46)

## 목적 / 배경
- 옛 인챈트(T-092)는 장비 등급과 무관하게 2~3줄이 붙어 "좋은 장비에 큐브를 돌린다"는 동기가 없었다(#46, 태웅 요청).
- 사용자(기획·서버) 결정: 장비 등급 = 칸 수(1·1·2·2·3·3), 인챈트 등급은 **장비 하나에 하나**(모든 칸 공유), 수치는 등급×종류 고정값, 큐브 2종(B = A × 1.25), 큐브 1회 = 상승 판정 + **칸 전부** 다시 뽑기, **착용 중 불가**.

## 변경 내용
- 엑셀 `EquipEnchant.xlsx` — `EnchantOptionTable` 42행(TID 1101~1607 = 1000 + 등급×100 + 종류) · `EnchantGradeTable`(`SlotCount` · `UpPermyriad`) · `EnchantItemTable`(`UpRatePermille`). `Item.xlsx` 원석·확장석 4종 삭제 · 상급 큐브 100018 추가 · `Gacha.xlsx` 상자 풀 갱신 · `Constants.xlsx` 줄 수 상수 2개 삭제 · `Enum.xlsx` `EnchantAction` 시트 삭제.
- 서버 — `EnchantCatalog`(칸 수·만분율 상승·풀 검증) · `User.Enchant.cs`(동작 분기 제거, 단일 경로) · `BuildEquip`이 칸 수를 넘는 칸을 버림 · `PacketEnum` 611~613 퇴역(614 `EnchantEquipped` 유지).
- 패킷 모양은 그대로다 — `C_EquipEnchantRequest { EquipId, ItemTid }`, 응답 `Success` = "한 단계 올랐는가".
- 문서 — 캐릭터 1.4 · 아이템 4.2 · 게임기획코어 · `Server/docs/데이터-카탈로그.md` 9장 등.

## 주요 결정 / 근거
- **한 번 칸마다 등급이 따로인 구조로 잘못 구현했다가 되돌렸다.** #46 원안(칸마다 등급·고른 칸 하나)과 사용자의 "수치 랭크는 다 같음"이 겹쳐 오독했다. 실제 의도는 메이플 잠재능력식(장비 등급 하나 · 전 칸 재추첨). 그래서 장비·우편·경매·저장 경로와 `EnchantGrade` 필드는 T-092 그대로다.
- 상승 확률을 **만분율**로 둔 이유: 전설→신화 0.04%를 정수로 담으려고. 큐브 차이는 배율 컬럼 하나(`UpRatePermille`)라 큐브가 늘어도 행만 더한다.
- 옵션 TID를 101~307에서 새 번호로 옮겼다 — 옛 번호는 "희귀~전설" 의미가 박혀 있어 재사용 금지 규칙에 걸린다. 옛 TID로 저장된 개체는 로드에서 칸이 버려진다(테스트 단계라 수용).
- 첫 부여는 상승 판정 없이 일반 — 일반 행의 `UpPermyriad`는 "일반→고급" 확률이다.

## 후속 작업 / 주의사항
- **DB 정리 미실행** — `game.sqlite3`에 옛 원석·확장석(100013·14·16·17) 보유 행이 남아 있을 수 있다. 자동 권한에 막혀 손대지 않았다. 스키마 변경은 필요 없다(`enchant_grade` 그대로 사용).
- 클라(T-095, 태웅): 칸 수 규칙을 `EnchantGradeTable.SlotCount`에서 읽고, 큐브 화면에 칸 선택이 필요 없다(요청은 장비·큐브만). `EquipLabel.GetStatSlotCount`(1~6)는 서버와 다르다.
- `UserMailTest.접속_중인_유저에게_보내면_그_유저의_우편함으로_도착한다`가 한 번 실패 후 재실행에서 통과 — 기존 불안정(T-089)으로 보인다.
