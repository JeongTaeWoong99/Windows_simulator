# 창 크기 어긋남 — 원인 오판을 접고 계측·감시로 전환

## 배경

[[2026-08-30-borderless-frame-inflation]] 에서 "`ClientSizeToOuterSize`가 프레임을 더한다"를 원인으로
잡고 고쳤는데, **재빌드해도 증상이 그대로였다** (창이 화면 밖 · 맞춤인데 위젯이 작업표시줄과 안 맞음).

## 왜 틀렸나 — 되새길 교훈

`1324x745` + `AdjustWindowRectEx(WS_OVERLAPPEDWINDOW, 125%)` = `1342x792` 가 저장된 해상도와
**정확히 일치**했다. 그 일치를 원인 확정으로 읽었다. 하지만 같은 숫자는 다른 경로로도 나온다 —
**유니티가 이전 실행에서 저장한 해상도**(`Screenmanager Resolution ...`)가 마침 그 값이었을 뿐이다.

🔴 **수치 일치는 가설을 지지할 뿐 확정하지 않는다.** 여러 경로가 같은 숫자를 만들 수 있으면,
   경로를 직접 관측해야 한다. 이번엔 그 단계를 건너뛰고 두 번을 낭비했다.

## 이번 실행에서 확인한 사실

빌드 시각(21:46) > 소스 수정(21:41) → **수정본이 확실히 들어간 빌드**였고, 그런데도
`Screenmanager Resolution = 1342x792`, `Window.PosX/PosY = 274,648`(648+792 = 1440 = 모니터 바닥).
위치 클램프는 동작했고 **크기만 계속 어긋난다.**

## 넣은 것

1. **계측** — `ClientLogger.Window`("창") 태그. 맞춤 계산 입력값 · 적용 요청값 · 실측 보정 회차 ·
   0.5초 간격 감시 상태 · 종료 직전 상태를 Player.log 에 남긴다.
2. **감시(`WatchWindowSize`)** — 부팅 후 8초 동안 실제 렌더 크기를 `_targetClient` 와 비교해
   어긋나면 되돌린다. 유니티가 저장 해상도를 늦게 되살려 우리 적용을 덮는 경우를 잡는다.
   ⚠️ 덮인 크기는 종료 시 다시 저장되어 **스스로 재생산**되므로, 한 번 어긋나면 재빌드로 안 풀린다.
   이 점이 "고쳤는데 그대로"를 설명할 수 있는 유일한 가설이다.

## 진단 도구 (다음에 그대로 쓸 것)

| 무엇 | 어디 |
|---|---|
| 런타임 로그 | `%USERPROFILE%\AppData\LocalLow\<회사>\<제품>\Player.log` (직전 실행 `Player-prev.log`) |
| 저장값 | `HKCU:\Software\<회사>\<제품>` — 유니티 `Screenmanager *` 와 우리 `Window.*` 가 한곳에 |
| QWORD 읽기 | `Window.WidgetSlotHeight` 는 `[BitConverter]::Int64BitsToDouble` |
| 빌드 최신 여부 | `<빌드>\<제품>_Data\Managed\Assembly-CSharp.dll` 의 수정 시각 vs 소스 시각 |

## 결과 — 가설 확정 (같은 날 재빌드·재실행)

계측 로그가 그대로 잡아냈다.

| 시점 | 렌더 크기 |
|---|---|
| 우리 적용 직후 | `1324x745` (요청대로, dx=dy=0) |
| **감시 +0.5s** | **`1342x792`** ← 유니티가 저장 해상도를 되살려 덮음 |
| 되돌린 뒤 +1.0s ~ +8.0s | `1324x745` 유지 |

`창 크기가 밖에서 바뀌었다 — 실제 1342x792 ≠ 요청 1324x745. 되돌린다` 경고가 정확히 한 번 찍혔다.
**보고된 두 증상(창이 화면 밖 · 위젯이 작업표시줄과 안 맞음)은 이 한 번의 덮어쓰기가 원인이었다** —
`1487 > 1440`이고 위젯은 `87×792/1080 = 63.8px`.

**재생산 고리도 끊겼다** — 종료 후 `Screenmanager Resolution`이 `1324x745`로, `Window.PosY=695`
(695+745 = 1440 = 모니터 바닥)로 저장됐다. 사용자 확인: 증상 해소.
