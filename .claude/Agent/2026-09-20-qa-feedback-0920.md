# 0920 QA 피드백 답변 문서화 · 일감 반영

## 목적 / 배경

QA·기획으로 합류한 한규빈님의 플레이 피드백 8건(`gyub/0920-정리.md`)에 사용자가 항목마다
채택/대체/미채택을 답했다. **피드백만 있고 답이 어디에도 없으면 "그건 왜 안 하기로 했나"가 다시 올라온다.**
답을 문서로 고정하고, 채택한 것을 일감으로 내렸다. **코드는 건드리지 않았다.**

## 변경 내용

- `gyub/0920-피드백 및 답변 정리(정태웅)/0920-피드백 및 답변 정리.md` (신규) — 항목별 **한 줄 답 → 이유 → 어디에 남겼나** 3단 구성 + 사진 4장.
- `tasks/T-069` · `T-070` · `T-071` · `T-072` (신규) · `tasks/T-058` 확장 · `tasks/README.md` INDEX.
- `Assets/Scripts_Client/UI/Storage/Storage 규칙.md` — "걸러 보이지 않는다" 아래 T-069 포인터 한 줄.

> 각 일감의 내용은 일감 파일이 갖는다. 여기 옮겨 적지 않는다.

## 주요 결정 / 근거

- **검색과 필터를 한 일감으로 묶었다(T-069).** 둘 다 "격자에 일부만 보이게 한다"는 같은 동작이고
  거르는 자리(`StorageSlotSource`)도 화면(도구 줄)도 같다. 따로 만들면 **"빈 칸을 어떻게 보일까"를
  두 번 판단**하게 된다.
- **정렬 기준 다각화는 클라·서버 둘로 갈랐다 (2026-09-20 사용자 지적으로 방향 수정).**
  처음엔 "클라에 먼저 넣으면 두 번 만든다"고 서버 T-058에만 넣었는데, **줄 세우는 것 자체는
  받아 둔 목록을 다시 정렬하는 것이라 서버가 필요 없다.** 서버가 필요한 것은 **"그 순서가 재접속해도
  남는가"** 하나다. 그래서 `T-073(클라 기준 추가 · 세션 한정) → T-058(칸 번호·정렬 요청) → T-044(연동)`
  세 층으로 적었다.
  ⚠️ **T-073만 끝난 상태에서 "재접속하면 순서가 풀리는 것"은 정상 동작이다** — 그 한계를 화면에서
  말할지도 T-073 할 일에 넣었다. 말하지 않으면 버그로 신고된다.
  ⚠️ **T-058과 T-073의 기준 목록은 같아야 한다** — 다르면 서버 정렬을 켜는 순간 순서가 바뀐다.
- **"트레이 상주"를 채택하지 않고 "창을 더 작게 + 투명도"로 대체했다(T-070, 사용자 결정).**
  트레이는 Win32를 새로 짜야 하는데, 설정에 선택지 둘을 더하면 같은 목적("비켜 두고 싶다")이 선다.
- **알림 세분화·도움말은 등록만 하고 우선순위 낮음(T-071·T-072).** 둘 다 **컨텐츠·UI가 굳어야**
  내용이 정해지는 것이라 지금 만들면 다시 만든다. 막힌 게 아니라 미룬 것이므로 ▶ 표에 낮음으로 뒀다.
- **자동 판매는 일감으로 만들지 않았다(미채택).** 창고가 안 차서 **무한 파밍**이 되고, 백그라운드
  판매 패킷이 늘고, 성장 인플레를 예측할 수 없다. 대체는 일괄 판매(T-056). 사유는 답변 문서에만 남겼고
  **기획 문서(게임기획코어 5장)에는 올리지 않았다** — "기록만"이 사용자 지시였고, 확정 결정으로
  올릴지는 별도 판단이다.

- **답변 문서의 독자는 QA + 기획이라, 항목마다 `🧪 QA가 알아 둘 것`을 붙였다.**
  "지금 그렇게 보이는 게 정상인가, 리포트할 버그인가"를 가르는 줄만 모은 절이다 —
  예: 정렬은 **재접속하면 풀리는 게 정상**(T-058 전), 창고는 **200칸 넘으면 뒤가 잘리는 게 알려진 상태**(T-063 전),
  캐릭터가 좋아도 **판정 1회당 분포는 같다**. 이걸 안 적으면 전부 버그 리포트로 돌아온다.

## 후속 작업 / 주의사항

- **창고 200칸은 여전히 클라 프레임 수일 뿐이다 (2026-09-20 코드 확인).** "서버가 한도·거절을 이미
  넣지 않았나"는 질문에 확인한 결과 — `EResultCode`에 창고 관련 코드가 없고 `GainItem`·`GrantGachaCharacters`
  어디에도 개수 검사가 없다. **T-063(서버 한도·뽑기 거절, 우선순위 높음)·T-064(클라 안내) 둘 다 대기**다.
  답변 문서와 T-069에 이 사실을 못 박아 뒀다 — 다음에 같은 질문이 또 나온다.

- ⚠️ **T-070에 지뢰 둘을 일감에 박아 뒀다** — `WindowScale`은 씬·`PlayerPrefs`에 int로 저장되므로
  값을 중간에 끼우면 안 되고(`Mathf.Clamp(…, (int)WindowScale.FitTaskbar)` 두 곳이 마지막 값을 가정),
  투명도를 `SetLayeredWindowAttributes`로 만들면 **DWM per-pixel 투명이 덮여 창이 검게 변한다**
  (`WindowManager.SetClickThrough` 주석).
- ⚠️ **T-069는 기존 결정을 뒤집는다** — `Storage 규칙.md`의 "산업별로 걸러 보이지 않는다".
  규칙 문서에는 포인터만 달았다. **결정이 서면 규칙 문서를 그때 고친다**(일감 항목에 있다).
- **INDEX에서 낡은 것 둘을 함께 고쳤다** — 보관된 T-035 행이 ▶ 표에 남아 있었고(상태: 완료),
  T-022의 「무엇을 기다리나」가 `tasks/T-002`(보관됨)를 가리키고 있었다.
  **T-002는 2026-09-17에 끝났으므로 T-022의 선행이 이미 풀렸을 수 있다** — 판단은 서버 담당 몫이라
  ⏸ 표에 남기고 [T-066](../../tasks/T-066-연계일감갱신스킬.md)을 가리켜 뒀다.
- **피드백 8번은 조사에서 그치지 않고 기획을 확정했다 (사용자 결정).**
  **캐릭터는 판정 1회의 양·질에 관여하지 않는다** — 수량 보너스(+N)도 상위 희귀도 확률 가중도 두지 않는다.
  근거는 **좋은 캐릭터가 이미 판정 횟수로 보상받는다**는 것(적성 1~9 = 실효 주기 → 파밍량 → 상위 등급 총량).
  보상 축을 둘로 늘리면 산업별 5개 분포 시트에 캐릭터 축이 곱해져 실측이 어려워진다.
  - 채취 README 5장의 **Open Question 5를 삭제**하고 "해소됨"으로 내렸다 — 6~11번 번호가 한 칸씩 당겨졌다.
    낚시 README가 참조하는 **"5장 결정 필요 4번"은 그대로**라 깨지지 않았다(확인함).
  - "상/중/하"는 **기획 문서에 기록된 적이 없다.** 개체 변량 금지가 이미 답이었고, 이번에 **왜 안 되는지를
    기획코어 4장에 명시**해 같은 제안이 다시 올라오지 않게 했다.
