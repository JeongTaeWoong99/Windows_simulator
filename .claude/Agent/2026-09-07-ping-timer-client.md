# 핑 송신을 백그라운드 타이머로 — 드래그 끊김의 클라 몫

> ✅ **빌드 실측 통과 (2026-09-07).** 창을 20초 이상 끌어도 클라 알림·서버 무응답 로그 둘 다 없다.

## 목적 / 배경

**창을 5초 이상 끌면 연결이 끊긴다**(빌드에서 확정 재현). 이슈 #19에서 원인 두 겹을
규명하고 **A-1**(서버 판정 15초) · **B-1**(소켓 루프를 스레드풀로)을 채택했고,
서버 몫은 `add9b9f`로 들어왔다. **남아 있던 클라 몫**이 이 작업이다.

`45b55c6`(되돌려진 커밋)에 완성된 형태가 있어 **그중 셋만** 되살렸다.

### B-1만으로는 낫지 않는 이유 — 넣는 쪽과 비우는 쪽

| | 무엇을 푸는가 | 상태 |
|---|---|---|
| B-1 (서버 몫) | **큐를 비우는 쪽** — `SendLoop`이 메인 스레드에 안 묶인다 | ✅ `add9b9f` |
| 이 작업 (클라 몫) | **큐에 넣는 쪽** — `PingManager`가 `Update()`에서 핑을 만든다 | ✅ 이번 |

드래그로 `Update`가 멈추면 **큐에 들어갈 핑 자체가 없다.** 서버 담당도 이슈 #19에서
"5초에서 끊기는거 15초 드래그 시 끊기는 걸로 변경되었습니다"라고 확인해 줬다 —
증상이 사라진 게 아니라 판정 시간만큼 미뤄졌을 뿐이었다.

## 주요 결정 / 근거

### 🔑 오탐 가드는 곁다리가 아니라 타이머와 동급이다

**끊는 주체가 서버만이 아니었다.** 드래그 20초 시나리오:

1. 타이머가 핑을 보냄 → 서버가 Pong → 수신 루프(스레드풀)가 `NetworkMessageQueue`에 **쌓음**
2. 메인 스레드가 멈춰 `NetworkManager.Update`의 `Flush()`가 안 돎 → `PongReceived` 미발행
   → `_lastPongTime`이 드래그 시작 시각에 고정
3. 드래그 종료. 첫 프레임에서 `silentSeconds = 20 > 15` → `RaiseFatal` → **클라가 스스로 앱을 내린다**

게다가 `NetworkManager.Update`(Flush)와 `PingManager.Update`(판정)의 **스크립트 실행 순서가
지정돼 있지 않아** 어느 쪽이 먼저 도느냐로 갈린다 — 빌드마다 다르게 나올 수 있는 종류다.
**가드가 없으면 서버 쪽 끊김만 사라지고 화면 증상은 그대로 남는다.**

> `Script Execution Order`로 순서를 고정하는 길은 택하지 않았다 — 절전·긴 GC에는 듣지 않고,
> ProjectSettings 전역 설정이 이 파일 하나의 사정을 떠안게 된다.

### ⛔ `45b55c6`에서 일부러 가져오지 않은 것

- **핑 주기 `5f` → `2f`.** 그건 **A-2**다. A는 **A-1**(판정 15초)로 결정돼 적용됐고,
  그러면 **5초가 규칙에 맞는 값**이다(15 ÷ 3 = 5). 트래픽을 2.5배로 늘릴 이유가 없다.
- 문서의 **`T-037` 참조.** 그 일감은 존재하지 않는다 — A-1로 흡수돼 해결됐다. 죽은 링크가 된다.

### 주석에 "이미 스레드풀에서 돈다"고 쓰지 않았다

`45b55c6`은 "송신 루프는 이미 스레드풀에서 돈다"고 적었는데 **그 시점엔 틀린 말이었고,
그래서 1차 수정이 무효였다**([경위](2026-08-28-ping-disconnect-cause.md)).
지금 사실이 된 것은 B-1 덕분이므로, 주석에는 **"B-1이 되돌아가면 이 타이머도 함께 무력해진다"**
— 둘이 한 쌍이라는 것을 적었다.
