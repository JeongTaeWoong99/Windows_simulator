# 게임 시계 · 시간 조작 치트 (T-128 · 이슈 #48)

## 목적 / 배경
- 경매 만료·전일 평균·우편 7일 삭제를 기다리지 않고 시험하려는 클라 요청(#48 · T-106). 할 일·완료 조건 → `tasks/T-128-게임시계시간치트.md`
- 사용자 결정: 채취는 안 쌓이게 · 오프셋은 재시작 후 유지 안 함

## 주요 결정 / 근거
- **`GameClock`은 User가 읽지 않는다** — 시각을 인자로 받는 저장소 관례를 지킨다. User가 `_clock`을 쥐는 건 치트로 움직이기 위해서고, 읽는 곳은 인자를 뚫을 수 없는 경계(OnDestroy·정산 실패 콜백)뿐이다. 테스트는 `TestUserBuilder.Clock`으로 자기 시계를 갖는다(전역 오프셋을 병렬 테스트끼리 공유하지 않게)
- **채취 안 쌓임 = 슬롯 `LastTickAt`을 같은 delta만큼 민다.** 슬롯만 실제 시계로 돌리는 안은 기각 — 장착·특성·해금 핸들러가 같은 `now`를 슬롯 정산에도 쓰고, 클라 진행도도 서버 시각 기준이라 시계가 둘이면 어긋난다. 오프라인 누적은 지금 없어서(로그인 때 "지금부터") DB 쪽은 손댈 게 없었다
- **경매장 오프셋은 릴레이가 매 바퀴(1초) `SetClockOffset`으로 보낸다** — 바뀔 때만 보내면 경매장 재시작(오프셋 0)을 메인이 모른다. 실패하면 RpcException 경로라 그 바퀴의 outbox·이벤트도 건너뛴다(어긋난 시계로 등록하지 않게)
- 경매장 `GameTimeProvider`는 `GetUtcNow`만 오프셋, 타이머는 안쪽 그대로 — `SweepService`는 원래 `TimeProvider`(실제)를 받는다
- 치트 번호 12·13 — 이슈가 적은 11은 `SetTraitLevel`(T-115)이 먼저 썼다

## 후속 작업 / 주의사항
- **`TokenBucket`이 시계 역행에 막히던 지뢰** — `now <= _lastRefill`이면 회복 안 함이라 `ResetTime` 뒤 넘겼던 만큼 검색이 막혔다. 기준을 당기도록 고쳤다. 게임 시각을 받아 "마지막 시각"을 들고 있는 다른 곳을 만들면 같은 역행을 본다
- 받은 우편 7일 삭제는 로그인 때만 판정 → 넘긴 뒤 재접속해야 보인다
- 일감 번호: 처음 T-126으로 만들었다가 창고 클라 일감과 충돌해 T-128로 옮겼다 — 워크트리·브랜치 이름과 첫 커밋 메시지(`487f50d`)의 T-126은 이 일감이다
- 클라 몫(ServerClock · 치트 창 버튼) → T-106 · 실측 남음
