# 게임 기획 참조

> 최종 업데이트: 2026-09-14 (해금 문서 추가 · 하이브리드 분할 — 전파 알고리즘·사고 사례·검사 옵션·새 시스템 절차를 `전파 상세.md`로)
>
> 게임 시스템·콘텐츠를 만지기 전에 **[`GameDesign/design/게임기획코어.md`](../../../../GameDesign/design/게임기획코어.md)** 를
> 먼저 읽고, 그 다음 해당 영역의 **상세 기획안**을 읽는다.
> 게임기획코어는 "무엇을 왜 만드는가", 상세 기획안은 "어떻게 만드는가"를 담는다.
>
> **기획 문서를 고쳤으면 헤더의 `바뀌면 갱신` 블록을 따라 재귀적으로 전파한다** (아래 "재귀 전파").

---

## 트리거 — 언제 읽는가

**게임의 규칙·수치가 바뀌는 작업.** 예:

- 채취/퀘스트/특성/아이템/거래/성장 관련 로직 구현·수정
- `GameDesign/Excel/*.xlsx` 데이터 추가·변경
- 게임 데이터 테이블(`GameData`) 스키마 변경
- 게임 관련 패킷·DB 테이블 설계
- 기획 문서 자체의 수정·추가

## 읽지 않아도 되는 경우

- **게임 규칙이 바뀌지 않는 UI 작업** — 화면 배치, 컴포넌트 배선, 레이아웃, 이름 정리.
  화면이 게임 값을 *보여주기만* 한다면 기획은 그대로다
- 게임 규칙과 무관한 순수 인프라 작업 (빌드 스크립트, 로깅, 네트워크 계층 자체 등)
- 파일을 바꾸지 않는 단순 질의응답

> 가르는 기준은 **"이 작업으로 기획 문서의 어떤 문장이 틀리게 되는가"** 다.
> 틀려지는 문장이 없으면 읽지 않는다.

---

## 절차

1. **[`GameDesign/design/게임기획코어.md`](../../../../GameDesign/design/게임기획코어.md) 를 읽는다.** (항상, 예외 없이)
   - 특히 **5장 "확정 / 미확정 현황"** 을 확인한다.
   - **6장 "개발 시 지켜야 할 접점"** 의 고정 규칙을 지킨다.
2. 게임기획코어의 **3장 시스템 지도**에서 이번 작업에 해당하는 시스템을 찾아,
   그 **상세 기획안**(`GameDesign/design/<시스템>/README.md`)을 읽는다.
   - 여러 시스템에 걸치면 관련된 것을 전부 읽는다.
   - 각 문서 말미의 **"결정 필요 (Open Questions)"** 를 반드시 확인한다.
3. **[`문서관계도.md`](../../../../GameDesign/design/문서관계도.md) 2.2에서 그 문서의 정참조를 본다.**
   함께 읽어야 할 문서가 거기 있다. 각 문서 헤더의 `상위`/`전제` 줄도 같은 정보를 준다.
4. 설계 판단이 갈리면 게임기획코어 1장의 **설계 원칙(P1~P4)** 을 기준으로 결정한다.
5. 리스크가 걸리는 작업이면 [`GameDesign/design/기획평가.md`](../../../../GameDesign/design/기획평가.md)
   의 리스크 등급표를 함께 본다.

## 지켜야 할 것

| 규칙 | 내용 |
| --- | --- |
| **미확정 항목을 임의로 정하지 않는다** | 게임기획코어 5장·각 문서의 "결정 필요" 항목은 **아직 기획이 없는 것**이다. 구현에 그 값이 필요하면 **사용자에게 먼저 확인**한다. 부득이하면 가정을 명시하고 임시값임을 코드·문서에 남긴다 |
| **기획과 다른 구현을 발견하면 알린다** | 조용히 한쪽에 맞추지 말고 **차이를 보고**한다. 문서가 낡은 것인지 구현이 틀린 것인지는 사용자가 판단한다 |
| **밸런스 수치는 코드에 넣지 않는다** | 원본은 `GameDesign/Excel/*.xlsx`. 수정 후 `GameDesign/generate-tables.ps1`을 돌려 생성물까지 같은 커밋에 담는다. 생성물(`Server/GameData`·`Server/Shared/Data`·`GameDesign/DataLog`·Unity 미러)은 직접 수정하지 않는다 |
| **바뀐 내용만 적는다 — 이력을 남기지 않는다** | 기획이 달라지면 이전 서술을 **지우고** 대체한다. 취소선·"폐지"·"재정의됨"·"해소"를 남기지 않는다 — 변경 이력은 git이 갖는다. 폐지된 시스템은 항목째 삭제하고, 그 결과 유효한 규칙이 있으면 **긍정문 한 줄**로 남긴다. 게임기획코어 5장 표도 `❌ 폐지` 행을 쌓지 않는다 |

### 재귀 전파 — 기획을 바꿨으면 어디까지 바꾸는가

**한 문서만 고치고 끝내지 않는다.** 이 저장소에서 실제로 반복된 사고는
"하위 문서만 고치고 상위·형제를 안 고친 것"이다.

1. 고친 문서 헤더의 **`바뀌면 갱신` 블록**(= [`문서관계도.md`](../../../../GameDesign/design/문서관계도.md) 2.1)에
   적힌 문서를 **전부 열어 본다.** 깊이 제한은 없다 — 보통 2단계에서 자연히 멎는다.
2. 이번 변경으로 서술이 낡은 문서만 고치고 **그 문서에서 또 퍼진다.** 열어 보고 안 고치는 것이 정상이며,
   그대로인 문서에서는 가지가 끝난다.
3. `최종 업데이트`는 **고친 문서만** 올린다. 안 고친 문서의 날짜를 올리면 역전 검사가 무력해진다.
4. 이미 본 문서는 다시 가지 않는다 (캐릭터 ↔ 작업슬롯 같은 순환은 여기서 멈춘다).
5. **`게임기획코어` 5장은 항상 본다** — 확정/미확정이 바뀌었으면 반드시 반영하고, 확정된 항목의 `⚠️`(제안) 표기는 지운다.

- **전파 대상이 되는 변경**은 이름 · 수치/개수 · 확정 상태 · 폐지 · 구조가 바뀐 것뿐이다. 표현만 다듬은 것은 전파하지 않는다.
- **전파는 문서에서 끝나지 않는다.** 확정된 기획은 엑셀 → 생성물 → 서버 코드로 흐른다(대응표는 문서관계도 4장).
  엑셀 구조를 바꿀 때는 **그 시트를 읽는 서버 코드를 같은 작업 단위로** 본다 — 엑셀만 앞서면 "미구현"이 아니라 "오동작"이 된다.
  코드가 못 따라가면 [`tasks/`](../../../../tasks/README.md)에 등록하고 문서에 `❌ 미구현 (일감 T-0XX)`를 **반드시** 적는다.
- **고쳤으면 검사한다** — `powershell -File GameDesign/check-doc-graph.ps1 -Changed`.
  오류(깨진 링크·블록 불일치)는 반드시 고치고, 경고(갱신일 역전)는 전파를 빠뜨린 게 아닌지 확인한다.

> 📖 전파 알고리즘 · 실제 사고 사례 · 검사 옵션(`-Fix`·`-Graph`) · **새 시스템/산업 문서를 추가하는 절차**는
> **[`전파 상세.md`](<전파 상세.md>)** 에 있다 — 위 규칙으로 판단이 서면 열지 않아도 된다.
> **새 시스템·산업 문서를 만들 때는 연다.**
