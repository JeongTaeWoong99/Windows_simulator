# GitHub 이슈 작성

> 이슈는 **사람 사이의 창구**다. 저장소 안의 할 일 목록은 [`tasks/`](../task-writer/SKILL.md)가 갖고,
> 이슈는 **"당신이 먼저 해 줘야 내가 움직인다"** 를 상대에게 전하는 자리다.

---

## 트리거 — 언제 여는가

| 상황 | 이슈 |
| --- | --- |
| 상대 직군이 먼저 해 줘야 내 작업이 열린다 | **요청** |
| 내가 한 결정·변경을 상대가 알아야 한다 (반대는 안 해도 됨) | **공유** |
| 상대 영역의 판단을 받아야 내가 진행한다 | **확인** |
| 상대 영역에서 난 버그를 넘긴다 | **버그** |
| 내 몫이 끝나 상대가 이어받을 수 있다 | **완료** |

### 이슈로 만들지 않는 것

- **내가 내 영역에서 처리하는 일** — 그건 `tasks/`의 일감이다. 이슈는 상대가 볼 때만 쓴다.
- 일감 하나를 이슈로 **복사**하는 것. 이슈에는 **상대가 할 몫만** 적고 일감을 링크한다.
- 한 대화 안에서 물어보고 끝날 질문.

---

## 1. 제목 — 누구에게 · 무슨 일인지가 먼저 보여야 한다

```
[<대상 직군> <종류>] <한 줄 요약> (T-0XX)
```

**앞의 대괄호가 꼬리표다.** 목록에서 제목이 길게 늘어서도 `[서버 요청]`·`[클라 버그]`가
왼쪽 끝에 모여 있어 무엇이 내 것인지 한눈에 걸러진다.

| 자리 | 값 |
| --- | --- |
| **대상 직군** | `서버` · `클라` · `기획` — **요청을 받는 쪽**이다 (내 직군이 아니다). **둘이면 가운뎃점으로 한 칸에 묶는다** — `기획·서버` · `기획·클라` |
| **종류** | `요청` · `공유` · `확인` · `버그` · `완료`. **하나만 쓴다** — 직군이 둘이어도 종류는 대표값 하나다 |
| **한 줄 요약** | 무슨 작업인지. 시스템 이름 + 동사. **대괄호 밖은 `—`로 다시 끊지 않는다** |
| `(T-0XX)` | 관련 일감이 있으면 끝에. 여러 개면 `·`로 잇는다. 없으면 생략 |

```
[서버 요청] 장비 뽑기 — 가챠 풀에 장비 축 (T-067)
[서버 확인] 가챠 1번 풀을 서버에 남겨도 되는지 (T-031)
[클라 완료] 창고 칸 위치 저장 · 서버 패킷 반영 필요 (T-058)
[기획 공유] 자원 뽑기 폐지 — 코어 루프에서 sink가 아니다
[기획·서버 확인] 캐릭터 레벨 효과 간소화 — 적성 포인트를 자동 가산으로 (T-003)
[긴급][기획·서버 요청] 공용 값의 소유권 정리 — 이중 상수 · 한도 검사 누락 (T-085)
[긴급][서버 버그] 창 드래그 중 연결이 끊긴다 — 하트비트가 메인 스레드에 묶여 있다
```

- **한 일을 두 직군이 나눠 받으면 `기획·서버`처럼 묶고, 종류는 하나로 적는다.**
  예전에는 `[서버 요청 · 기획 확인]`처럼 직군마다 종류를 따로 달았는데, 칸이 길어져
  **목록에서 왼쪽 끝의 꼬리표가 밀려났다** (2026-09-24에 #33·#34·#35를 이 형식으로 맞췄다).
  종류가 정말 둘로 갈린다면 **이슈 두 개로 나누는 쪽**을 먼저 본다.
- **긴급이면 `[긴급]`을 맨 앞에 하나 더 붙인다.** 상대 작업을 멈춰서라도 먼저 봐야 할 때만이고,
  평소엔 붙이지 않는다 — 전부 긴급이면 아무것도 긴급하지 않다.
- 요약 안에서 부연이 필요하면 그때 `—`를 쓴다. 꼬리표와 요약 사이에는 쓰지 않는다.
- **꼬리표는 「지금 공을 쥔 쪽」을 가리킨다.** 처리한 뒤 되돌려 확인을 요청하면
  `[서버 확인 → 클라 확인]`처럼 칸이 늘어난다 (3장).

> ⚠️ **대상 직군을 내 직군으로 쓰지 않는다.** `[클라 …]`는 서버·기획이 클라에게 보낼 때의 꼬리표다.
> 내가 클라이고 서버에 요청한다면 **`[서버 요청]`** 이다.

> **닫힌 이슈의 제목은 고치지 않는다** — 알림만 다시 가고 링크된 문서의 인용과 어긋난다.
> **열려 있는 이슈는 사용자가 지시할 때 한 번에 형식을 맞춘다**(2026-09-20에 #27·#29·#30을 그렇게 정리했다).
> 스스로 판단해 남의 이슈 제목을 바꾸지 않는다.

## 2. ASSIGNEES · LABELS — 둘 다 필수다

**하나라도 비면 올리지 않는다.** 알림이 가지 않아 이슈가 잊힌다.

### ASSIGNEES = 요청 대상 (처리할 사람)

| 직군 | GitHub | |
| --- | --- | --- |
| 클라 | `JeongTaeWoong99` | 정태웅 |
| 서버 | `wlsdn2749` | 진우 |
| 기획 · QA | `Gyubin-Han` | 규빈 |

- 대상이 둘이면 둘 다 넣는다. **제목의 대상 직군과 반드시 일치**한다 — `[기획·서버 …]`면 `Gyubin-Han`·`wlsdn2749` 둘 다다.
- **기획 판단이 섞여 있으면 규빈을 빠뜨리지 않는다.** 서버·클라만 걸린 일로 보여도 엑셀 데이터·수치·규칙이 바뀌면 기획 몫이다.
- 내가 이어서 할 일이 남아 있어도 assignee는 **상대**다 — 내 몫은 `tasks/`가 추적한다.
- **공이 넘어가면 assignee도 함께 바꾼다** — 제목만 바꾸고 두면 목록에서 누구 차례인지 어긋난다 (3장).

### LABELS = 종류에 맞춰

| 종류 | 라벨 |
| --- | --- |
| 요청 · 완료 (새 기능·확장) | `enhancement` |
| 확인 (판단·정보를 받아야 함) | `question` |
| 버그 | `bug` |
| 문서·작업 환경 | `documentation` |

- 라벨은 저장소에 **이미 있는 것만** 쓴다 (`gh label list`로 확인). 새로 만들지 않는다.

## 3. 공이 넘어갈 때 — 제목과 assignee를 함께 바꾼다

요청을 받은 쪽이 처리한 뒤 **그대로 닫지 않고 되돌려 확인을 요청하는 흐름**이 자주 생긴다.
이때 제목과 assignee를 그대로 두면 목록에서 **아직 상대가 안 한 것처럼 보인다** —
"왜 아직 안 닫혔지?" 하고 열어 보고서야 **나한테 넘어와 있었다**는 걸 알게 되고, 그만큼 묵는다.

**꼬리표의 마지막 칸이 지금 공을 쥔 쪽이다. assignee와 항상 일치한다.**

```
[서버 확인] 가챠 1번 풀을 서버에 남겨도 되는지 (T-031)        · assignee 서버
      ↓ 서버가 처리하고 되돌린다
[서버 확인 → 클라 확인] 가챠 1번 풀을 … (T-031)              · assignee 클라
```

- **앞 칸을 지우지 않고 `→`로 덧붙인다.** 제목만 보고 어디서 시작해 어디까지 왔는지 읽힌다.
- **칸은 둘까지만 보인다.** 세 번째로 넘어가면 가장 왼쪽 칸을 떨어뜨리고 최근 둘만 남긴다.
  왕복이 세 번을 넘으면 **한 이슈에 두 가지 일이 들어 있다는 신호**다 — 쪼개는 쪽을 먼저 본다.
- **라벨은 그대로 둔다.** 종류가 실제로 바뀌었을 때(`확인`에서 `버그`로)만 바꾼다.
- 일감 쪽 상태도 함께 본다 — 공이 나에게 왔으면 그 일감은 **⏸(남을 기다림)이 아니다.**

### 넘기는 절차

```bash
gh issue edit <번호> \
  --title "[서버 확인 → 클라 확인] …" \
  --add-assignee <받을 사람> \
  --remove-assignee <넘기는 사람>

gh issue comment <번호> --body-file "<스크래치패드>/handoff.md"
```

- ⚠️ **`--remove-assignee`를 빠뜨리지 않는다.** 둘 다 붙어 있으면 누구 차례인지 다시 모호해진다.
- **코멘트를 반드시 함께 남긴다.** 제목 변경만으로는 알림이 약하다.
  내용은 **무엇을 했나 / 무엇을 확인해 주시면 닫아도 되나** 두 가지면 충분하고,
  마무리 문장은 본문과 같다: `확인 후, 처리 코멘트 등록 부탁드립니다.`
- **공을 넘겨받아 본문을 갱신할 때는 마무리 문장을 바꾼다.** 이제 닫는 쪽이 나이므로
  "확인 후, 처리 코멘트 등록 부탁드립니다"가 아니라 **"확인되면 닫겠습니다"** 로 적는다.

## 4. 본문 — 요약이 맨 앞, 앞뒤로 「한 것 → 해 주실 것」

````markdown
<요약 2~3줄 — 제목만 보고 들어온 사람이 이 문단만 읽고 무슨 일인지 알 수 있어야 한다.
 무엇을 왜 하는지, 상대에게 필요한 게 무엇인지를 여기서 끝낸다. 헤딩을 붙이지 않는다.>

## 무엇을 했나

<내 쪽에서 끝난 것 · 지금 상태. 표·코드 블록으로 사실만.
 커밋 해시가 있으면 적는다. 확인한 방법(더미 클라·실서버 등)도.>

## 무엇을 해주셔야 하나

<상대가 할 일. 체크리스트나 번호 목록으로 — 세어질 수 있게 쓴다.>

- [ ] …
- [ ] …

## 알아두실 점

<주의·부작용·영향 없는 범위. "이건 안 건드려도 됩니다"도 여기에 적는다.
 없으면 이 절을 통째로 뺀다 — 빈 절을 남기지 않는다.>

확인 후, 처리 코멘트 등록 부탁드립니다.
````

- **말투는 존댓말**이다. 저장소 문서(반말)와 다르다 — 사람에게 보내는 글이다.
- 코드·패킷 이야기는 **지금 모양 → 요청 모양**을 코드 블록 둘로 나란히 보인다. 말로 풀지 않는다.
- 문서·일감 링크는 **저장소 상대 경로**로 건다 (`tasks/T-031-클라가챠화면.md`).
- 마무리 문장은 **한 줄 그대로** 쓴다: `확인 후, 처리 코멘트 등록 부탁드립니다.`

## 5. 올리는 절차

1. **본문을 파일로 쓴다** — 스크래치패드에 `.md`로. 한글·백틱이 많아 인자로 넘기면 깨진다.
2. `gh label list`로 라벨 이름을 확인한다.
3. 이슈를 만든다.

   ```bash
   gh issue create \
     --title "[서버 확인] …" \
     --body-file "<스크래치패드>/issue.md" \
     --assignee wlsdn2749 \
     --label question
   ```

4. **올린 뒤 번호를 일감에 적는다** — `tasks/T-0XX-*.md`의 관련 링크 줄에
   `[이슈 #NN](https://github.com/JeongTaeWoong99/Windows_simulator/issues/NN)`.
   INDEX 표에도 이미 이슈 링크를 다는 칸이 있다.
5. **사용자에게 초안을 보이고 확인을 받은 뒤 올린다.** 이슈는 남에게 알림이 가는 글이다 —
   확인 없이 `gh issue create`를 실행하지 않는다.

---

## 6. 이슈를 닫을 때

- **마지막으로 공을 쥔 쪽이 닫는다.** 상대가 처리 코멘트를 남기고 **내 쪽 확인까지 끝났을 때**다.
- 요청이 무산됐거나 다른 방법으로 풀렸으면 **왜 안 하기로 했는지 코멘트를 남기고** 닫는다 —
  `wontfix` 라벨. 조용히 닫지 않는다.
