# GitHub 이슈 작성

> 이슈는 **사람 사이의 창구**다. 저장소 안의 할 일 목록은 [`tasks/`](../task-writer/SKILL.md)가 갖고,
> 이슈는 **"당신이 먼저 해 줘야 내가 움직인다"** 를 상대에게 전하는 자리다.

---

## 트리거 — 언제 여는가

| 상황 | 이슈 |
| --- | --- |
| 상대 직군이 먼저 해 줘야 내 작업이 열린다 | **요청** |
| 내가 한 결정·변경을 상대가 알아야 한다 (반대는 안 해도 됨) | **공유** |
| 상대 영역의 판단을 받아야 내가 진행한다 | **확인** |
| 상대 영역에서 난 버그를 넘긴다 | **버그** |
| 내 몫이 끝나 상대가 이어받을 수 있다 | **완료** |

### 이슈로 만들지 않는 것

- **내가 내 영역에서 처리하는 일** — 그건 `tasks/`의 일감이다. 이슈는 상대가 볼 때만 쓴다.
- 일감 하나를 이슈로 **복사**하는 것. 이슈에는 **상대가 할 몫만** 적고 일감을 링크한다.
- 한 대화 안에서 물어보고 끝날 질문.

---

## 1. 제목 — 누구에게 · 무슨 일인지가 먼저 보여야 한다

```
[<대상 직군> <종류>] <한 줄 요약> (T-0XX)
```

**앞의 대괄호가 꼬리표다.** 목록에서 제목이 길게 늘어서도 `[서버 요청]`·`[클라 버그]`가
왼쪽 끝에 모여 있어 무엇이 내 것인지 한눈에 걸러진다.

| 자리 | 값 |
| --- | --- |
| **대상 직군** | `서버` · `클라` · `기획` — **요청을 받는 쪽**이다 (내 직군이 아니다) |
| **종류** | `요청` · `공유` · `확인` · `버그` · `완료` |
| **한 줄 요약** | 무슨 작업인지. 시스템 이름 + 동사. **대괄호 밖은 `—`로 다시 끊지 않는다** |
| `(T-0XX)` | 관련 일감이 있으면 끝에. 여러 개면 `·`로 잇는다. 없으면 생략 |

```
[서버 요청] 장비 뽑기 — 가챠 풀에 장비 축 (T-067)
[서버 확인] 가챠 1번 풀을 서버에 남겨도 되는지 (T-031)
[클라 완료] 창고 칸 위치 저장 · 서버 패킷 반영 필요 (T-058)
[기획 공유] 자원 뽑기 폐지 — 코어 루프에서 sink가 아니다
[긴급][서버 버그] 창 드래그 중 연결이 끊긴다 — 하트비트가 메인 스레드에 묶여 있다
```

- **긴급이면 `[긴급]`을 맨 앞에 하나 더 붙인다.** 상대 작업을 멈춰서라도 먼저 봐야 할 때만이고,
  평소엔 붙이지 않는다 — 전부 긴급이면 아무것도 긴급하지 않다.
- 요약 안에서 부연이 필요하면 그때 `—`를 쓴다. 꼬리표와 요약 사이에는 쓰지 않는다.

> ⚠️ **대상 직군을 내 직군으로 쓰지 않는다.** `[클라 …]`는 서버·기획이 클라에게 보낼 때의 꼬리표다.
> 내가 클라이고 서버에 요청한다면 **`[서버 요청]`** 이다.

> 2026-09-20 이전 이슈는 꼬리표 없이 `서버 요청 — …` 형태다. **옛 이슈 제목을 고치지 않는다** —
> 알림만 다시 가고 링크된 문서의 인용과 어긋난다. 새로 만드는 것부터 이 형식으로 쓴다.

## 2. ASSIGNEES · LABELS — 둘 다 필수다

**하나라도 비면 올리지 않는다.** 알림이 가지 않아 이슈가 잊힌다.

### ASSIGNEES = 요청 대상 (처리할 사람)

| 직군 | GitHub | |
| --- | --- | --- |
| 클라 | `JeongTaeWoong99` | 정태웅 |
| 서버 | `wlsdn2749` | 진우 |
| 기획 · QA | `Gyubin-Han` | 규빈 |

- 대상이 둘이면 둘 다 넣는다. **제목의 대상 직군과 반드시 일치**한다.
- 내가 이어서 할 일이 남아 있어도 assignee는 **상대**다 — 내 몫은 `tasks/`가 추적한다.

### LABELS = 종류에 맞춰

| 종류 | 라벨 |
| --- | --- |
| 요청 · 완료 (새 기능·확장) | `enhancement` |
| 확인 (판단·정보를 받아야 함) | `question` |
| 버그 | `bug` |
| 문서·작업 환경 | `documentation` |

- 라벨은 저장소에 **이미 있는 것만** 쓴다 (`gh label list`로 확인). 새로 만들지 않는다.

## 3. 본문 — 요약이 맨 앞, 앞뒤로 「한 것 → 해 주실 것」

````markdown
<요약 2~3줄 — 제목만 보고 들어온 사람이 이 문단만 읽고 무슨 일인지 알 수 있어야 한다.
 무엇을 왜 하는지, 상대에게 필요한 게 무엇인지를 여기서 끝낸다. 헤딩을 붙이지 않는다.>

## 무엇을 했나

<내 쪽에서 끝난 것 · 지금 상태. 표·코드 블록으로 사실만.
 커밋 해시가 있으면 적는다. 확인한 방법(더미 클라·실서버 등)도.>

## 무엇을 해주셔야 하나

<상대가 할 일. 체크리스트나 번호 목록으로 — 세어질 수 있게 쓴다.>

- [ ] …
- [ ] …

## 알아두실 점

<주의·부작용·영향 없는 범위. "이건 안 건드려도 됩니다"도 여기에 적는다.
 없으면 이 절을 통째로 뺀다 — 빈 절을 남기지 않는다.>

확인 후, 처리 코멘트 등록 부탁드립니다.
````

- **말투는 존댓말**이다. 저장소 문서(반말)와 다르다 — 사람에게 보내는 글이다.
- 코드·패킷 이야기는 **지금 모양 → 요청 모양**을 코드 블록 둘로 나란히 보인다. 말로 풀지 않는다.
- 문서·일감 링크는 **저장소 상대 경로**로 건다 (`tasks/T-031-클라가챠화면.md`).
- 마무리 문장은 **한 줄 그대로** 쓴다: `확인 후, 처리 코멘트 등록 부탁드립니다.`

## 4. 올리는 절차

1. **본문을 파일로 쓴다** — 스크래치패드에 `.md`로. 한글·백틱이 많아 인자로 넘기면 깨진다.
2. `gh label list`로 라벨 이름을 확인한다.
3. 이슈를 만든다.

   ```bash
   gh issue create \
     --title "[서버 확인] …" \
     --body-file "<스크래치패드>/issue.md" \
     --assignee wlsdn2749 \
     --label question
   ```

4. **올린 뒤 번호를 일감에 적는다** — `tasks/T-0XX-*.md`의 관련 링크 줄에
   `[이슈 #NN](https://github.com/JeongTaeWoong99/Windows_simulator/issues/NN)`.
   INDEX 표에도 이미 이슈 링크를 다는 칸이 있다.
5. **사용자에게 초안을 보이고 확인을 받은 뒤 올린다.** 이슈는 남에게 알림이 가는 글이다 —
   확인 없이 `gh issue create`를 실행하지 않는다.

---

## 5. 이슈를 닫을 때

- 상대가 처리 코멘트를 남기고 **내 쪽 확인까지 끝났을 때** 닫는다.
- 요청이 무산됐거나 다른 방법으로 풀렸으면 **왜 안 하기로 했는지 코멘트를 남기고** 닫는다 —
  `wontfix` 라벨. 조용히 닫지 않는다.
