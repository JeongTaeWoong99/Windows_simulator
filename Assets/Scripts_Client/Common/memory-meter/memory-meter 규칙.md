# memory-meter 폴더 규칙

> 최종 업데이트: 2026-08-31 (라벨이 바뀔 때만 툴바 갱신) · 대상: `Common/memory-meter/`

**에디터 메모리 사용량을 상단 툴바에 실시간으로 표시하는 툴.** 게임을 전혀 모르는 범용 툴이라
[Arca Unity Toolkit](https://github.com/JeongTaeWoong99/Arca_Unity_Toolkit) 사본인 `Common/` 아래에 있다.
툴바 버튼·아이콘·환경 설정 공통 규칙은 [`editor-shared 규칙.md`](<../editor-shared/editor-shared 규칙.md>)에 있다.

이 문서는 **길지만 쪼개지 않는다** — 버튼에 뜨는 숫자를 오해 없이 읽으려면
용어 정의와 작업 관리자 대응표를 함께 봐야 한다.

## 무엇을 어떻게 재나

유니티에는 **메모리를 상시로 보여 주는 내장 설정이 없다** — Profiler 창이나 Memory Profiler
패키지를 열어야만 보인다. 그래서 상단 툴바에 숫자 하나를 얹어 곁눈질로 확인할 수 있게 했다.
(하단 상태 표시줄에 얹는 공식 API는 없다. 내부 API뿐이라 쓰지 않는다.)

- **버튼에 보이는 값은 프로세스의 워킹셋** — OS가 재는 "지금 물리 RAM에 올라가 있는 양"이다.
  툴팁의 세 갈래를 더한 값이 **아니고**, 그 셋과 배타적으로 나뉘지도 **않는다**(아래 용어 절 참조).
  작업 관리자 `프로세스` 탭의 메모리 열은 **활성 개인 작업 집합**(공유 페이지 제외)이라
  이 값이 공유 DLL 몫만큼 더 크게 나온다.
  ⚠️ **`System.Diagnostics.Process.WorkingSet64`는 유니티의 Mono에서 현재 프로세스에 대해 0을 준다**(실측).
  그래서 `psapi.dll`의 `GetProcessMemoryInfo`를 P/Invoke로 직접 부른다. Windows 전용이며,
  실패하면 경고 한 번을 남기고 0으로 표시한다.
- **툴팁은 세 갈래로 쪼개 보여 준다** — 네이티브(에셋·씬) · Mono 힙(C# 스크립트) · 그래픽 드라이버.
  각각 `할당 / 확보`로 적는다. 프로파일러 수치는 **물리 RAM 적재 여부와 무관**하다.
  실측에서 어느 중형 프로젝트 에디터가 **워킹셋 2.1GB / 커밋 크기 9.2GB**였다(2026-08-22).
  그래서 `Mono 할당 2.58GB`인데 버튼이 `0.81GB`를 가리키는 상황이 정상이다.
- **확보(Reserved)는 줄일 수 없다.** 유니티의 GC는 Boehm 기반이라 **비압축(non-compacting)** —
  객체를 회수해도 힙을 압축해 OS에 반납하지 못한다. 정리 버튼이 줄이는 건 '할당'뿐이고,
  확보를 되돌리려면 **에디터를 재시작**해야 한다. 툴팁에도 이 문장을 적어 뒀다.
  비압축이 실제로 물리는 대가는 둘이다 — ⓐ 빈 공간 **총량**이 남아도 **연속 블록**이 모자라면
  힙을 새로 확장한다(확보가 계단식으로만 오른다) ⓑ 살아있는 객체가 흩어져 있어 페이지를
  통째로 비우지 못하므로 안 쓰는 페이지가 콜드로 내려가지 못한다.
- ⚠️ **GC 수거는 물리 메모리를 즉시 줄이지 않는다.** 회수된 자리는 Mono의 free list에 남을 뿐
  커밋도 워킹셋도 그대로다. 그 페이지를 한동안 아무도 안 건드려 **OS가 트림해야** 비로소
  워킹셋에서 빠진다 — 즉 물리가 내려가는 건 GC가 아니라 OS의 판단이고, 시차가 있다.
- ⚠️ **툴팁 패널의 폭은 넓힐 수 없다.** 유니티 내장 툴팁은 네이티브가 그리고 폭 상한이 고정이라
  USS(`--unity-tooltip`은 색 계열 커스텀 프로퍼티일 뿐이다)로도 공개 API로도 못 건드린다.
  그래서 **툴팁 문구는 한 줄을 한글 24자 이내로 직접 끊는다** — 그래야 문장 중간에서 꺾이지 않는다.
  수치는 가변폭 폰트라 공백 패딩으로 열을 못 맞추므로 **`이름 줄` / `값 줄`로 나눠** 세로로 세운다.
  (내부 툴팁 요소를 리플렉션으로 손대는 건 [`editor-shared 규칙.md`](<../editor-shared/editor-shared 규칙.md>)의 "툴바 버튼은 공식 API로만 붙인다"와 같은 부류라 하지 않는다.)
- **갱신은 `EditorApplication.update`에서 1초에 한 번**, 그중에서도 **라벨이 실제로 바뀐
  경우에만** 한다. 값을 바꾼 뒤 `MainToolbar.Refresh(path)`로 툴바에 알리는 게 공식 갱신 경로다.
  도메인 리로드마다 팩토리 메서드가 다시 불리므로 구독은 `-=` 후 `+=`로 건다.
- 🔴 **바뀐 게 없으면 `Refresh`를 부르지 않는다.** `Refresh`는 UI Toolkit에게 버튼 텍스트
  메시를 다시 만들게 하는데, 그 생성이 **지연 실행**이라 그 사이 유니티가 폰트 아틀라스
  `Material`을 언로드하면(플레이 모드를 빠져나올 때 자동으로 돈다) 콘솔에
  `MissingReferenceException: ... Material ... has been destroyed`가 뜬다.
  뒤이어 `MeshGenerationContext ... Did you forget to call 'End'?`가 따라오는데 **같은 사건의
  후유증**이다 — 예외가 그리기 도중에 던져져 `End()`가 불리지 못한 것이지 별개 문제가 아니다.
  유니티 내부의 레이스라 우리가 없앨 수는 없다. 다만 바뀐 것도 없이 매초 다시 만들며 그 창을
  열어 둘 이유가 없어 라벨 비교를 둔다 (2026-08-30 실측: 플레이 종료 18회 중 2회).
  ※ 대신 라벨(워킹셋)이 같은 동안은 **툴팁 수치도 멈춘다.** 툴팁은 네이티브가 그려 이 문제와
    무관하고, 라벨이 같다는 건 MB 단위로 그대로라는 뜻이라 감수한다.
- **클릭하면** `EditorUtility.UnloadUnusedAssetsImmediate()` + `GC.Collect()`로 정리하고
  `[메모리] 전 → 후 (차이)`를 콘솔에 남긴다. 확인 팝업은 없다(되돌릴 게 없는 안전한 동작).
  에디터에서 `Resources.UnloadUnusedAssets()`는 비동기라 결과를 바로 못 재므로 즉시판을 쓴다.
  전/후를 **워킹셋으로 재므로 델타가 `+`(증가)로 찍힐 수 있다** — 트림 시점은 OS 소관이라
  정리 직후엔 아직 안 빠졌고, 정리하느라 훑은 페이지가 오히려 워킹셋에 올라오기 때문이다.
  로그 코드에 `+` 분기가 있는 이유가 이것이다(오류가 아니다).

## 📖 용어 — 예약 · 커밋 · 워킹셋 · 대기 · 할당 · 확보

**섞어 쓰면 반드시 오해가 난다.** 층이 둘인데, 두 층이 같은 단어를 다른 뜻으로 쓴다.

### ① 먼저 두 층을 가른다 — 가상 주소 vs 물리 프레임

아래 모든 혼동의 뿌리다. **'페이지'라는 한 단어로 두 개를 가리키면 반드시 꼬인다.**

```
[가상 주소 공간]   프로세스 소유. 유니티 할당자 · Mono 힙이 사는 세계
       │
       │  매핑 — OS가 붙였다 뗐다 한다
       ▼
[물리 RAM 프레임]  OS 소유. 모든 프로세스가 나눠 쓰는 자원
```

| | 다루는 층 |
|---|---|
| 예약 · 커밋 · `확보` · `할당` · **Boehm이 반납을 안 한다** | 위(가상) |
| 워킹셋 · 대기 · 트림 · **값이 오르내린다** | 아래(물리) |

> ⚠️ **커밋된 가상 페이지가 남에게 넘어가는 일은 없다.** 프로세스가 죽을 때까지 그 프로세스 것이다.
> 다른 프로세스가 가져가는 건 **그 페이지가 앉아 있던 물리 프레임**이고, 매핑만 끊긴다.
> 그래서 두 층은 **따로 움직인다** — 한쪽이 줄어도 다른 쪽은 그대로일 수 있다.

### ② OS(Win32) 층 — 3단계

| 용어 | 영문 | 뜻 | 물리 RAM에 있나 |
|------|------|-----|-----------------|
| **예약** | Reserve | 가상 주소만 찜해 둔 상태. **접근하면 죽는다**(access violation) | ❌ 페이지 파일도 안 쓴다(공짜) |
| **커밋** | Commit | OS가 "이만큼은 보장한다"고 약속한 상태. **접근 가능** | 🔸 물리 RAM **또는** 페이지 파일 |
| **워킹셋** | Working set | 커밋분 중 **지금 물리 RAM에 올라와 있는 부분** | ✅ |

> ⚠️ **커밋은 "물리 RAM에 없는 것"이 아니다.**
> 커밋은 "쓸 수 있게 확보한 것"이고, 그중 실제로 건드린 페이지는 물리 RAM에 올라가 있다.
> 즉 **`워킹셋 ⊂ 커밋`**. 오래 안 건드린 페이지는 Windows가 워킹셋에서 빼내는데(트림),
> **커밋에는 그대로 남고 워킹셋에서만 빠진다.** 빠진 페이지의 행선지는 ⑤에 있다.

### ③ 유니티 프로파일러 층 — 2단계

**OS의 '커밋' 안쪽을 쪼갠 이야기다.** 이 층은 물리 RAM을 아예 재지 않는다.

| 툴팁 표기 | API | 뜻 |
|-----------|-----|-----|
| **확보** | `GetTotalReservedMemoryLong` · `GetMonoHeapSizeLong` | 유니티 할당자가 OS에서 미리 받아 둔 풀 |
| **할당** | `GetTotalAllocatedMemoryLong` · `GetMonoUsedSizeLong` | 그 풀에서 실제로 객체에 나눠 준 양 |

> ⚠️ **유니티의 `Reserved`를 '예약'으로 옮기면 안 된다.**
> Win32의 예약(주소만 찜해 접근하면 죽는 상태)이 아니라 **이미 커밋된 풀**이다.
> 그래서 툴팁은 `예약`이 아니라 **`확보`**로 적는다.
>
> 같은 이유로 `Allocated`도 '실제 사용량'이라 쓰지 않는다 — "물리 RAM에 올라와 있다"로
> 읽히는데 실제로는 RAM 적재 여부와 무관하다. **`할당`**으로 적는다.

### ④ 포함 관계

```
할당  ≤  확보  ≤  프로세스 커밋
워킹셋  ⊂  프로세스 커밋
워킹셋  vs  할당 · 확보   →   포함 관계 없음
```

> 📌 **버튼 값(워킹셋)과 툴팁의 세 갈래는 배타적 분할이 아니다.**
> 같은 메모리를 다른 잣대로 잰 값이라 **서로 겹친다** —
> `Mono 할당 2.58GB`의 일부는 이미 `워킹셋 0.81GB` 안에 들어 있다.
> 그래서 툴팁에서 "전체 / 몫"이라는 단어를 버리고
> `버튼 값 = 워킹셋` · `유니티 할당자`로 적는다.
> 단, **그래픽 드라이버 몫은 VRAM이라 워킹셋에 아예 안 들어간다.**

### ⑤ 워킹셋이 오르내리는 이유 — 트림과 대기(Standby)

버튼 값이 `8.9GB → 2GB`로 떨어져도 **대개 해제된 게 아니다.** OS가 트림한 것이다.

```
Active (워킹셋)
   │  ← 트림
   ├─ 수정된(dirty) 페이지 → 수정 리스트 → 페이지 파일에 '사본'을 기록 ─┐
   └─ 안 바뀐(clean) 페이지 ────────────────────────────────────────┤
                                                                    ▼
                                                    대기(Standby) 리스트
                                                    ★ 아직 RAM에 있고 내용도 온전하다
                                                                    │
                                              ← 다른 데서 RAM을 요구할 때 비로소 회수
                                                                    ▼
                                                            여유(Free) — 내용 소멸
```

> ⚠️ **트림된 페이지가 곧장 디스크로 내려가는 게 아니다.** 대기 리스트는 **물리 RAM**이다.
> 트림은 페이지를 옮기는 게 아니라 *"이 프로세스 소유"*에서 *"필요하면 뺏어가도 되는 캐시"*로
> **분류를 바꾸는 것**이다.

| 다시 접근할 때 | 무슨 일 | 비용 |
|---|---|---|
| 아직 **대기**에 있으면 | soft fault — 라벨만 되돌린다. 디스크에 안 간다 | 마이크로초 |
| 이미 **여유**로 회수됐으면 | hard fault — 페이지 파일에서 읽어 온다 | 수백 마이크로초 |

- **트림 트리거**: 시스템 메모리 압박 · **창 최소화**(Windows가 특히 공격적으로 민다) · 백그라운드 전환.
- 그래서 **오르내림 자체는 정상**이다. 계단식으로 한 번 뚝 떨어졌다면 그건 트림이 아니라
  진짜 해제다 — 도메인 리로드(스크립트 재컴파일로 Mono 힙 폐기) · 에셋 언로드 · 씬 언로드.

### ⑥ 커밋 한도와 OOM

```
커밋 한도 = 물리 RAM + 페이지 파일 크기      (시스템 전체 합계)
```

- **트림은 커밋을 한 톨도 줄이지 않는다.** 페이지가 워킹셋에 있든 대기에 있든 페이지 파일에
  있든 **커밋 차지는 똑같다** — 커밋은 위치가 아니라 "백업 저장소를 잡아 뒀다"는 약속이다.
  커밋이 줄어드는 건 프로세스가 `VirtualFree`로 반납할 때뿐인데, **Boehm은 그걸 안 한다.**
- 그래서 **물리 RAM이 남아돌아도 커밋 한도가 차면 할당이 거부된다**(OOM). `확보`가 안 줄어드는
  게 비용으로 돌아오는 지점이 여기다. 실측 `워킹셋 2.1GB / 커밋 9.2GB`에서 위험한 쪽은 뒤 숫자다.
- ❌ **주소 공간이 연속으로 모자라서 나는 게 아니다.** 64비트 사용자 모드 주소 공간은 128TB라
  거의 문제되지 않는다(32비트 시절 이야기다). 연속성이 실제로 걸리는 곳은 **Mono 힙 안쪽**이고,
  그건 위 "무엇을 어떻게 재나" 절의 비압축 ⓐ 항목이다.

## 🔍 작업 관리자와 견주는 법

### 먼저 — 필요한 열은 기본으로 꺼져 있다

`커밋 크기`는 **처음엔 화면에 없다.** 직접 켜야 한다.

```
작업 관리자
  └ 왼쪽 사이드바 '자세히' 클릭          ← '프로세스'가 아니다
      └ 열 머리글 아무 데나 우클릭
          └ [열 선택(S)]
              └ 목록에서 '커밋 크기' 체크 → 확인
```

> 💡 탭 이름이 **`자세히`**(영문 Details)다. 사이드바 맨 위의 **`프로세스`**는
> 앱이 트리로 묶여 나오고 `메모리` 열이 기본으로 보이는 다른 화면이다.
> (열 이름은 `Taskmgr.exe.mui`의 한국어 리소스에서 실제 문자열을 확인한 것이다.)

### 어느 열과 견주나

| 툴팁 / 버튼 항목 | 재는 잣대 | 작업 관리자에서 |
|------------------|-----------|-----------------|
| **버튼 값 = 워킹셋** | 전체 워킹셋 — 공유 DLL 포함 | `자세히` → **`작업 집합(메모리)`** |
| **네이티브 · Mono 힙의 `확보`** | 유니티가 커밋해 받아 둔 풀 | `자세히` → **`커밋 크기`** ⭐ 켜야 보임 |
| **네이티브 · Mono 힙의 `할당`** | 그 풀 안에서 실제로 나눠 준 양 | ❌ **대응 열이 없다** (아래 참조) |
| **그래픽 드라이버** | VRAM — 프로세스 메모리엔 아예 안 잡힌다 | `자세히` → **`전용 GPU 메모리`**, 또는 `성능 → GPU` |
| *(참고)* `프로세스` 탭의 '메모리' | 활성 개인 작업 집합 — 공유 몫 제외 | `프로세스` 탭에 **기본으로 있는** 열 |
| *(참고)* 트림돼 빠져나간 몫 | 대기(Standby) — 시스템 전체 값이라 프로세스별로는 못 본다 | `성능 → 메모리`의 **메모리 구성** 막대 (아래) |

> ⚠️ **`할당`은 작업 관리자에서 볼 수 없다 — 빠뜨린 게 아니라 원래 없다.**
> `할당`은 유니티 할당자가 **자기 풀 안에서** 나눈 몫이라 유니티만 아는 값이다.
> OS는 풀을 통째로 커밋해 준 뒤로는 그 안을 들여다보지 않으므로, 유니티가 객체에
> 얼마를 내줬는지 셀 방법이 없다. 작업 관리자에 있는 열은 전부 OS 층의 잣대
> (예약 · 커밋 · 워킹셋)뿐이다.
> 👉 `할당`을 보려면 **`Window → Analysis → Profiler → Memory`** 모듈이나
> **Memory Profiler 패키지**를 연다. 툴바 버튼의 툴팁이 읽는 값도 여기와 같은 API다.

> 💡 `Win+R` → **`resmon`**(리소스 모니터) → `메모리` 탭이면
> 커밋 · 작업 집합 · 공유 가능 · 프라이빗을 **열 추가 없이 한 화면**에서 볼 수 있다.

### 대기(Standby)를 눈으로 확인하는 곳

`성능 → 메모리`의 **`메모리 구성`** 막대에 마우스를 얹으면 네 구획이 뜬다.
(아래는 `Taskmgr.exe.mui` 한국어 리소스에서 뽑은 실제 문자열이다.)

| 구획 | 툴팁 설명 |
|------|-----------|
| `사용 중` | 프로세스, 드라이버 또는 운영 체제에서 사용하는 메모리 |
| `수정` | 다른 용도로 사용하기 전에 콘텐츠를 디스크에 기록해야 하는 메모리 |
| **`대기`** | 캐시된 데이터와 활발히 사용되지 않는 코드를 포함하는 메모리 |
| `여유` | 현재 사용 중이 아니며 … 추가 메모리가 필요할 때 먼저 사용되는 메모리 |

> 📌 같은 화면의 요약 수치가 이 관계를 못 박아 준다.
> - **`사용 가능`** = "즉시 사용할 수 있는 메모리**(대기 메모리 및 여유 메모리 포함)**의 양"
> - **`캐시됨`** = "…캐시된 데이터와 코드를 포함하는 메모리**(대기 메모리 및 수정된 메모리 포함)**의 양"
>
> 즉 **대기는 이미 `사용 가능`으로 집계돼 있다.** 트림으로 워킹셋에서 빠진 몫은
> RAM에 앉은 채 "남는 메모리"로 계산되고 있는 것이지, 사라진 게 아니다.
