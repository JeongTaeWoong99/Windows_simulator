## 기능별 패킷 요약

### 로그인 — ⭐ 한 번 보내면 여러 개가 따라온다

- 보냄: `C_LoginRequest { Id }` (Id만 넘기면 됨)
- 받음: **연달아 1회씩.** 인벤토리·슬롯을 따로 요청하는 패킷은 **서버에 아예 없다.**

```
S_LoginResponse             { Result, SessionId }
S_CurrencyResponse          { Currencies }   ← 재화 잔액
S_InventoryResponse         { Items }        ← 인벤토리 전체 스냅샷
S_GatherResultResponse      { ... }          ← 오프라인 누적 채취분 (있을 때만)
S_CharacterListResponse     { Characters }   ← 보유 캐릭터 (슬롯보다 먼저 온다)
S_WorkStationSlotsResponse  { Slots }        ← 작업슬롯 전체 스냅샷
```

**UI 초기화는 이것들이 다 온 뒤를 기준으로 잡는다.** 로그인 응답만 보고 화면을 그리면 빈 상태가 보인다.

> ⚠️ **인벤토리 스냅샷은 채취 정산 "전" 값이다.** 서버가 `SendInventory()`를 먼저 보내고
> 그 다음에 정산한다(`User.cs`). 오프라인 누적분은 뒤이어 오는
> `S_GatherResultResponse.ItemChanges`에 들어 있으니, 스냅샷만 믿으면 수량이 모자라 보인다.

> 💡 **닉네임 패킷은 없다.** 서버가 이름을 돌려주지 않아서
> 로그인에 쓴 Id(`PlayerDataModel.LoginId`)를 그대로 표시에 쓰고 있다.

### 가챠

- 보냄: `C_GachaDrawRequest { GachaId, DrawCount(1 or 10) }`
- 받음: `S_GachaDrawResponse { Result, Rewards, ItemChangeInfos }`
- ⚠️ **로그인으로 User가 생성된 뒤에만 동작** → 반드시 **로그인 먼저 → 가챠** 순서.
- **인벤토리 반영은 `ItemChangeInfos`로 한다** — 갱신 후 누적 총량이라 **덮어쓰기**
  ([`서버 동작 이해.md`](<서버 동작 이해.md>)의 「⭐ 수량 값의 의미」 참조).
  별도 `S_UpdateItemResponse`는 오지 않는다. 필요한 값이 이 패킷에 다 들어 있다.
- `Rewards`는 **연출 전용**이다. 10연차는 뽑힌 순서대로 개별 항목이 오므로 같은 아이템이 여러 줄일 수 있다 —
  등급·순서를 보여 주는 데만 쓰고, **수량 계산에는 쓰지 않는다.**

### 작업슬롯 / 채취

**"낚시 패킷"은 없다.** 낚시 = `Industry = EIndustryType.Fishing`인 작업슬롯 배치일 뿐이고,
채취 결과는 산업 구분 없이 전부 `S_GatherResultResponse`로 온다.

> ⚠️ **산업 타입은 `MikaProtocol.EIndustryType`이다** (2026-08-10 · 이슈 #13. 전에는 `byte`였다).
> **1차 산업 5종 + `None`만** 담는 전용 타입이라 아이템 분류(`Misc`·`Special`)가 섞일 수 없다.
> `GameData.ItemType`으로 캐스팅하지 않는다 — 값은 1:1이지만 뜻이 다르다.

- 보냄: `C_WorkStationAssignRequest { SlotIndex, Industry, CharacterId }`
  - **배치와 해제가 같은 패킷.** `Industry = EIndustryType.None, CharacterId = 0`으로 보내면 해제다.
- 받음: `S_WorkStationAssignResponse { Result, Slot }` — 변경된 **슬롯 하나만** 온다
- 받음(푸시): `S_GatherResultResponse { SlotIndex, JudgeCount, ItemChanges }`
- 받음(푸시): `S_WorkStationSlotSyncResponse { Slot }` — **정산·속도 변경 때마다** 그 슬롯의 최신 상태.
  전체 스냅샷이 아니라 1칸이다. `PlayerDataModel`이 캐시에 병합하고 `WorkStationSlotsChanged`를 발행한다.
  **채취 결과와 별개 패킷인 이유**는 수확이 없어도(버프·장비로 속도만 바뀌어도) 내려와야 하기 때문이다.

⭐ **핵심 — 로그인만으로는 채취 패킷이 오지 않는다.**
서버 타이머(`GatheringScheduler`)는 항상 돌지만, 슬롯이 **활성**
(`Industry != None && CharacterId != 0`)이어야 판정이 나간다.
신규 계정 슬롯은 `industry=0, character_id=0`으로 생성되므로 **배치 요청을 보내야 시작된다.**

```
로그인 → 슬롯 배치 → (주기) → 채취 푸시 → (주기) → 채취 푸시 → ... → 해제하면 멈춤
```

- 수확이 없으면 패킷 자체가 안 온다(빈 패킷 스팸 없음).
- 로그인·슬롯 변경 시엔 밀린 구간을 한 번에 정산하므로 `JudgeCount`가 2 이상일 수 있다.

#### 카운트다운은 클라가 직접 계산한다

**서버는 주기(초)를 보내지 않는다.** 슬롯마다 속도가 다르고 버프로 바뀌기 때문이다.
대신 진행도·속도·1회 비용을 주므로 클라가 계산한다. 단위는 **밀리초 × 천분율 속도**다.

```
경과ms = 지금ms - LastTickAtUnixMs
누적   = ProgressUnits + 경과ms × CurrentWorkSpeed
남은량 = JudgeCostUnits - (누적 % JudgeCostUnits)
남은초 = 남은량 / CurrentWorkSpeed / 1000
```

- `JudgeCostUnits`는 `(산업, 레벨)`의 `IndustryLevelTable.RequiredScore`다. Lv1 = `30,000,000`(1.0배속 30초).
- `CurrentWorkSpeed`는 **보정이 전부 적용된 확정값**이다. 적성 기본값이 아니다.
- ⚠️ **이 카운트다운은 연출이다.** 판정은 서버가 하고, 어긋나면 정산마다 오는
  `S_WorkStationSlotSyncResponse`가 교정한다. (전체 스냅샷은 로그인 때 한 번뿐이라 그걸 기다리면 안 된다)

> ⚠️ **`LastTickAtUnixMs`는 밀리초다** (2026-08-10 · 이슈 #11. 전에는 `LastTickAtUnix` **초**였다).
> **`× 1000`을 하지 않는다** — 초로 내려오던 시절 카운트다운이 결과보다 **0.9초 빨랐다.**
> `ProgressUnits`가 "그 시각의" 값인데 시각만 초 경계로 잘려서 클라가 소수부만큼 더 일한 것으로 셌다.
> 같이 고쳐진 것: 서버 푸시 해상도 **1초 → 0.1초**, `LastTickAt`을 정산한 만큼만 전진.

#### ⚠️ CharacterId는 **개체 PK**다 (TID 아님)

가장 헷갈리는 지점. `CharacterId`는 `CharacterTable`의 TID가 아니라
**유저가 소유한 캐릭터 개체의 PK**(`t_character.character_id`)다.
같은 캐릭터를 여러 장 가질 수 있어서 TID로는 유일하게 못 찾는다.

배치가 거절되는 조건은 둘이다.

| 조건 | 내용 |
|------|------|
| 보유 여부 | `TryGetCharacter(characterId)` — **그 개체를 갖고 있지 않으면 거절** |
| 적성 | `CanWork(industry)` — **그 산업의 적성이 0이면 거절** |

> ✅ **캐릭터 목록은 로그인 때 온다** — `S_CharacterListResponse`(슬롯 스냅샷보다 먼저 도착).
> `PlayerDataModel.Characters`에 캐시되고, 배치에 넣을 값은 `FirstCharacterId`로 꺼낸다.
> **인스펙터에 PK를 박지 않는다** — 계정마다 다른 값이라 박는 순간 다른 계정에서 깨진다.

> ⚠️ **이름을 찍을 땐 `PlayerDataModel.GetCharacterName(개체번호)`를 쓴다.**
> `GameDataLoader.GetCharacterName`은 **TID**를 받는다 — 개체 번호를 그대로 넣으면 `?#2`가 나온다.

> ✅ **거절 사유는 `EResultCode`로 온다** — `CharacterNotOwned`(미보유) · `NoAptitude`(적성 0) ·
> `InvalidSlotIndex`(없는 슬롯). `PlayerDataModel`가 `[↓수신]` 경고로 남기는 데서 **끝나지 않는다** —
> `WorkStationAssignCompleted(bool, EResultCode)`로 코드를 함께 실어 보내고,
> 받은 Presenter가 `ResultMessages.ToText(code)`로 우리말 문구를 만들어 알림에 띄운다.
> **서버 enum을 화면에 그대로 노출하지 않는다** — 문구 표는 `UI/System/ResultMessages.cs` 한 곳이다.

#### 적성은 패킷에 실려 온다 (2026-08-10 · 이슈 #13)

`CharacterInfo.Aptitudes`(`List<AptitudeInfo>`)에 **1차 산업 5종이 값 0까지 전부** 들어 있다.
0을 빼면 "다루지 못함(잠금)"과 "정보를 못 받음"이 구분되지 않기 때문이다.

```csharp
// 순서 규약이 아니라 값이 자기 산업을 들고 다닌다 — 한 칸 밀려도 조용히 틀릴 일이 없다
public partial struct AptitudeInfo { EIndustryType Industry; byte Value; }   // Value 0~10
```

- 조회는 **`PlayerDataModel.GetAptitude(개체번호, EIndustryType)`**.
- ⚠️ **`CharacterTable`을 직접 읽지 않는다.** 오늘은 두 값이 같지만(적성을 바꾸는 주체가 아직 없다),
  장비가 적성에 얹히면 개체마다 갈라진다. 특히 **적성 0 → 1 승격**이 생기면 테이블만 본 화면이
  *실제로는 배치 가능한 캐릭터를 잠근다.* `CurrentWorkSpeed`와 같은 원칙 — 보정이 붙는 값은 서버가 낸다.
- **사전 필터는 UX용이고 서버 거절은 그대로 남는다.** 적성 0 배치는 계속 `NoAptitude`로 거절된다.
- 세션 도중 적성이 바뀌면 서버가 푸시한다 → 일감 `T-022`(선행 T-002). 클라는 같은 필드를 다시 읽으면 된다.

#### 현재 서버 제약 (2026-08-10 기준)

| 항목 | 상태 |
|------|------|
| 드롭 테이블 | **5개 산업 전부 등록됨** (농사·낚시·채굴·벌목·사냥, 각 38행) |
| 슬롯 개수 | **0번 하나뿐.** `DefaultSlotCount = 1`이고 해금 경로가 없다(`Unlock()`은 호출부 없음) |
| 없는 슬롯 배치 | `Result = InvalidSlotIndex`로 온다 (예전엔 `Success=false` 하나뿐이었다) |
| 캐릭터 지급 | ⚠️ **1001 한 종만.** 시작 지급이 `DefaultCharacterTid` 고정이고 **가챠는 아이템 전용**이라 다른 종을 가질 길이 없다. 획득 경로는 **기획 미정**(T-010) — 엑셀엔 1001~1006이 이미 있다 |
| 산업 레벨 | ✅ 패킷에 **`WorkStationSlotInfo.IndustryLevel`이 있다.** 다만 지금은 **전원 Lv1**이고 상위 레벨 배치는 거절된다(해금 판정 T-021 미구현) |

구조 자체(딕셔너리·슬롯별 독립 정산·슬롯별 푸시)는 다중 슬롯을 이미 지원한다.

## 게임 테이블 (아이템·캐릭터 이름)

서버와 클라가 **같은 엑셀에서 생성된 `.bytes`** 를 읽는다.
**패킷은 Id만 보낸다** — 이름을 보내지 않으므로 테이블이 없으면 화면에 숫자만 뜬다.

> ⚠️ **적성은 테이블에서 읽지 않는다.** `CharacterTable`에 적성 5열이 있긴 하지만
> **전달값의 주인은 서버**다 — 패킷의 `CharacterInfo.Aptitudes`를 쓴다(위 참조).

> ⚠️ **`CharacterId`는 개체 번호지 TID가 아니다.** 이름 조회 함수가 갈린다.
> 적재 방식·조회 규칙·TID 함정은 [`Data 규칙.md`](<Data/Data 규칙.md>) 참조.

## 테스트 방법

### 패킷은 실제 화면에서 보낸다

**단발 테스트용 디버그 패널은 없다.** 버튼과 패킷이 한자리에 있어야 "이 화면이 무엇을 보내는가"가
코드에서 바로 보이기 때문에, 요청은 그 요청을 일으킨 Presenter가 직접 보낸다.

| 무엇을 보내려면 | 어디서 |
|------|--------|
| 로그인 | `!Login Canvas`의 아이디 입력 후 버튼(또는 엔터) — `LoginPresenter` |
| 가챠 1회 / 10연 | `#Market Canvas > Gacha Presenter` — `GachaPresenter` |
| 작업슬롯 배치 / 해제 | `#Main Canvas`에서 칸을 눌러 `WorkStation Select Presenter` — `WorkStationSelectPresenter` |

> ⚠️ **로그인 전에 보내면 서버가 조용히 버린다.** User를 못 찾아 응답도 오류도 없어서
> 클라에서는 "눌렀는데 아무 일도 안 일어난다"로만 보인다. 각 Presenter가 보내기 전에
> `IsLoggedIn`을 확인하고 이유를 로그로 남긴다.

> ⚠️ **배치에 넣는 값은 캐릭터 종류(TID)가 아니라 서버가 발급한 개체 번호다.**
> 계정마다 다르므로 인스펙터에 박아 둘 수 없다 — 누른 줄(`CharacterStateRowView.CharacterId`)이
> 그 값을 들고 있다. 캐릭터 선택 UI가 없던 시절의 임시 통로는 `PlayerDataModel.FirstCharacterId`다.

### 화면 UI

어느 화면이 어느 패킷을 다루는지는 [`UI 규칙.md`](<UI/UI 규칙.md>) 8장
"지금 배치"에 씬 계층 전체와 함께 있다. 스크립트 배치·전환 흐름도 거기서 본다.

> 로그·하트비트로 왕복을 확인하는 방법은
> [`서버 동작 이해.md`](<서버 동작 이해.md>)의 「로그로 패킷 흐름 보기」·「하트비트」에 있다.
