# Scripts_Client 폴더 구조

> 최종 업데이트: 2026-08-14 (XML 태그 기준 재정의 · `ServerPacketHandler` 예외를 링크로) · 대상: `Assets/Scripts_Client/`

**클라이언트 코드를 처음 열었을 때 읽는 문서.** 어느 폴더에 무엇이 있고,
**새로 만든 스크립트를 어디에 둘지**를 여기서 정한다.

각 폴더의 상세 규칙은 그 폴더 안의 `<폴더명> 규칙.md`에 있다 — 이 문서는 **지도**다.

---

## 1. 폴더 지도

| 폴더 | 무엇이 있나 | 무엇을 넣나 | 넣지 말 것 |
|------|------------|------------|-----------|
| [`Common/`](<Common/Common 규칙.md>) | 서비스 로케이터 · 확장 메서드 · 인스펙터 어트리뷰트 | **게임을 모르는 범용 코드만** | 이 게임을 아는 것 전부. ⚠️ **함부로 만들지 않는다** — 아래 2절 |
| [`Managers/`](<Managers/Managers 규칙.md>) | `PlayerDataModel` · `UIManager` · `WindowManager` · `PingManager` | `MonoService<T>`를 상속해 **서비스로 등록되는** 것 | 화면을 그리는 것(→ `UI/`), 등록이 필요 없는 정적 유틸 |
| [`UI/`](<UI/UI 규칙.md>) | 캔버스 View · Presenter · 종속 View · 레이아웃 | 화면에 무언가를 그리거나 입력을 받는 것 | 화면이 없는 것(`PlayerDataLogger`가 `Log/`에 있는 이유) |
| [`Data/`](<Data/Data 규칙.md>) | `GameDataLoader` | 엑셀에서 나온 **고정 테이블**을 읽는 코드 | 내 계정 상태(→ `Managers/PlayerDataModel`) |
| [`Log/`](<Log/Log 규칙.md>) | `ClientLogger` · `PlayerDataLogger` | 로그 출력 창구와 관찰자 | `Debug.Log` 직접 호출 (전부 `ClientLogger`를 거친다) |
| [`DesktopWindow/`](<DesktopWindow/DesktopWindow 규칙.md>) | `Win32Native` | Win32 / DWM **P/Invoke 선언** | 호출 순서·조건 판단(→ `Managers/WindowManager`) |
| [`Settings/`](<Settings/Settings 규칙.md>) | `WindowSettings` | `PlayerPrefs` 저장·복원 키와 헬퍼 | 설정을 **적용**하는 로직(→ `Managers/WindowManager`) |
| [`Editor/`](<Editor/Editor 규칙.md>) | 씬 복사 · 서버 콘솔 등 (기능별 하위 폴더) | **기능에 묶이지 않는 프로젝트 전용 에디터 툴** | 특정 기능의 에디터 확장(→ 그 폴더 안 `Editor/`), 런타임 코드 |

> `Common/`은 [Arca Unity Toolkit](https://github.com/JeongTaeWoong99/Arca_Unity_Toolkit)의 **사본**이라
> 다른 폴더와 규칙이 다르다. 반드시 [`Common 규칙.md`](<Common/Common 규칙.md>)를 먼저 읽는다.

## 2. 새 스크립트를 어디에 둘까 — 판단 흐름

```
이 스크립트가 이 게임을 아는가? (패킷·테이블·화면 이름을 참조하는가)
├─ 아니오 — 어느 프로젝트에 옮겨도 그대로 쓴다
│   └─ Common/  ⚠️ 단, 마음대로 만들지 않는다 → Common 규칙.md 확인 + 승인 필요
│
└─ 예 — 이 게임 전용이다
    │
    ├─ 화면에 그리거나 입력을 받는가?         → UI/<캔버스>/<Presenter>/
    ├─ Services.Get으로 꺼내 쓸 전역 상태인가? → Managers/   (MonoService<T> 상속)
    ├─ 엑셀 테이블을 읽는가?                   → Data/
    ├─ 로그를 내보내거나 관찰하는가?           → Log/
    ├─ Win32 API 선언인가?                    → DesktopWindow/
    └─ PlayerPrefs 키·저장 헬퍼인가?           → Settings/
```

**두 곳에 걸치면 자른다.** `Win32Native`(선언)와 `WindowManager`(호출 판단)가 갈라져 있고,
`ClientLogger`(출력 방법)와 `PlayerDataLogger`(무엇을 출력할지)가 갈라져 있는 것이 그 예다.

## 3. 클라 전체에 걸리는 규약

### 3-1. nullable 참조 형식 — `= null!` + `RequireRef`

`Assets/csc.rsp`의 `-nullable:enable`로 **켜져 있다.**

| | 필수 참조 (없으면 성립 불가) | 선택 참조 (없어도 정상) |
|---|---|---|
| 선언 | `private Button okButton = null!;` | `private Button? hintButton;` |
| 검증 | `this.RequireRef(...)` → **즉시 예외** | `if (x != null)` → 조용히 건너뜀 |
| 위치 | Presenter·Manager는 `Start()`, 종속 View는 `Awake()` | — |

- **`?`는 안전장치가 아니라 "비어도 정상"이라는 선언이다.** 전부 `?`로 두면 미연결이
  조용히 무시돼 "왜 안 되지?"가 된다.
- ⚠️ **Unity 객체에 `?.`·`??`를 쓰지 않는다.** 파괴된 오브젝트의 "가짜 null"을 통과시킨다.
  `== null`로 검사한다. `?.`는 순수 C#(이벤트·컬렉션)에만.
- 서비스 필드는 `= null!` + `Services.Get<T>()`로 충분하다 — `Get`이 미등록 시 예외를 던진다.

> 상세와 근거는 [`clean-code-style` 9장](<../../.claude/skills/client/clean-code-style/SKILL.md>) 참조.

### 3-2. 서비스 조회는 반드시 `Start`

`Services.Get<T>()`를 `Awake`·`OnEnable`에서 부르면 안 된다. Unity는 오브젝트마다
`Awake → OnEnable`을 이어서 부르므로, 그 시점엔 다른 서비스가 아직 등록 전일 수 있다.

```
Start     → Get + 최초 구독
OnEnable  → 캐시가 있을 때만 재구독 (껐다 켜는 경로)
OnDisable → 구독 해제
```

어기면 `KeyNotFoundException`이 나고, 캐시 필드가 null로 남아 한참 뒤
`NullReferenceException`으로 다시 터진다. 자세한 건 [`Managers 규칙.md`](<Managers/Managers 규칙.md>).

### 3-3. 주석은 코드를 설명하고, 구조는 md가 설명한다

| 코드에 남기는 것 | md로 옮기는 것 |
|---|---|
| `<summary>` 1~3줄 요약 | 여러 파일에 걸친 구조·흐름 |
| 그 줄이 **왜 그런지**(로컬 컨텍스트) | 설계 대안 비교·채택 근거 |
| 고칠 때 **즉시 필요한** 함정 경고 | 역사적 경위("예전엔 ~였다") |
| 호출 경로 표기 (`// … (Unity 메시지)`) | 일반 개념 설명 · 확장 절차 |

#### 예외 — 구조 주석을 코드에 두는 두 곳

| 위치 | 왜 예외인가 |
|---|---|
| [`Common/`](<Common/Common 규칙.md>) | 툴킷 사본이라 **다른 프로젝트로 복사될 때 md가 따라가지 않는다.** 주석을 걷으면 새 프로젝트에서 설명이 통째로 사라진다 |
| `Scripts_Server/.../ServerPacketHandler.cs` | 규칙 md를 둘 자리가 없어 파일 안 주석에 둔다 — 자세한 사정은 [`서버 동작 이해.md`](<서버 동작 이해.md>)의 「⭐ `ServerPacketHandler`는 문서 규칙의 예외다」 |

> 두 곳 다 **표기 규칙(3-4)은 똑같이 지킨다** — 예외인 것은 "무엇을 적는가"이지 "어떻게 적는가"가 아니다.

### 3-4. ⚠️ XML **서식** 태그를 쓰지 않는다

가르는 기준은 **구조냐 서식이냐**다.

| | 태그 | |
|---|---|---|
| ✅ **구조** — 문단의 역할을 나타낸다 | `<summary>` · `<remarks>` · `<param>` · `<returns>` | 쓴다 |
| ❌ **서식** — 글자를 꾸민다 | `<c>` · `<b>` · `<br/>` · `<para>` · `<code>` · `<see cref>` | 쓰지 않는다 |

> 실제로 이 프로젝트에 쓰인 건 `<summary>`·`<remarks>`·`<param>` 셋뿐이다
> (반환값 있는 public API가 드물어 `<returns>`는 아직 등장하지 않았을 뿐, 금지는 아니다).

| | |
|---|---|
| ❌ | `/// <c>UIManager</c>가 <b>단일 출입구</b>다` |
| ✅ | `/// 'UIManager'가 단일 출입구다` |

**이유** — 이 태그들은 **IDE 툴팁에서만** 서식으로 변환된다. 정작 코드를 읽을 때는
태그가 그대로 보여 문장을 가린다. 얻는 것(툴팁 서식)보다 잃는 것(상시 가독성)이 크다.
`<b>`·`<br/>`는 애초에 XML 문서 주석 표준 태그도 아니다(HTML이라 IDE마다 다르게 그려진다).

- **클래스·파일·오브젝트 이름은 작은따옴표**로 감싼다 — `'WindowManager'` · `'UI 규칙.md'` · `'#Main Canvas'`
- 강조가 필요하면 **문장을 다시 쓴다.** 굵게 하는 대신 ⚠️·★ 같은 기호를 문장 앞에 둔다
- 다이어그램은 `<code>` 없이 `///` 들여쓰기만으로 그린다

> ⚠️ 제네릭을 주석에 적을 때 주의 — `MonoService<T>`처럼 `<`가 들어가면 XML 파서가
> 태그로 읽어 **CS1570**이 난다. `'MonoService T'`처럼 풀어 쓰거나 따옴표 안에 둔다.
