# Scripts_Client 폴더 구조

> 최종 업데이트: 2026-08-25 (XML 문서 주석 금지로 3-4절 개정) · 대상: `Assets/Scripts_Client/`

**클라이언트 코드를 처음 열었을 때 읽는 문서.** 어느 폴더에 무엇이 있고,
**새로 만든 스크립트를 어디에 둘지**를 여기서 정한다.

각 폴더의 상세 규칙은 그 폴더 안의 `<폴더명> 규칙.md`에 있다 — 이 문서는 **지도**다.
`UI/`·`Editor/`는 하위 폴더마다 규칙 문서를 또 둔다(→ [3-5절](#3-5-규칙-md는-자기-폴더의-규칙만-담는다)).

## 2. 새 스크립트를 어디에 둘까 — 판단 흐름

```
이 스크립트가 이 게임을 아는가? (패킷·테이블·화면 이름을 참조하는가)
├─ 아니오 — 어느 프로젝트에 옮겨도 그대로 쓴다
│   └─ Common/  ⚠️ 단, 마음대로 만들지 않는다 → Common 규칙.md 확인 + 승인 필요
│
└─ 예 — 이 게임 전용이다
    │
    ├─ 화면에 그리거나 입력을 받는가?         → UI/<캔버스>/<Presenter>/
    ├─ Services.Get으로 꺼내 쓸 전역 상태인가? → Managers/   (MonoService<T> 상속)
    ├─ 엑셀 테이블을 읽는가?                   → Data/
    ├─ 로그를 내보내거나 관찰하는가?           → Log/
    ├─ Win32 API 선언인가?                    → DesktopWindow/
    └─ PlayerPrefs 키·저장 헬퍼인가?           → Settings/
```

**두 곳에 걸치면 자른다.** `Win32Native`(선언)와 `WindowManager`(호출 판단)가 갈라져 있고,
`WindowSettings`(저장 키)와 `WindowManager`(적용 판단)가 갈라져 있는 것이 그 예다.

## 3. 클라 전체에 걸리는 규약

### 3-1. nullable 참조 형식 — `= null!` + `RequireRef`

`Assets/csc.rsp`의 `-nullable:enable`로 **켜져 있다.**

| | 필수 참조 (없으면 성립 불가) | 선택 참조 (없어도 정상) |
|---|---|---|
| 선언 | `private Button okButton = null!;` | `private Button? hintButton;` |
| 검증 | `this.RequireRef(...)` → **즉시 예외** | `if (x != null)` → 조용히 건너뜀 |
| 위치 | Presenter·Manager는 `Start()`, 종속 View는 `Awake()` | — |

- **`?`는 안전장치가 아니라 "비어도 정상"이라는 선언이다.** 전부 `?`로 두면 미연결이
  조용히 무시돼 "왜 안 되지?"가 된다.
- ⚠️ **Unity 객체에 `?.`·`??`를 쓰지 않는다.** 파괴된 오브젝트의 "가짜 null"을 통과시킨다.
  `== null`로 검사한다. `?.`는 순수 C#(이벤트·컬렉션)에만.
- 서비스 필드는 `= null!` + `Services.Get<T>()`로 충분하다 — `Get`이 미등록 시 예외를 던진다.

> 상세와 근거는 [`clean-code-style` 9장](<../../.claude/skills/client/clean-code-style/SKILL.md>) 참조.

### 3-2. 서비스 조회는 반드시 `Start`

`Services.Get<T>()`를 `Awake`·`OnEnable`에서 부르면 안 된다. Unity는 오브젝트마다
`Awake → OnEnable`을 이어서 부르므로, 그 시점엔 다른 서비스가 아직 등록 전일 수 있다.

```
Start     → Get + 최초 구독
OnEnable  → 캐시가 있을 때만 재구독 (껐다 켜는 경로)
OnDisable → 구독 해제
```

어기면 `KeyNotFoundException`이 나고, 캐시 필드가 null로 남아 한참 뒤
`NullReferenceException`으로 다시 터진다. 자세한 건 [`Managers 규칙.md`](<Managers/Managers 규칙.md>).

### 3-3. 주석은 코드를 설명하고, 구조는 md가 설명한다

| 코드에 남기는 것 | md로 옮기는 것 |
|---|---|
| `<summary>` 1~3줄 요약 | 여러 파일에 걸친 구조·흐름 |
| 그 줄이 **왜 그런지**(로컬 컨텍스트) | 설계 대안 비교·채택 근거 |
| 고칠 때 **즉시 필요한** 함정 경고 | 역사적 경위("예전엔 ~였다") |
| 호출 경로 표기 (`// … (Unity 메시지)`) | 일반 개념 설명 · 확장 절차 |

#### 예외 — 구조 주석을 코드에 두는 두 곳

| 위치 | 왜 예외인가 |
|---|---|
| [`Common/`](<Common/Common 규칙.md>) | 툴킷 사본이라 **다른 프로젝트로 복사될 때 md가 따라가지 않는다.** 주석을 걷으면 새 프로젝트에서 설명이 통째로 사라진다 |
| `Scripts_Server/.../ServerPacketHandler.cs` | 규칙 md를 둘 자리가 없어 파일 안 주석에 둔다 — 자세한 사정은 [`서버 동작 이해.md`](<서버 동작 이해.md>)의 「⭐ `ServerPacketHandler`는 문서 규칙의 예외다」 |

> 두 곳 다 **표기 규칙(3-4)은 똑같이 지킨다** — 예외인 것은 "무엇을 적는가"이지 "어떻게 적는가"가 아니다.

### 3-4. ⚠️ XML 문서 주석(`///`)을 쓰지 않는다

**주석은 전부 `//` 로 쓴다.** `<summary>` · `<remarks>` · `<param>` 같은 구조 태그도,
`<c>` · `<b>` · `<see cref>` 같은 서식 태그도 마찬가지다.

**이유** — 이 태그들은 **IDE 툴팁에서만** 뜻을 갖는다. 정작 코드를 읽을 때는 태그가
그대로 보여 문장을 가리고, 3줄 설명이 5~6줄이 된다. 이 프로젝트는 문서 XML을 만들지도
않고(`Assets/csc.rsp` 에 `-nullable:enable` 뿐) 외부에 배포하는 라이브러리도 아니라,
얻는 것(툴팁)보다 잃는 것(상시 가독성)이 크다.

| | |
|---|---|
| ❌ | `/// <summary>'UIManager'가 단일 출입구다</summary>` |
| ❌ | `/// <c>UIManager</c>가 <b>단일 출입구</b>다` |
| ✅ | `// 'UIManager'가 단일 출입구다` |

- **클래스·파일·오브젝트 이름은 작은따옴표**로 감싼다 — `'WindowManager'` · `'UI 규칙.md'` · `'#Main Canvas'`
- 강조가 필요하면 **문장을 다시 쓴다.** 굵게 하는 대신 ⚠️·★ 같은 기호를 문장 앞에 둔다
- 다이어그램은 `//` 들여쓰기만으로 그린다
- 파라미터 설명이 꼭 필요하면 본문 아래에 이름 열을 맞춰 적는다

```csharp
// 서버 요청 하나의 대기를 시작한다 — 로딩을 띄우고 응답까지 감시한다.
//   label    : 타임아웃 문구에 쓸 요청 이름 (예: "로그인")
//   onClosed : 대기가 끝날 때 호출 — 호출부의 버튼 잠금 해제에 쓴다
public ServerWaitHandle Begin(string label, Action? onClosed = null)
```

> `///` 를 걷어내면 제네릭 `<` 로 **CS1570**이 나던 함정도 함께 사라진다.
> `//` 주석은 XML 파서를 타지 않으므로 `MonoService<T>` 를 그대로 적어도 된다.

#### 남아 있는지 확인하는 법

```bash
grep -rn "///" --include="*.cs" Assets/Scripts_Client
```

컴파일도 IDE도 이걸 잡아 주지 않아 **한 번 새면 계속 쌓인다** — 실제로 2026-08-23에
서식 태그가 7개 파일 50곳에서 발견됐고, 2026-08-25에 `///` 자체를 278곳에서 걷어냈다.
주석을 많이 손댄 작업 뒤에는 위 한 줄을 돌린다(0건이어야 한다).

### 3-5. 규칙 md는 자기 폴더의 규칙만 담는다

문서가 커지는 건 대개 **한 하위 주제가 문서를 잠식해서**다. 실제로 `Editor 규칙.md`의 62%가
메모리 미터 설명이었고, `UI 규칙.md`는 함정 절이 175줄이었다. 버튼 하나 붙이려는 사람이
그걸 다 지나쳐야 했다. 2026-08-23에 하위 폴더 문서로 갈랐다.

| 언제 내리나 | 기준 |
|---|---|
| **한 하위 주제가 문서의 1/3을 넘는다** | 그 하위 폴더로 내린다 |
| **400줄(약 25KB)을 넘는다** | 분할을 **검토**한다 — 넘었다고 무조건은 아니다 |

- **한 주제로 이어 읽어야 하는 문서는 길어도 그대로 둔다.** `memory-meter 규칙.md`가
  그렇다 — 용어 표와 작업 관리자 대조는 따로 읽으면 쓸모가 없다.
- 상위 문서에는 **링크와 한 줄 요약만** 남기고, 맨 앞에 "어디를 읽나" 지도를 둔다.
- **짧은 하위 문서는 결함이 아니다.** 그 폴더를 만질 때 도착하는 착지점이고 규칙이 생기면
  거기 쌓인다. 다만 **채우려고 내용을 지어내지 않는다.**

#### 가리킬 때는 번호가 아니라 절 제목으로

```
❌ 'UI 규칙.md' 8장 참조          ← 재편하면 조용히 어긋난다
✅ 'Main 규칙.md'의 "전환 층은 하나다" 절 참조
```

문서 **안에서**는 `§3` 같은 번호를 써도 된다(같이 움직인다). **문서 밖**에서 —
코드 주석·다른 md — 가리킬 때만 제목으로 쓴다. 실제로 코드 주석 5곳이 존재하지 않는
`'UI 규칙.md' 8장`을 가리키고 있었고, 컴파일도 grep도 그걸 잡아 주지 않았다.

#### 하위 폴더가 영문이면 문서명도 영문을 따른다

`memory-meter 규칙.md` · `Layout 규칙.md`처럼 **`<폴더명> 규칙.md` 공식을 지킨다.**
루트 `CLAUDE.md`의 "문서명은 한글" 규칙의 명시적 예외다 — 폴더와 문서 이름이 어긋나면
어느 폴더의 규칙인지 목록에서 알 수 없다.
