# 경매장 — 서버 설계

> 최종 업데이트: 2026-09-23 · 상태: **즉시구매 구현 (T-087) · 입찰은 미착수**

기획 원본은 [`trade/README.md`](../../GameDesign/design/trade/README.md)(D안 — 자유 거래 + 가격 밴드)다.
여기는 그 거래소를 **메인 서버와 분리된 경매장 서버**로 만들 때의 경계·흐름·함정을 적는다.

---

## 1. 전제와 원칙

| 항목 | 내용 |
| --- | --- |
| 배치 | 경매장(`AuctionServer`)은 메인(`WSGameServer`)과 **다른 머신**에 떠 있어도 된다. 메인이 재시작·배포 중이어도 계속 돈다 |
| DB | 각자 로컬 SQLite 파일 하나 — 메인 `game.sqlite3`, 경매장 `auction.sqlite3`. **두 파일에 걸친 트랜잭션은 없다** |
| 통신 | 클라 ↔ 메인은 기존 커스텀 TCP. 메인 ↔ 경매장은 **gRPC, 메인이 항상 호출자**다. 경매장은 외부 포트가 없다 |
| 검색 | **메인이 중계한다** — 클라 → 메인(TCP) → 경매장(gRPC `Search`). 요청 빈도 제한도 메인이 유저 단위로 건다 |
| 전송 보안 | 설정으로 h2c(평문)·mTLS를 고른다. 기본 h2c — 운영 배포 전에 정한다 |
| 거래 | **즉시구매만.** 매물은 **통째로만** 산다(스택 매물의 일부 구매 없음). 입찰은 뒤에 얹는다(8장) |

**소유권은 메인 DB 한 곳에만 있다.** 등록은 아이템을 경매장으로 "옮기는" 것이 아니라 메인 안에서
**잠그는** 것이고, 경매장 DB는 매물 표시·판매 과정의 사실만 갖는다. 아이템이 어느 순간에도
정확히 한 곳에만 있으므로 복제가 구조적으로 생기지 않는다. 경매장 DB가 통째로 사라져도
메인이 잠긴 것을 전부 돌려주면 복구가 끝난다(6장 대사).

## 2. 우리 서버에 맞춘 결정

범용 설계와 달라진 곳과 그 이유다.

| # | 결정 | 이유 |
| --- | --- | --- |
| 1 | **장비는 잠금, 자원은 에스크로** | 장비는 개체(`t_user_equip`)라 행에 잠금을 걸 수 있다. 자원은 스택 수량이라 잠글 개체가 없다 — 인벤토리에서 빼서 `t_auction_trade` 행으로 옮긴다. 둘 다 메인 DB 안이라 한 트랜잭션이다 |
| 2 | **잠긴 장비는 메모리에 없다** | 메인은 메모리가 원천이고 저장은 뒤따른다. 판매자 메모리에 남아 있으면 판매자 쪽 저장이 팔린 장비 행을 덮을 수 있다. 등록하는 순간 메모리에서 빼고, 로그인 적재도 `auction_trade_id = 0`만 읽는다 |
| 3 | **경매장에서 나오는 아이템·골드는 전부 우편** | 골드 저장은 **확정 잔액 덮어쓰기**다. 구매자 트랜잭션이 판매자 골드를 직접 올리면 판매자 메모리의 다음 저장이 덮는다. 우편은 받는 쪽 메모리를 건드리지 않는 단방향 INSERT다. 반환(취소·만료)도 우편이라 창고가 가득 찬 경우를 우편함이 흡수한다 |
| 4 | **장비 우편은 개체를 싣는다** | 기존 `equip_tids`는 TID로 **새로 만든다** — 인챈트가 사라진다. `equip_ids`에 개체 스냅샷을 싣고, 받을 때 잠금을 풀어 창고 칸을 준다 |
| 5 | **구매 중 골드 hold** | `Reserve` 응답을 기다리는 동안 가챠로 골드를 써 버리면 안 된다. `사용 가능 = 잔액 − hold`. 입찰이 그대로 재사용한다 |
| 6 | **gRPC는 로직 스레드 밖** | 로직 스레드(`LogicExecutor`)에서 응답을 기다리지 않는다. DB와 같은 모양 — 호출은 밖에서, 결과는 `LogicExecutor.Post`로 돌아온다 |
| 7 | **경매장은 GameData를 모른다** | 등록 스냅샷에 종류·분류·희귀도·인챈트를 실어 보낸다. 가격 밴드·수수료는 메인이 검증한다 |
| 8 | **Redis·운영 툴 없음** | 메인이 1대라 판매자 알림은 `UserManager`로 직접 한다 |

## 3. 데이터

### 3.1 메인 DB (`game.sqlite3`)

| 테이블/컬럼 | 내용 |
| --- | --- |
| `t_user_equip.auction_trade_id` | 0 = 잠금 없음. 0이 아니면 그 거래에 묶여 **아무의 메모리에도 없다**(등록 중이거나, 우편으로 가는 중) |
| `t_auction_trade` | 등록 1건 = 1행. **메인 쪽 거래 원장이자 자원 에스크로.** `trade_id`가 곧 경매장의 매물 ID다 |
| `t_auction_outbox` | 경매장에 보낼 메시지. 상태 변경과 **같은 트랜잭션**에서 쓴다 |
| `t_user_mail.equip_ids` | 개체 장비 첨부 JSON — 받기 전까지 장비 행은 잠긴 채 받는 사람 소유다 |

`t_auction_trade.state`: `Listed(1) → Settled(2)` 또는 `Listed(1) → Returned(3)`.
**모든 전이는 `WHERE state = 1` 조건부 UPDATE**라서, 정산·반환이 몇 번 들어와도 한 번만 일어난다 —
정산과 만료 반환이 경합해도 먼저 커밋한 쪽만 1행을 바꾼다.

### 3.2 경매장 DB (`auction.sqlite3`, WAL · `synchronous=FULL`)

| 테이블 | 내용 |
| --- | --- |
| `t_listing` | 매물. `listing_id` = 메인 `trade_id`(유니크 = 등록 멱등 키). 스냅샷 · 가격 · 상태 · 예약자 · 만료 시각 |
| `t_purchase` | 구매 시도 1건 = 1행. `purchase_id`(메인 발급)가 `Reserve`·`Confirm`의 멱등 키 |
| `t_event` | 메인이 가져갈 이벤트(취소·만료). `AckEvents`로 지운다 |

매물 상태머신 — 컬럼 하나에 열거형:

```
Listed   → Reserved → Sold
Reserved → Listed            (Confirm 실패 · 예약 타임아웃)
Listed   → Cancelled | Expired
(Reserved | Listed | Expired | Cancelled) → Sold   ← Confirm(성공)만. 메인이 이미 정산했다는 뜻이다
```

`Confirm(성공)`이 종착 상태까지 덮는 이유: 메인이 정산을 커밋한 뒤에만 보내므로 **그 판매는 이미 일어난 사실**이다.
예약 타임아웃 뒤 늦게 도착해도 반영한다. 메인 쪽 반환은 `state = 1` 조건에 걸려 무시되므로 이중 지급은 없다.

## 4. 흐름

### 4.1 등록

```
클라 C_AuctionRegisterRequest(종류, TID/장비 ID, 수량, 단가)
메인 (로직) 검증: 가격 밴드 · 건수 상한 · 등록비 · 보유 · 착용 중 아님
     (로직) 메모리에서 빼기(자원 차감 / 장비 제거) + 등록비 차감
     (DB 1트랜잭션) 인벤 확정 수량 · 골드 확정 잔액 · t_auction_trade INSERT(Listed)
                   · 장비 잠금 · outbox(Register)
     → 클라 S_AuctionRegisterResponse(Ok, 매물 ID)
릴레이 outbox → gRPC Register → 경매장: INSERT Listed(listing_id 유니크) → 커밋 → 인덱스 추가 → Ok
```

- 경매장이 내려가 있으면 outbox가 재시도한다 — 매물이 검색에 늦게 나타날 뿐이다.
- 경매장이 **거부**하면(스냅샷 불량) 메인이 반환 우편을 보낸다(등록비 포함).

### 4.2 구매

```
클라 C_AuctionBuyRequest(매물 ID, 본 총액)
메인 (로직) 사용 가능 골드 ≥ 총액 확인 → hold → purchase_id 발급
     (밖)  gRPC Reserve(purchase_id, 매물, 구매자, 총액)
경매장 Listed → Reserved 조건부 UPDATE (총액 일치 · 판매자 ≠ 구매자 조건 포함) → 인덱스에서 뺌
메인 (로직) 실패 → hold 해제, 사유 응답 (구매 중 / 판매 완료 / 가격 변경 / 없음 / 내 매물)
     (로직) 성공 → hold 해제 · 골드 차감
     (DB 1트랜잭션) trade Listed→Settled 조건부 · 구매자 골드 확정 잔액 · 장비 소유 이전
                   · 구매자 우편(아이템) · 판매자 우편(대금 − 수수료) · outbox(Confirm 성공)
     → 구매자·(접속 중이면) 판매자에게 우편 도착 · S_AuctionBuyResponse(Ok)
     (0행이면) 골드 환급 · outbox(Confirm 실패)
릴레이 outbox → gRPC Confirm → 경매장 Reserved → Sold (실패면 → Listed, 인덱스 복귀)
```

- **선착순은 경매장 쓰기 채널 도착 순서다.** 클라 시계를 믿지 않는다.
- 정산 트랜잭션의 `state = 1` 조건이 이중 판매를 막는다 — 경매장 예약이 어긋나도 메인이 한 번만 판다.
- 메인이 `Reserve` 뒤·정산 전에 죽으면 매물이 `Reserved`에 남는다 → 경매장이 타임아웃으로 `Listed`에 돌린다.

### 4.3 취소 · 만료 (잠금 해제는 이벤트 경로 하나)

```
취소: 클라 → 메인 → gRPC Cancel(매물, 판매자) → 경매장 Listed→Cancelled + t_event (한 트랜잭션)
만료: 경매장 타이머 → Listed→Expired + t_event
메인 릴레이 FetchEvents → trade Listed→Returned 조건부 + 판매자 우편(아이템 · 만료면 등록비 환급) → AckEvents
```

- `Reserved`는 취소할 수 없다(구매 진행 중).
- 취소 응답 직후 메인이 죽어도 이벤트가 경매장에 남아 있다 — 아이템이 영원히 잠기지 않는다.
- **등록비는 만료면 환급, 취소면 환급하지 않는다** — 방치하다 만료돼도 손해가 없고(P3), 등록·취소 반복은 비용을 문다.

### 4.4 검색

`C_AuctionSearchRequest` → 메인(유저별 토큰 버킷) → gRPC `Search` → 경매장 메모리 인덱스 → 응답.

- 이름 검색은 클라가 한다 — 이름을 TID 목록으로 바꿔 보낸다. 서버는 이름·로컬라이징을 모른다.
- 필터: 종류(자원/장비) · 분류(`ItemType`/`EquipKind`) · TID 목록 · 희귀도 범위 · 인챈트 등급 하한 ·
  **옵션 TID 전부 포함** · 단가 상한. 정렬은 **단가 오름차순** 하나.
- 인챈트 옵션은 수치가 아니라 **값이 고정된 옵션 TID**라 범위 비교가 없다 — 포함 검사만 한다.
- 페이지는 마지막으로 본 `(단가, 매물 ID)` 커서로 넘긴다(오프셋 금지 — 사이에 매물이 들고나면 중복·누락).
- 응답에 판매자를 싣지 않는다.

## 5. 경매장 내부

| 단위 | 하는 일 |
| --- | --- |
| `AuctionStore` | SQLite 접근. 전이는 전부 조건부 UPDATE |
| `ListingIndex` | 불변 스냅샷. 전체·분류별로 `(단가, 매물 ID)` 정렬 집합. 쓰기는 새 버전을 만들어 참조만 바꾼다 |
| `AuctionEngine` | **쓰기 채널 하나 · 소비자 하나.** 명령마다 SQLite 커밋 → 인덱스 반영. 만료·예약 타임아웃 청소도 같은 채널을 탄다 |
| `AuctionGrpcService` | gRPC ↔ 엔진 매핑만 |

- **커밋이 먼저, 인덱스가 나중**이다 — 디스크에 확정된 매물만 검색에 보인다.
- 채널 하나라 DB 커밋 순서와 인덱스 반영 순서가 어긋나지 않는다(어긋나면 매물이 검색에서 사라진 채 남는다).
- 인덱스의 불변성은 **메모리 구조를 지키는 용도**다. 거래 정합성은 SQLite 조건부 UPDATE가 판정한다 —
  방금 팔린 매물이 검색에 한순간 보여도 구매는 0행으로 튕긴다.
- 재시작하면 `Listed` 매물로 인덱스를 다시 만든 뒤에 리스너를 연다.
- 메모리 인덱스를 들고 있으므로 **경매장은 한 대만** 띄운다.

## 6. 복구와 대사

| 상황 | 결과 |
| --- | --- |
| 메인이 등록 커밋 후 죽음 | outbox가 재시작 후 보낸다 |
| 경매장이 `Register` 처리 후 ack 전에 죽음 | 재전송 → `listing_id` 유니크 → 이미 있음 = 성공 |
| 메인이 `Reserve` 후 정산 전에 죽음 | 경매장 예약 타임아웃 → `Listed` |
| 정산 커밋 후 `Confirm`이 늦음 | outbox 재전송 → 어느 상태든 `Sold` |
| 취소 응답 후 메인이 죽음 | 이벤트가 남아 있다 → 다음 `FetchEvents` |
| 경매장이 ack 후 커밋을 잃음(전원 장애) | **대사**가 잡는다 ↓ |

**대사(`GetListingStates`)**: 메인이 주기적으로 오래된 `Listed` 거래 중 **등록 메시지를 이미 보낸 것**을 묻는다.
경매장에 없거나(`NotFound`) 끝났는데(`Cancelled`·`Expired`) 메인이 아직 `Listed`면 반환한다(`NotFound`는 등록비 환급).
`Sold`인데 메인이 `Listed`면 있을 수 없는 상태라 로그만 남기고 손대지 않는다.

## 7. 수치 (테스트값 — 서버 상수 `AuctionRules`)

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 단가 하한 | `max(BasePrice, 1)` | 즉시 판매가 = 거래소 바닥(기획 3.1) |
| 단가 상한 | 하한 × 10 | 가격 밴드 배수 |
| 등록비 | 총액의 1%(최소 1) | 만료 환급 · 취소 미환급 |
| 판매 수수료 | 총액의 5% | 판매자 우편에서 뺀다 |
| 등록 건수 상한 | 20건 | 판매 중인 매물 수 |
| 등록 기간 | 48시간 | |
| 예약 타임아웃 | 2분 | gRPC 기한(3초)보다 훨씬 길게 |
| 검색 빈도 | 순간 5회 · 2초당 1회 회복 | 분당 약 30회 |

수치가 확정되면 엑셀로 옮긴다(기획 4장 "엑셀로 갈 것").

## 8. 입찰 확장 (미착수)

즉시구매에서 미리 해 둔 것: 상태머신(`Bidding` 추가 자리), **골드 hold**(`User.Auction`).
입찰은 메인이 hold 확보 → gRPC `Bid` → 거절이면 hold 해제, 밀려난 입찰자의 hold 해제는 경매장 이벤트로 받는다.
순서는 **새 hold 확보 → 경매장 갱신 → 이전 hold 해제**. 같은 유저의 증액은 기존 hold를 늘린다.
`Bid` 타임아웃은 입찰 ID로 결과를 조회해 정리한다.
