# 치트 (Cheat) — 개발·운영 명령

> 최종 업데이트: 2026-10-07 (응축 누적 `SetCondenseCount = 14` — T-130) · 2026-10-06 (시간 치트 `AdvanceTime = 12` · `ResetTime = 13` · 게임 시계 5장 — T-128 · 이슈 #48) · 2026-10-06 (특성 레벨 `SetTraitLevel = 11` — T-115) · 상태: **기획·서버 구현 완료(장비 지급 `GiveEquip = 8` 포함 · 지급 3종 창고 한도 검사) · 클라 입력 UI 미착수**

테스트와 운영이 유저 상태를 바로 바꾸는 통로다. 게임 규칙이 아니라 **개발 인프라**라 `GameDesign/design`이 아니라 여기 둔다.
게임 규칙(경험치·해금·재화)은 건드리지 않고 **기존 지급 함수를 그대로 부른다** — 치트가 통하는 경로와 게임이 통하는 경로가 같아야 치트로 검증한 것이 실제와 같다.

---

## 1. 확정 사항

| # | 항목 | 확정 내용 |
| --- | --- | --- |
| 1 | **권한** | `t_user.admin_level ≥ CheatAdminLevel`. 아니면 `NoPermission`으로 거절하고 아무것도 바꾸지 않는다. ⚠️ **개발 기간엔 `CheatAdminLevel = 0`** — 모든 계정이 통과한다(권한 테스트는 Skip). 배포 전 1로 되돌린다 |
| 2 | **한 패킷** | `C_CheatRequest { ECheatCommand Command, long Arg1, long Arg2 }` / `S_CheatResponse { Result, Command, Message }` |
| 3 | **명령은 enum** | `ECheatCommand`. 문자열 파싱을 두지 않는다 — 오타가 컴파일에서 잡힌다. **뒤에만 추가** |
| 4 | **기존 경로 재사용** | `GainGold` · `TrySpendGold` · `GainItem` · `GrantGachaCharacters` · `GrantCharacterExp` · `SettleWorkStation` · `GrantUnlock`. 치트 전용 지급 코드를 만들지 않는다 |
| 5 | **결과는 기존 푸시로** | 재화·인벤토리·캐릭터·슬롯이 바뀌면 각자의 동기화 패킷이 나간다. 응답의 `Message`는 로그용 한 줄이다 |
| 6 | **전부 기록** | 성공·실패 모두 `ServerLog.Warn("치트", …)`. 운영에서 누가 무엇을 했는지가 남아야 한다 |
| 7 | **실행 시각은 호출자가 넘긴다** | `ExecuteCheat(req, now)`. 테스트가 시각을 고정한다 (저장소 규약) |

## 2. 명령

| `ECheatCommand` | `Arg1` | `Arg2` | 동작 | 거절 |
| --- | --- | --- | --- | --- |
| `GiveGold = 1` | 금액 | — | 양수면 `GainGold`, 음수면 `TrySpendGold(-Arg1)` | 0 → `InvalidCheatArgs` · 잔액 부족 → `NotEnoughCurrency` |
| ~~`GiveDia = 2`~~ | — | — | **폐지**(2026-09-28, 다이아 폐지 #41). 번호는 재사용하지 않는다 | — |
| `GiveItem = 3` | `ItemTID` | 개수 (1~) | `AddItem` — 저장 + `S_UpdateItemResponse` 푸시. **인챈트 큐브(100015 · 100018)도 이것으로 준다** — 평범한 아이템이라 인챈트 전용 명령을 두지 않는다 | 테이블에 없는 TID · 개수 ≤ 0 → `InvalidCheatArgs` · 새 종류인데 자원 칸이 가득 → `StorageFull` |

| `Settle = 6` | 판정 횟수 (1~100, 0이면 1) | — | 가동 중인 슬롯마다 판정 N회분 작업량을 얹고 `SettleWorkStation(now)` — 쌓인 진행도만 정산하면 스케줄러(0.1초)가 먼저 가져가 늘 0개라서 | 100 초과 → `InvalidCheatArgs` |
| `Unlock = 7` | `UnlockTID` | — | `GrantUnlock` — 조건·차감 없이 열고, 기록·`S_UnlockResponse`·슬롯 스냅샷까지 유저 해금과 같다. **특성은 열지 않는다** — 레벨형 특성(T-108) 이후 특성은 `UnlockTable`에 없다. 특성은 `SetTraitLevel`로 | 테이블에 없는 TID → `InvalidCheatArgs` · 이미 열림 → `AlreadyUnlocked` |

| `SendMail = 10` | `MailTemplateTID` | 받는 UID (0이면 전체) | `SendOperationMail` — 운영툴과 같은 발송 경로. 개인: 접속 중이면 `S_MailArrivedResponse`, 아니면 다음 로그인 목록. 전체: 템플릿 `PeriodDays` 동안 로그인한 계정 + 발송 순간 접속자 → [우편](../../GameDesign/design/mail/README.md) | 없는 템플릿 · 음수 UID · 전체인데 `PeriodDays = 0` → `InvalidCheatArgs` |
| `SetTraitLevel = 11` | `UserTraitTID` (0이면 전 특성) | 레벨 | 계정 레벨 조건·포인트 없이 특성 레벨을 정한다. 특성마다 **기본~최대 레벨로 자른다** — `0, 99`면 전부 최대, `0, 0`이면 전부 기본. 속도·산출량 특성이 바뀌면 **바꾸기 전에 정산**하고 속도를 다시 매긴다(정상 경로 `TryLearnTrait`와 같다). 바뀐 것이 있으면 `S_UserTraitListResponse`를 다시 보낸다. 포인트는 돌려주지 않는다 · 산업 개척을 내려도 **이미 그 레벨로 돌던 슬롯은 그대로 돈다**(다시 배치할 때 거절된다) | 없는 TID · 음수 레벨 → `InvalidCheatArgs` |
| `AdvanceTime = 12` | 넘길 초 (1~365일, 누적) | — | **서버 전체**의 게임 시계를 앞으로 넘긴다(5장). 접속 중인 모두에게 슬롯 스냅샷·`S_ServerTimeResponse`를 다시 보내고 경매장 릴레이를 깨운다. **채취는 쌓이지 않는다** — 슬롯 기준 시각도 같이 민다. 판정을 당기려면 `Settle` | 0 이하 · 1년 초과 → `InvalidCheatArgs` |
| `ResetTime = 13` | — | — | 오프셋을 0으로. 슬롯 기준 시각도 같은 만큼 되돌린다. ⚠️ **넘긴 동안 저장된 시각(우편 도착·경매 등록·만료)은 미래로 남는다** — 그 우편은 되돌린 뒤 7일+넘긴 시간이 지나야 지워진다 | 없음(이미 0이면 `Ok`만) |

- 값 대역: `EResultCode` **400~ 치트** — `NoPermission = 400` · `InvalidCheatCommand = 401` · `InvalidCheatArgs = 402`.
- `Arg`는 `long`이다. 골드가 `long`이고, 개체 PK도 `long`이라 하나의 타입으로 전부 나른다.

## 4. 두지 않는 것

- **명령줄 파서** — `"gold 100"` 같은 문자열을 서버가 해석하지 않는다. 클라 입력창이 문자열을 받더라도 enum·숫자로 바꿔 보내는 것은 클라 몫이다.
- **치트 전용 저장 경로** — 지급 함수가 각자 저장한다. 치트가 DB에 직접 쓰는 일은 없다.
- **운영 빌드에서의 차단 스위치** — `admin_level`이 곧 스위치다. 별도 설정을 두지 않는다.

## 5. 게임 시계 — 시간 치트의 바탕 (T-128 · 이슈 #48)

서버의 "지금"은 **`GameClock`**(`Server/WSGameServer/Common/GameClock.cs`) 하나에서 나온다 — 실제 시각 + 오프셋.
시간 치트는 오프셋만 움직인다. 기다려야 결과가 나오는 기능(경매 만료 · 거래소 전일 평균 · 받은 우편 7일 삭제 · 전체 우편 기간)을 기다리지 않고 시험하기 위해서다.

| 따른다 (게임 시계) | 따르지 않는다 (실제 시간) |
| --- | --- |
| 패킷 핸들러가 넘기는 `now` 전부 · 채취 스케줄러 · 경매 릴레이 · 로그인·종료 시각 | 세션 감시(`SessionWatchdog`) · gRPC 기한 · 로그 시각 · 구매 ID 발급(`AuctionService`) |
| 경매장의 "지금"(`GameTimeProvider`) — 만료 · 예약 해제 · 전일 평균의 하루 경계 | 경매장 청소 주기(타이머) |

- **오프셋은 서버 전체 하나다.** 경매가 공용이라 계정별 시계는 의미가 없다. **저장하지 않는다** — 재시작하면 0이다.
- **경매장은 메인 릴레이가 맞춘다** — `SetClockOffset` RPC를 바퀴(1초)마다 보낸다. 바뀔 때만 보내면 경매장이 재시작해 0으로 돌아간 것을 메인이 알 길이 없다. 맞추지 못한 바퀴는 전송·이벤트도 건너뛴다.
- **채취는 쌓이지 않는다**(2026-10-06 결정) — 넘기는 순간 접속 중인 모든 슬롯의 기준 시각을 같이 민다. 진행 중이던 조각은 남는다. 오프라인 누적은 지금 없다(로그인 때 슬롯이 "지금부터" 시작한다).
- **우편 시각은 코드가 넘긴다** — `received_at`·`claimed_at`·`ends_at`을 SQL `datetime('now')` 기본값에 기대지 않는다. 받은 우편 7일 삭제는 **로그인 때** 판정하므로 넘긴 뒤 다시 접속해야 보인다.
- 검색 빈도 제한(`TokenBucket`)은 게임 시각을 받지만, 시계가 뒤로 가면(`ResetTime`) 기준을 당겨 막히지 않는다.

**새 시간 기능을 만들 때** — "지금"은 핸들러·타이머가 넘긴 `now`(= 게임 시계)에서만 받는다. `DateTime.UtcNow`를 게임 로직에 직접 쓰지 않는다.
테스트는 시각을 고정해 넘기거나 `FakeTimeProvider`로 `GameClock`을 만든다.
