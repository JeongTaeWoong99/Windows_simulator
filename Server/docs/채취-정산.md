# 채취 정산 — 구현 근거

> 최종 업데이트: 2026-09-16 · 상태: **구현 완료 · 산업 레벨 저장·해금 검증은 T-017**

작업슬롯 정산 파이프라인(`WorkStationSlot` → `WorkSpeed` → `GatheringScheduler` → `User.WorkStation` → `WorkStationSlotInfo`)의
설계 근거다. **"왜 주기가 아니라 속도인가"·정산 의사코드·시계 전진 규칙**은 기획 문서가 원본이다 →
[`workslot/README.md`](../../GameDesign/design/workslot/README.md) 2~3장. 여기는 그 규칙을 코드로 옮길 때 정한
**단위·상태 경계·함정**만 적는다. 코드 주석은 1~2줄과 이 문서 링크만 둔다.

---

## 1. 상태 경계 — 무엇을 저장하고 무엇을 버리는가 (`WorkStationSlot`)

| 필드 | 성격 | 이유 |
| --- | --- | --- |
| `Industry` · `IndustryLevel` · `CharacterId` | **DB 저장** | "어떤 산업에 누구를 배치했는가"라는 **설정**. 슬롯 행이 남기는 것은 이것뿐이다 |
| `LastTickAt` · `ProgressUnits` | **세션 지역** | 오프라인 진행이 폐지됐으므로(게임기획코어 P2) 저장할 진행도가 없다. 로그인 시 접속 시각·0에서 시작하고 접속이 끊기면 조각은 버려진다 |
| `CurrentWorkSpeed` · `JudgeCostUnits` | **세션 지역(재계산)** | 캐릭터 스탯·버프·레벨 테이블에서 접속할 때마다 다시 계산한다. 저장하면 원본(테이블)과 사본이 둘이 된다 |

- `IndustryLevel`은 DB 저장·패킷·해금 검증이 미구현이라(T-017) 지금은 항상 `DefaultIndustryLevel`(1)로 적재된다.
- 정산(`SettleWorkStation`)은 슬롯 자체를 저장하지 않는다 — 정산으로 바뀌는 영속 상태가 없다. 지급된 아이템은 `GainItem`이 각자 저장한다.

## 2. 단위 — 나눗셈 없는 정수 누적

| 상수 | 값 | 의미 |
| --- | --- | --- |
| `WorkSpeedScale` | 1000 | 작업속도의 정수 표현. **1000 = 1.0배(천분율)**. 이 프로젝트에서 "작업속도"라고 적힌 정수는 전부 이 단위다 |
| `BaseCycleSeconds` | 30 | 속도 1.0배일 때 판정 1회에 걸리는 기준 시간 |
| `JudgeCost` | 30 × 1000ms × 1000 = 30,000,000 | **Lv1 판정 비용**. `경과ms × 속도천분율`의 차원과 같다 |

`ProgressUnits += 경과ms × CurrentWorkSpeed`로 누적하면 **나눗셈이 한 번도 없다.**
나눗셈을 끼우면 정산할 때마다 1 미만이 잘려 나가고, 푸시 주기가 짧을수록 손실이 커진다.
실제 판정 비용은 인스턴스의 `JudgeCostUnits`(레벨별 `IndustryLevelTable.RequiredScore` × 1000)이며 Lv1이 정확히 `JudgeCost`다.
×1000이 서버 몫인 이유는 [데이터 카탈로그](데이터-카탈로그.md) 2장.

### 자투리는 초가 아니라 작업량으로 든다

`ProgressUnits`를 초 단위로 두면 속도가 바뀔 때 "이 자투리는 몇 판정어치인가"가 달라져 재환산이 필요하고,
그 틈이 곧 익스플로잇이 된다(30초 주기의 15초 = 0.5판정, 20초 주기 = 0.75판정). 작업량으로 두면 주기가 바뀌어도 값이 그대로다.

## 3. 불변식 — 순서와 하한

| 규칙 | 깨지면 |
| --- | --- |
| **`Assign`·`ApplyWorkSpeed` 호출 전에 반드시 정산한다** | 아직 정산되지 않은 이전 구간이 새 설정·새 속도로 계산된다(소급). 정산 → 변경 순서를 지키면 한 구간의 속도는 항상 하나다 |
| **`Assign`은 진행 조각을 버린다** (`ProgressUnits = 0`) | 이월하면 "산업을 계속 갈아타며 조각을 모으는" 악용이 된다. 레벨만 바뀌고 `JudgeCostUnits`가 남아도 싸게 쌓아 비싸게 쓰는 구멍이라 둘을 함께 바꾼다 |
| **비활성 슬롯은 시계만 따라간다** (`LastTickAt = now`) | 비어 있는 동안 시간이 쌓이면 캐릭터를 꽂는 순간 한꺼번에 터진다 |
| **`MinWorkSpeed = 1`** | 0이면 `TimeUntilNextJudge`에서 0으로 나눈다. "채취 정지"는 속도 0이 아니라 **배치를 비우는 것**으로 표현한다. `WorkSpeed.Multiply`가 0 이하 배수를 무시하는 것도 같은 이유 — 보정 하나가 슬롯을 조용히 멈춰 세우면 안 된다 |
| **`AssignWorkStation`은 레벨 하한(1 미만)을 따로 막는다** | 0·음수는 "열린 레벨 이하" 비교를 그냥 통과한다. 클라가 보낸 레벨이라 해금 검증도 서버가 한다(P4) |

### 정산을 부르는 시점 (`User.SettleWorkStation`)

| 시점 | `notify` | 비고 |
| --- | --- | --- |
| 슬롯 배치 변경 · 속도 재계산 | true | 해당 슬롯뿐 아니라 전체를 정리해 둔다 |
| 주기 푸시(`GatheringScheduler`) | true | |
| 접속 종료 | **false** | 세션이 끊겨 보낼 곳이 없다. **아이템 지급·DB 저장은 그대로 수행한다** — 접속 중 완성된 판정은 정당하게 번 것이다 |
| 로그인 | **부르지 않는다** | 오프라인 진행이 없어 정산할 구간이 없다. 속도 재계산은 `notify=false`로 — 직후 `SendWorkStationSlots`가 어차피 보낸다 |

## 4. 밀리초 정밀도 (이슈 #11)

- **시계는 `now`가 아니라 정산한 만큼(`elapsedMs`)만 전진한다.** `elapsedMs`가 버림이라 `now`까지 밀면 매 틱 1ms 미만이 사라지고,
  손실이 틱 수에 비례해 푸시가 촘촘할수록 서버가 느려진다. 남긴 자투리는 다음 구간의 `elapsedMs`에 포함된다.
  그래서 `LastTickAt`은 현재 시각보다 1ms 미만 뒤처져 있을 수 있다.
- **`ToInfo`는 `LastTickAt`을 밀리초까지 보낸다.** `LastTickAtUnixMs`와 `ProgressUnits`는 같은 순간을 가리켜야 한다. 초로 자르면
  클라이언트가 그 소수부만큼 일을 더 한 것으로 계산해 카운트다운이 먼저 0에 닿는다.
- 테스트: `Server/WSGameServer.Tests/WorkStation/WorkStationSlotTest.cs` "밀리초 정밀도" 절.

## 5. 작업속도 합성 (`WorkSpeed` · `User.ResolveSlotSpeed`)

**속도 = 적성기본값 × (1 + Σ가산) × Π승산** (기획 workslot 3.4)

| 항 | 무엇 | 왜 |
| --- | --- | --- |
| **기본값** | 캐릭터의 해당 산업 적성을 `WorkSpeedTable`로 변환한 값 | 나머지 보정은 전부 이 기본값 기준으로 말한다. `WorkSpeedTable.BaseWorkSpeedPermille`은 **입력**, `CurrentWorkSpeed`는 **결과** |
| **가산(Add)** | 특성 패시브 · 액티브 부스트 · 장비 (아직 미작성) | "+25%"는 기본값의 25%. 서로 곱하면 +25% 둘이 +56%가 되고 항을 추가할 때마다 밸런스를 전부 다시 잡아야 한다. 가산이면 보정원 개수와 무관하게 각 몫이 적힌 그대로다 |
| **승산(Multiply)** | 결과 전체에 얹히는 배수. 현재 `Global.GatherSpeedMultiplier` 하나 | 가산 전체를 함께 부풀려 영향이 비교가 안 된다. **새 보정은 기본이 가산, 승산은 의도적으로 고를 때만** |

- `WorkSpeed`는 값 타입 누산기다. 모으는 것과 적용하는 것을 분리해 실제 계산은 `Resolve`에서 한 번뿐이고, 가산은 합·승산은 곱이라 호출 순서가 결과를 바꾸지 않는다.
- `_mulRate == 0`은 "승산 없음(×1.0)"이다. `Multiply`가 0 이하를 거부하므로 0이 실제 배수로 들어올 일이 없다.
- `Resolve`에서만 실수 연산이 일어나고 `int`로 끝난다. 가산은 `(1000 + Σ)`를 먼저 곱한 뒤 나눈다(먼저 나누면 1 미만이 잘린다). 감소가 겹쳐 -100%를 넘으면 0으로 막는다.
- **속도에 관여하는 것은 전부 `ResolveSlotSpeed`로 모은다.** 누적식(`ConsumeJudgeCount`)에 배수를 곱하면 아직 정산되지 않은 구간에까지 소급된다. 이 함수만 "정산 → ApplyWorkSpeed" 순서를 타므로 여기서 곱하면 소급이 불가능하다.

### 전역 배수 `Global.GatherSpeedMultiplier`

기획 수치(`BaseCycleSeconds` = 30초, `WorkSpeedTable`)는 그대로 두고 서버 전체를 이 값 하나로 당긴다.
기획 데이터를 확인 편의로 고치면 엑셀이 진짜 밸런스인지 테스트용 값인지 구분이 사라진다.
현재 **6.0배**(기준 슬롯이 5초에 한 번 판정). ⚠️ 배포 전에 1.0으로 되돌린다 — 1.0이 아니면 시작 시 경고를 찍고,
[세션 감시](세션-감시.md)의 "부당 구간이 판정 1회를 못 채운다" 보장도 깨진다(T-004).

## 6. 푸시 스케줄러 (`GatheringScheduler`)

- **초당 수십 번 도는 루프를 두지 않는다.** 판정 간격이 수십 초인데 30fps로 깨우면 대부분의 틱이 헛돌고, 로직 스레드가 단일이라 그 낭비가 패킷 처리를 밀어낸다.
  진행도는 시각의 함수라 깨어난 시점에 경과분을 한 번에 계산하면 된다. 타이머가 늦게 돌아도 결과는 같다.
- `Interval`(0.1초)은 **푸시 해상도**이지 채취 주기가 아니다. 슬롯마다 주기가 달라 맞출 단일 주기가 없다.
  정산량은 경과 시각이 정하므로 얼마로 잡든 개수는 같고, "잡혔다"가 최대 이만큼 늦게 도착할 뿐이다.
- **0.1초인 이유** — 1초면 카운트다운이 0에 닿고도 결과가 최대 1초 늦게 와서 "슬라이더가 다 찼는데 아무 일도 없는" 구간이 보인다(이슈 #11). 30초 주기에 그보다 촘촘한 정밀도는 의미가 없다.
- ⚠️ 더 줄이려면 4장의 밀리초 이월이 전제다. 시계를 `now`까지 밀면 손실이 틱 수에 비례한다.
- `Tick(now, users)`가 시각·대상을 인자로 받는 이유: 재화가 생기는 권위 루프라 밖에서 불러야 검증이 된다. 타이머 스레드는 로직 스레드로 넘기기만 한다.

## 7. 패킷 `WorkStationSlotInfo` — 주기 대신 진행도·속도·비용

클라이언트는 `남은시간 = (비용 - 진행도 - 경과 × 속도) / 속도`로 카운트다운을 직접 구한다. 카운트다운은 연출이고 개수는 서버가 정한다.
"주기 N초"를 내려보내지 않는 이유는 슬롯마다 주기가 달라 고정값이 없고, 주기 규칙이 바뀌어도 클라를 고치지 않아도 되기 때문이다.
`LastTickAtUnixMs`가 밀리초인 이유는 4장.
