# 세션 감시 — 무응답 판정과 좀비 세션

> 최종 업데이트: 2026-09-16 · 상태: **구현 완료 (이슈 #10 · #19)**

`Global.SessionIdleTimeout`과 `SessionWatchdog`의 설계 근거다. 코드 주석은 1~2줄과 이 문서 링크만 둔다.

---

## 1. 왜 감시자가 필요한가 (이슈 #10)

TCP는 끊김을 알려 주지 않는다. FIN/RST 없이 사라지는 종료(Unity 에디터 플레이 중지·절전·랜선 뽑기)에서는
`ReceiveAsync`가 영원히 대기하고 세션이 접속 중으로 남는다. 그동안 `GatheringScheduler`가 정산·지급을 계속하므로
**좀비 유저는 폐지한 오프라인 적립을 되살린다.**

- **송신은 살아 있음의 증거가 아니다.** `Send`는 소켓 쓰기가 아니라 큐 적재라 소켓이 죽어도 1024개가 찰 때까지 성공한다. 그래서 **수신 시각**만 본다.
- `GatheringScheduler`와 타이머를 합치지 않았다. 채취 정산과 세션 정리는 관심사도 주기도 다르다(0.1초 vs 5초).
- 타이머 스레드는 로직 스레드로 넘기기만 한다. 세션을 끊으면 `Disconnected`가 발화해 `User.Destroy`로 이어진다.
- `Sweep` 한 번이 실패해도 감시를 멈추지 않는다 — 멈추면 좀비가 영구히 남는다.

## 2. 값 두 개 — 판정 시간과 검사 주기

| 값 | 현재 | 의미 |
| --- | --- | --- |
| `Global.SessionIdleTimeout` | 15초 | **무응답 판정 시간.** 이만큼 아무 바이트도 못 받은 세션은 끊는다 |
| `SessionWatchdog.Interval` | 5초 | **검사 주기.** 얼마나 자주 들여다볼지일 뿐이다. 실제 끊김은 최대 이만큼 늦어진다 |
| 클라 `PingManager.PingIntervalSeconds` | 5초 | 클라이언트가 `C_PingRequest`를 보내는 주기 |

### 🔒 불변식 — 핑 주기 ≤ 판정 시간 ÷ 3 (이슈 #19)

판정 시간과 클라 핑 주기는 각각 정하는 값이 아니라 **한 쌍**이다. 한때 판정을 5초로 내려 핑 주기(5초)와 같아진 적이 있는데,
여유가 0이 되어 **프레임 오버슈트 몇 ms 때문에 멀쩡한 세션이 무작위로 끊겼다.** 두 값 중 하나만 고치지 않는다.
현재 값은 핑을 세 번 연속 놓쳐야 끊긴다.

### ⚠️ 검사 주기를 늘려 무응답 끊김을 줄이려 하지 않는다

검사가 드물어지면 증상의 빈도만 낮아지고 **좀비 세션의 수명은 오히려 길어진다**(판정 시간 + 검사 지연).
여유를 만드는 값은 `SessionIdleTimeout`이다. 이슈 #19에서 실제로 한 번 헛짚은 자리다.

---

## 3. 판정 시간이 곧 "공짜로 얻는 최대 오프라인 시간"

접속 판정이 재화 생성 조건이라(게임기획코어 P2), 끊긴 걸 서버가 모르는 구간만큼 부당 적립이 생긴다.
채취 기준 주기(`WorkStationSlot.BaseCycleSeconds` = 30초)보다 짧게 두어 **부당 구간이 판정 1회를 못 채우게** 했다.

⚠️ `Global.GatherSpeedMultiplier`가 1.0이 아니면 실효 주기가 그만큼 짧아져 이 보장이 깨진다. 배포 전에 배수를 되돌린다(T-004).
