클라 왼쪽 열 **인벤토리**(자원·캐릭터·장비 탭)와, 거래 열의 **창고** 탭([T-101](../../tasks/archive/T-101-인벤토리개명거래탭.md))을

## 1. 결정 (2026-10-01)

| 항목 | 결정 |
| --- | --- |
| 창고의 역할 | **놓인 자리일 뿐이다** (2026-10-15 결정 · T-164). 창고의 것도 배치·장착·큐브·응축·잠금·판매·경매·상자 개봉에 그대로 쓰고, 배치·착용 중인 것도 맡긴다. 실수를 막는 것은 잠금(T-137)이다. ~~2026-10-01: 꺼내야 쓰는 보관소~~ |
| 자원 소모 | 인벤토리에서 먼저, 모자란 만큼 창고에서 뺀다(`Inventory.TryRemoveAcross`). 합쳐도 모자라면 아무것도 빼지 않는다 |
| 보관 대상 | 자원 · 캐릭터 · 장비 — 인벤토리와 같은 3탭 |
| 인벤토리 칸 수 | 탭마다 **50칸** (`Constants.StorageCapacity`) |
| 창고 칸 수 | 탭마다 **고정 50칸**(`Constants.WarehouseCapacity` · 클라는 5×10). 골드 페이지 확장은 **보류**(2026-10-06 이슈 #58) |
| 이동 | **놓은 칸에 넣는다** — 비었으면 이동, 차 있으면 스왑 (2026-10-06 이슈 #58) |
| 자원 묶음 | **칸 하나 = 묶음 하나**. `ItemTable.MaxStack`은 **칸 하나의 상한**이고, 차면 빈 칸에 이어 쌓는다 — 같은 자원이 여러 칸에 있을 수 있다. 버리는 것은 **칸이 전부 찼을 때뿐**(2026-10-15 · T-160). ~~2026-10-14: 종류 하나 = 칸 하나, MaxStack은 보유 총량~~ |
| 자원 지급 | ① **창고의 덜 찬 같은 자원 칸**(칸 번호 앞부터) MaxStack까지 → ② 인벤토리의 덜 찬 같은 자원 칸 → ③ 인벤토리 첫 빈 칸부터 새 묶음. **창고 빈 칸에는 새 묶음을 만들지 않는다** — 창고는 플레이어가 고른 것만 둔다(2026-10-24 · T-175). 칸 수 검사(`HasStorageFor`)는 창고·인벤토리 사본에 같은 순서로 넣어 보고 판정한다 |
| 칸 정리 | **[합치기]** 한 보관함 안 같은 자원을 칸 순서 그대로 앞 칸부터 MaxStack까지 채우고 비게 된 뒤 칸은 비운다 · **[창고에 쌓기]** 창고에 이미 있는 자원만 인벤토리 → 창고 같은 자원 칸으로, 창고 칸이 차서 남는 몫은 인벤토리에 둔다 (2026-10-24 · T-175) |
| 자원 차감 | 요청은 TID·수량 그대로. 서버가 **덜 찬 칸부터** 뺀다 — 칸이 빨리 빈다 |
| 자원 이동 | **수량을 지정한다**. 놓은 칸만 본다 — 같은 자원 칸이면 MaxStack까지 합치고 남는 것은 원래 칸에, 다른 자원 칸이면 **전량일 때만 스왑**·일부면 거절. 격자 안 자리 이동도 같은 자원 칸이면 합친다 (2026-10-14 · T-160) |
| 칸 위치 | 인벤토리·창고 **둘 다** 서버가 칸 번호를 들고, 정렬·자리 이동을 같은 패킷으로 한다 |
| 50칸 초과 기존 데이터 | **처리하지 않는다** — 지금 DB는 테스트 데이터다 |

### 고르지 않은 안

- **창고 전용 테이블** — 개체가 옮겨질 때마다 행이 테이블 사이를 오가 착용·경매 잠금 참조가 흔들리고, 칸·정렬 코드가 두 벌이 된다.
- **칸 배치 테이블 분리**(`t_user_slot`) — 자원이 두 곳에 나뉘는 문제는 어차피 자원 테이블이 풀어야 하고, 고아 칸 정합성만 늘어난다.

## 2. 칸 모델

칸 격자는 **보관함 × 탭**으로 6개다.

```
EContainer  { Inventory = 0, Warehouse = 1 }
EStorageTab { Resource = 0, Character = 1, Equip = 2 }
```

칸 번호는 격자 안에서 0부터다. 격자의 항목 키는 캐릭터면 `CharacterId`, 장비면 `EquipId`다(패킷에서는 `long Key` 하나로 싣는다).
**자원은 칸 번호가 곧 키다**(T-160) — 같은 자원이 여러 칸에 있을 수 있어 `ItemId`로는 칸을 가를 수 없다.

| 격자 | 칸 수 |
| --- | --- |
| 인벤토리 (탭마다) | `Constants.StorageCapacity` (50) |
| 창고 (탭마다) | `Constants.WarehouseCapacity` (50) |

## 3. DB

| 테이블 | 변경 |
| --- | --- |
| `t_user_inventory` | PK `(user_id, container, slot)` — 칸 하나에 행 하나, 같은 `item_id`가 여러 행일 수 있다(마이그레이션 `0007` · T-160). ~~T-058: PK `(user_id, container, item_id)`~~ |
| `t_character` | `container`·`slot` 추가. 기존 행은 `container = 0`, 칸은 `character_id` 순으로 0부터 |
| `t_user_equip` | `container` 추가. 칸은 기존 `slot_position`을 그대로 쓴다 |

**캐릭터·장비는 칸 중복을 DB 제약으로 막지 않는다.** 메모리가 원천이고, 교환은 두 행을 함께 고치는 저장이라
문장 하나하나에 걸리는 유니크 제약은 중간 상태에서 터진다. 중복은 메모리(`StorageSlots`로만 칸을 정한다)가 막는다.
**자원은 칸이 PK라 칸째 쓴다** — 바뀐 칸마다 확정 상태를 UPSERT(0이면 DELETE)하므로 교환 중에도 키가 겹치지 않는다.
쓰는 곳은 `SaveItemChangesRepository.WriteAsync` 하나다(지급·차감·판매·경매·창고 이동·자리 이동·정렬).

DDL은 `sqlite-sql-creator` 규칙(STRICT·주석)을 따른다. 테스트용 `SqliteFixture`의 DDL도 같이 고친다.

## 4. 메모리

### 칸은 개체가 든다 · 계산은 `StorageSlots`

칸 번호는 **개체 자신이 든다** — `Item.Slot`, `Character.Slot`, `Equip.SlotPosition`(이미 있다).
키 → 칸 사본을 따로 두면 두 곳이 어긋난다.
칸 계산은 상태 없는 순수 함수 `StorageSlots`가 한다. **Repository·DTO를 모른다.**

| 함수 | 설명 |
| --- | --- |
| `FirstFree(used)` | 첫 빈 칸. 지급 대기(PK 발급 전) 칸도 `used`에 넣어 찬 것으로 본다 |
| `Move(occupied, from, to)` | 빈 칸이면 옮기고 차 있으면 교환. 바뀐 `(Key, Slot)` 목록을 돌려준다 |
| `Renumber(keysInOrder)` | 정렬된 키를 0부터 촘촘히 매긴 `(Key, Slot)` 목록 |

장비의 `NextFreeEquipPosition`은 `FirstFree`를 쓴다. 캐릭터도 장비처럼 지급 대기 칸(`_pendingCharacterSlots`)을 둔다.

### 보관함 = 별도 묶음

창고의 것은 **인벤토리와 다른 컬렉션**에 둔다 — 창고용 `Inventory` 인스턴스(`Warehouse`), `_warehouseCharacters`, `_warehouseEquips` (`User.Warehouse.cs`).
로그인은 `container`를 함께 읽어 둘로 가른다. 창고에만 캐릭터가 있어도 시작 캐릭터를 다시 주지 않는다.
채취·판매·배치·장착·경매·한도 검사(`HasStorageFor`)는 지금처럼 인벤토리 쪽만 본다.
**창고 물건이 "쓸 수 없음"은 검사를 더해서가 아니라 기존 코드가 보지 못해서 성립한다.**

## 5. 규칙

### 칸 배정

- **캐릭터·장비는 언제나 인벤토리의 첫 빈 칸**으로 들어온다 — 채취·뽑기·우편·치트.
- **자원은 창고의 덜 찬 같은 자원 칸부터** 채우고, 남는 몫만 인벤토리로 간다(T-175). 창고에 없는 자원이 창고에 새로 생기는 길은 이동 요청뿐이다.
  창고에서 경매에 올린 개체도 반환·구매로 우편에서 받으면 인벤토리로 들어온다(`UnlockEquipAsync`·`UnlockCharacterAsync`가 `container = 0`).
- 인벤토리에서도 이미 가진 자원은 **덜 찬 칸부터 MaxStack까지** 채우고, 남으면 첫 빈 칸에 새 묶음을 놓는다(T-160).
- 수량이 0이 되면 행을 지우고 칸을 비운다 (지금 `Inventory`가 이미 그렇게 한다).
- 지급 대기 중인 캐릭터도 장비처럼 칸을 예약한다 — 응답 전 연속 뽑기가 같은 칸을 잡지 않게.

### 정렬

정렬하면 격자 전체를 **빈 칸 없이 0부터** 다시 매긴다. 자원은 그 전에 **같은 자원의 칸들을 합쳐**
MaxStack짜리 묶음 + 나머지 하나로 다시 나눈다(`StorageSort.CompactStacks` · T-160) — 찬 묶음이 앞에 선다. 규칙은 **클라 임시 정렬
(`InventorySlotSource.CompareByRule`·탭별 `CompareForSort`)과 같아야 한다** — 다르면 서버 정렬을 켠 순간 순서가 바뀐다.

1. **나가 있는 것은 맨 뒤** — 배치 중인 캐릭터 · 장착 중인 장비. **방향과 무관하다.**
2. 고른 기준(`SortKey`)으로 비교한다 — `Rarity`는 0(아래 탭 규칙만), `Name`은 표시 이름 서수 비교(`CompareOrdinal`), `Count`는 보유 수량 많은 순.
3. 동점이면 탭 규칙으로 끝까지 가른다 (동점이 남지 않게 마지막은 키):

| 탭 | 탭 규칙 |
| --- | --- |
| 자원 | 등급↓ → `ItemType`↑ → TID↑ → 묶음 순번↑ |
| 캐릭터 | 등급↓ → TID↑ → 개체 ID↑ |
| 장비 | 테이블에 없는 TID는 뒤 → 등급↓ → `EquipKind`↑ → `Industry`↑ → TID↑ → 개체 ID↑ |

4. 방향이 `Ascending`이면 **2~3의 결과 전체를 뒤집는다** (1은 뒤집지 않는다). 기본은 `Descending`(규칙 그대로).

`Count`는 자원 탭만 된다 — 캐릭터·장비 탭에서 오면 거절한다. 이름은 서버 GameData의 `Name`이다 — 출처는 [T-085](../../tasks/T-085-공용상수소유권.md)가 정해지면 따른다.

### 창고 이동

보내는 칸(`FromSlot`)을 반대 보관함의 놓은 칸(`ToSlot`)으로 옮긴다. 탭은 양쪽이 같다 — 다른 종류가 섞일 수 없다.

| 경우 | 처리 |
| --- | --- |
| 놓은 칸이 빔 | 그 칸으로 이동 |
| 놓은 칸이 참 (캐릭터·장비) | 스왑 — 받는 쪽 개체가 보내는 칸으로 |
| 자원 — 놓은 칸이 같은 자원 | MaxStack까지 합치고 **넘치는 몫은 원래 칸에 남긴다**. 놓은 칸이 이미 꽉 찼으면 거절 `StorageOverMaxStack` (T-160) |
| 자원 — 받는 쪽 다른 칸에 같은 자원 | 끌려가지 않는다 — 놓은 칸에 새 묶음이 선다 (T-160 · 전에는 그 칸에 합쳤다) |
| 자원 — 다른 자원 칸에 전량 | 두 칸의 묶음을 맞바꾼다 |
| 자원 — 다른 자원 칸에 일부 | 거절 `WarehousePartialSwap` |
| 배치 중 캐릭터 · 장비를 입은 캐릭터 · 장착 중 장비 | **그대로 옮긴다** — 슬롯·착용 매핑은 개체 id를 가리키므로 배치·착용이 유지된다(T-164) |
| 놓은 칸이 지급 대기 칸(인벤토리) | 거절 `StorageSlotPending` |

칸 수 안의 칸에만 놓으므로 "가득 참"은 생기지 않는다. 저장은 양쪽 행을 **한 트랜잭션**으로 쓴다(`WarehouseTransferRepository`).

## 6. 패킷

### 기존 DTO에 칸을 싣는다

| DTO | 추가 |
| --- | --- |
| `ItemInfo` · `ItemChangeInfo` | `Container`, `Slot` |
| `CharacterInfo` | `Container`, `Slot` |
| `EquipInfo` | `Container` (`SlotPosition`은 이미 있다) |

스냅샷(`S_InventoryResponse`·`S_CharacterListResponse`·장비 목록)은 **인벤토리와 창고를 한 목록에** 싣는다. 클라가 `Container`로 가른다.
증분 푸시(`S_UpdateItemResponse`·`S_CharacterSyncResponse`·`S_EquipSyncResponse`)도 같은 필드를 싣는다.

### 새 요청

| 요청 | 응답 |
| --- | --- |
| `C_StorageSortRequest { Container, Tab, SortKey, Order }` | `S_StorageSlotsResponse { Result, Container, Tab, Slots[(Key, Slot)], Items[ItemChangeInfo] }` — 격자 전체 |
| `C_StorageMoveSlotRequest { Container, Tab, FromSlot, ToSlot }` | `S_StorageSlotsResponse` — 바뀐 칸만. 자원은 같은 자원 칸에 놓으면 MaxStack까지 합치고 남는 것은 원래 칸에 |
| `C_WarehouseTransferRequest { From, Tab, FromSlot, ToSlot, Count }` | `S_WarehouseTransferResponse { Result, Tab, Changes[(Container, Key, Slot, Count)] }` — 양쪽 보관함의 바뀐 칸. `Count`는 자원만 읽는다 |
| `C_StorageMergeRequest { Container }` (T-175) | `S_StorageSlotsResponse` (`Tab = Resource`) — 바뀐 칸만. 합칠 것이 없으면 `Items`가 빈 `Ok` |
| `C_WarehouseStackRequest { }` (T-175) | `S_WarehouseTransferResponse` (`Tab = Resource`) — 양쪽 바뀐 칸. 옮길 것이 없으면 `Changes`가 빈 `Ok` |

`Changes`의 `Count`는 자원이면 **그 칸의** 수량(0 = 칸 비움), 캐릭터·장비면 1(그 개체가 `Container`의 `Slot`으로 옮겨졌다).

**자원 탭의 `S_StorageSlotsResponse`는 `Items`가 정본이다**(T-160) — 바뀐 칸마다 한 줄, `Count` 0이면 그 칸이 비었다.
클라는 `(Container, Slot)`으로 덮어쓴다. 정렬도 `Items`는 바뀐 칸만 싣는다(합쳐져 빈 칸 포함).
자원의 `Slots(Key = ItemId)`는 같은 자원이 한 칸뿐일 때만 맞는 옛 형식이라, 클라 다중 칸 표시([T-161](../../tasks/archive/T-161-클라다중칸표시.md)) 뒤에 지운다.
창고 안의 정렬·자리 이동은 인벤토리와 같은 `C_StorageSortRequest`·`C_StorageMoveSlotRequest`에 `Container = Warehouse`.

### 거절 코드

| 코드 | 경우 |
| --- | --- |
| 새 코드 — 칸 범위 밖 | `FromSlot`·`ToSlot`이 격자 칸 수 밖 |
| 새 코드 — 항목 없음 | 보내는 칸이 비었거나 `Key`가 그 보관함에 없음, 자원 수량 부족 |
| 새 코드 — 쓸 수 없는 정렬 기준 | 캐릭터·장비 탭의 `Count` |
| 새 코드 — 빈 칸 | 자리 이동의 `FromSlot`이 비어 있음 |
| `StorageEntityBusy` (1104) | **쓰지 않는다**(T-164부터 사용 중이어도 옮긴다). 패킷 호환 때문에 코드만 남긴다 |
| `WarehousePartialSwap` (1105) | 다른 자원 칸에 일부 수량 |
| `StorageOverMaxStack` (1106) | 놓은 같은 자원 칸이 이미 꽉 참 — 일부라도 들어가면 거절하지 않고 남는 것을 원래 칸에 둔다(T-160) |
| `NotEnoughItem` (기존) | 옮길 수량이 0 이하이거나 가진 것보다 많음 |
