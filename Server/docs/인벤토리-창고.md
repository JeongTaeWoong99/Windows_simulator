# 인벤토리 칸 위치 · 창고 — 서버 설계

> 최종 업데이트: 2026-10-01 · 상태: **설계 확정 — 서버 [T-058](../../tasks/T-058-창고칸위치서버.md)(칸 위치·정렬·이동) → T-107(창고) · 클라 [T-044](../../tasks/T-044-창고칸이동.md)**

클라 왼쪽 열 **인벤토리**(자원·캐릭터·장비 탭)와, 거래 열의 **창고** 탭([T-101](../../tasks/T-101-인벤토리개명거래탭.md))을
서버가 어떻게 들고 있는지 적는다. 두 기능은 **같은 칸 모델**을 쓴다 — 그래서 한 문서에 둔다.

---

## 1. 결정 (2026-10-01)

| 항목 | 결정 |
| --- | --- |
| 창고의 역할 | **인벤토리 확장 보관소**. 창고 안의 것은 채취·판매·배치·장착·경매에 쓰지 못하고, 꺼내야 쓴다 |
| 보관 대상 | 자원 · 캐릭터 · 장비 — 인벤토리와 같은 3탭 |
| 인벤토리 칸 수 | 탭마다 **50칸** (`Constants.StorageCapacity` 200 → 50) |
| 창고 칸 수 | 탭마다 `페이지 수 × 페이지당 칸`. **골드로 페이지를 하나씩 산다** (탭별로 따로) |
| 자원 이동 | **수량을 지정한다** — 같은 자원이 양쪽에 나뉘어 있을 수 있고, 양쪽에서 각각 칸 하나를 차지한다 |
| 칸 위치 | 인벤토리·창고 **둘 다** 서버가 칸 번호를 들고, 정렬·자리 이동을 같은 패킷으로 한다 |
| 50칸 초과 기존 데이터 | **처리하지 않는다** — 지금 DB는 테스트 데이터다 |

### 고르지 않은 안

- **창고 전용 테이블** — 개체가 옮겨질 때마다 행이 테이블 사이를 오가 착용·경매 잠금 참조가 흔들리고, 칸·정렬 코드가 두 벌이 된다.
- **칸 배치 테이블 분리**(`t_user_slot`) — 자원이 두 곳에 나뉘는 문제는 어차피 자원 테이블이 풀어야 하고, 고아 칸 정합성만 늘어난다.

## 2. 칸 모델

칸 격자는 **보관함 × 탭**으로 6개다.

```
EContainer  { Inventory = 0, Warehouse = 1 }
EStorageTab { Resource = 0, Character = 1, Equip = 2 }
```

칸 번호는 격자 안에서 0부터다. 격자의 항목 키는 자원이면 `ItemId`, 캐릭터면 `CharacterId`, 장비면 `EquipId`다
(패킷에서는 `long Key` 하나로 싣는다).

| 격자 | 칸 수 |
| --- | --- |
| 인벤토리 (탭마다) | `Constants.StorageCapacity` (50) |
| 창고 (탭마다) | `pages × 페이지당 칸` — 행이 없으면 기본 페이지 수 |

---

## 3. DB

| 테이블 | 변경 |
| --- | --- |
| `t_user_inventory` | **다시 만든다** — PK `(user_id, container, item_id)`, `slot` 추가. 기존 행은 `container = 0`, 칸은 `item_id` 순으로 0부터 |
| `t_character` | `container`·`slot` 추가. 기존 행은 `container = 0`, 칸은 `character_id` 순으로 0부터 |
| `t_user_equip` | `container` 추가. 칸은 기존 `slot_position`을 그대로 쓴다 |
| `t_user_warehouse` (신규) | `(user_id, tab)` PK, `pages`. 산 페이지 수. 행이 없으면 기본 페이지 수 |

**칸 중복을 DB 제약으로 막지 않는다.** 메모리가 원천이고, 교환은 두 행을 함께 고치는 저장이라
문장 하나하나에 걸리는 유니크 제약은 중간 상태에서 터진다. 중복은 메모리 `SlotGrid`가 막는다.

DDL은 `sqlite-sql-creator` 규칙(STRICT·주석)을 따른다. 테스트용 `SqliteFixture`의 DDL도 같이 고친다.

## 4. 메모리

### `SlotGrid` — 칸 배정 순수 클래스

격자 하나 = 인스턴스 하나. 키 → 칸 매핑을 들고 다음을 한다. **Repository·DTO를 모른다.**

| 동작 | 설명 |
| --- | --- |
| `Place(key, slot)` | 로그인 적재 |
| `TakeFirstFree()` / `Reserve`·`Release` | 첫 빈 칸. 지급 대기(PK 발급 전) 칸도 찬 것으로 본다 |
| `Remove(key)` | 칸 비우기 |
| `Move(from, to)` | 빈 칸이면 옮기고 차 있으면 교환. 바뀐 `(key, slot)` 목록을 돌려준다 |
| `Reorder(keysInOrder)` | 정렬 결과를 0부터 촘촘히 다시 매긴다 |

장비의 `NextFreeEquipPosition`·`_pendingEquipPositions`는 이리로 옮긴다.

### 보관함 = 별도 묶음

창고의 것은 **인벤토리와 다른 컬렉션**에 둔다 — 창고용 `Inventory` 인스턴스, `_warehouseCharacters`, `_warehouseEquips`.
채취·판매·배치·장착·경매·한도 검사(`HasStorageFor`)는 지금처럼 인벤토리 쪽만 본다.
**창고 물건이 "쓸 수 없음"은 검사를 더해서가 아니라 기존 코드가 보지 못해서 성립한다.**

## 5. 규칙

### 칸 배정

- **새로 들어오는 것은 언제나 인벤토리의 첫 빈 칸**이다 — 채취·뽑기·우편·치트. 창고에 들어가는 길은 이동 요청 하나다.
- 이미 가진 자원은 **수량만 늘고 칸은 그대로**다.
- 수량이 0이 되면 행을 지우고 칸을 비운다 (지금 `Inventory`가 이미 그렇게 한다).
- 지급 대기 중인 캐릭터도 장비처럼 칸을 예약한다 — 응답 전 연속 뽑기가 같은 칸을 잡지 않게.

### 정렬

정렬하면 격자 전체를 **빈 칸 없이 0부터** 다시 매긴다. 기준은 클라 [T-073](../../tasks/archive/T-073-창고정렬기준.md)과 같아야 한다.

| 기준 | 자원 | 캐릭터 · 장비 |
| --- | --- | --- |
| `Grade` | 등급↓ → 산업(`ItemType` 값 순) → TID↑ | 등급↓ → TID↑ → 개체 ID↑ |
| `Name` | 서버 GameData의 표시 이름 → TID↑ | 이름 → TID↑ → 개체 ID↑ |
| `Count` | 보유 수량 → TID↑ | **거절** (개체는 수량이 늘 1) |

방향(`Descending`)은 주 기준만 뒤집는다. 이름의 출처는 [T-085](../../tasks/T-085-공용상수소유권.md)가 정해지면 따른다.

### 창고 이동

| 경우 | 처리 |
| --- | --- |
| 배치 중인 캐릭터 | 거절 |
| 장비를 입은 캐릭터 | 거절 — 먼저 벗긴다. 입은 장비와 창고 칸이 엇갈리는 상태를 원천 차단 |
| 장착 중인 장비 | 거절 |
| 자원 일부 이동 | 보내는 쪽은 수량만 줄고(0이면 칸 비움), 받는 쪽은 같은 자원이 있으면 합치고 없으면 첫 빈 칸 |
| 받는 쪽 가득 참 | `StorageFull` |

### 페이지 확장

- 엑셀 시트 하나에 **페이지 번호별 골드 비용**, 그리고 기본 페이지 수·페이지당 칸. 행 수 = 최대 페이지.
  파일·시트·컬럼 이름은 만들기 전에 확인받는다 (`excel-table-creator`).
- 골드 차감과 `pages + 1`을 **한 트랜잭션**으로 저장한다.

## 6. 패킷

### 기존 DTO에 칸을 싣는다

| DTO | 추가 |
| --- | --- |
| `ItemInfo` · `ItemChangeInfo` | `Container`, `Slot` |
| `CharacterInfo` | `Container`, `Slot` |
| `EquipInfo` | `Container` (`SlotPosition`은 이미 있다) |

스냅샷(`S_InventoryResponse`·`S_CharacterListResponse`·장비 목록)은 **인벤토리와 창고를 한 목록에** 싣는다. 클라가 `Container`로 가른다.
증분 푸시(`S_UpdateItemResponse`·`S_CharacterSyncResponse`·`S_EquipSyncResponse`)도 같은 필드를 싣는다.

### 새 요청

| 요청 | 응답 |
| --- | --- |
| `C_StorageSortRequest { Container, Tab, Criterion, Descending }` | `S_StorageSlotsResponse { Result, Container, Tab, Slots[(Key, Slot)] }` — 격자 전체 |
| `C_StorageMoveSlotRequest { Container, Tab, FromSlot, ToSlot }` | `S_StorageSlotsResponse` — 바뀐 칸만 |
| `C_WarehouseTransferRequest { From, Tab, Key, Count }` | `S_WarehouseTransferResponse { Result, … }` — 양쪽의 바뀐 항목. `Count`는 자원만 읽는다 |
| `C_WarehouseExpandRequest { Tab }` | `S_WarehouseExpandResponse { Result, Tab, Pages, Gold }` |

로그인 때 `S_WarehouseInfoResponse { Pages[탭별] }`를 한 번 보낸다.

### 거절 코드

| 코드 | 경우 |
| --- | --- |
| 새 코드 — 칸 범위 밖 | `FromSlot`·`ToSlot`이 격자 칸 수 밖 |
| 새 코드 — 항목 없음 | 보내는 칸이 비었거나 `Key`가 그 보관함에 없음, 자원 수량 부족 |
| 새 코드 — 쓸 수 없는 정렬 기준 | 캐릭터·장비 탭의 `Count` |
| 새 코드 — 사용 중 | 배치 중 캐릭터 · 장비를 입은 캐릭터 · 장착 중 장비 |
| 새 코드 — 최대 페이지 | 더 살 페이지가 없음 |
| `StorageFull` (기존) | 받는 쪽 가득 참 |
| 골드 부족 (기존) | 확장 비용 모자람 |
