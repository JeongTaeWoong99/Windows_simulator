# 데이터 카탈로그 — 테이블 인덱스와 추첨기

> 최종 업데이트: 2026-09-19 · 상태: **구현 완료**

`GameTable`(엑셀 생성물) 위에 서버가 얹는 조회 인덱스(`DropTableCatalog` · `IndustryLevelCatalog` · `GachaPoolCatalog` · `EquipCatalog`)와
가중치 추첨기(`WeightedPicker`)의 설계 근거다. 코드 주석은 1~2줄과 이 문서 링크만 둔다.

---

## 0. 공통 — 카탈로그의 생명주기

- 서버 시작 시 `GameTable.LoadAll` **다음에** 각 카탈로그의 `LoadAll`을 한 번 부르고, 이후에는 조회만 한다. 테이블 데이터가 없으면 `LoadAll`에서 터진다.
- 등록이 끝나면 불변이라 여러 스레드가 동시에 읽어도 안전하다.
- **같은 키를 두 번 등록하면 예외.** 덮어쓰기를 허용하면 등록 순서에 따라 확률·필요 점수가 조용히 바뀐다. 중복은 데이터 오류로 본다.
- **조회 실패는 예외.** 조용히 기본값을 주면 잘못된 레벨이 30초로 돌거나 드롭이 비어도 아무도 모른다.

---

## 1. `DropTableCatalog` — (산업, 레벨) → 드롭 테이블

- 드롭 시트는 산업마다 하나지만 행이 레벨별로 갈라져 있다(`IndustryLevel` 컬럼, 산업레벨.md 6.2).
  시트 전체를 한 테이블로 등록하면 모든 레벨의 아이템이 한 통에 섞이므로 로드 시 레벨로 갈라 **레벨마다 독립 테이블**로 등록한다.
  테이블 이름은 `이름.Lv레벨` 꼴이다.
- 호출부가 각자 `DropTable.From`을 부르고 캐시를 따로 들면 캐시 위치가 흩어지고 "판정마다 새로 만드는" 실수가 섞인다.
  **만드는 곳을 `LoadAll` 한 군데로 모은다** — 드롭 시트를 추가하면 여기에 `Register` 한 줄을 더한다.
- **희귀도 가중치는 각 산업 시트가 직접 갖는다.** 공통 `RarityWeightTable`이 없어 분포를 산업마다 다르게 잡을 수 있지만, 확률을 손볼 때 **5개 시트를 함께** 봐야 한다.
  그래서 시작 로그에 산업×레벨별 분포를 찍는다(`LogDistributions`, R18 진단).
- 산업 축에 `IndustryType`을 그대로 쓴다. 이 enum은 아이템 분류(`Misc`·`Special`)도 겸해 의미가 둘로 갈려 있다.
  갈라지기 시작하면 분리한다(→ GameDesign 기획평가.md). 그때 고칠 곳이 모이도록 키를 이 클래스 안에 가둬 뒀다.

## 2. `IndustryLevelCatalog` — (산업, 레벨) → `IndustryLevelTableRow`

- 시트 키는 단일 컬럼 제약 때문에 `IndustryLevelTID`(산업×100+레벨)지만 서버가 묻는 것은 언제나 **(산업, 레벨)**이다.
  채번식 산수를 호출부마다 반복하지 않도록 로드 시 인덱스를 만든다(산업레벨.md 6.1). 산업 5 × 레벨 5 = 25행이 정상.
- **`GetJudgeCostUnits`의 ×1000은 단위 환산이다.** 엑셀 `RequiredScore`는 초×천분율, 서버는 밀리초×천분율.
  엑셀에 밀리초 값을 직접 넣으면 Lv5(24억)가 int를 넘겨 깨진다 — 환산은 반드시 서버 몫이다(산업레벨.md 2.4).
- 해금 요구치(`RequiredAptitude`·`RequiredAccountLevel`) 조회도 구현되면 여기로 모은다.

## 3. `GachaPoolCatalog` — GachaId → 추첨기

- 원본은 `Gacha.xlsx`의 세 시트 `GachaItemTable`·`GachaCharacterTable`·`GachaEquipTable`. 각 시트가 자기 TID 컬럼에 `Ref`를 걸어 실재하지 않는 보상은 `generate-tables.ps1`에서 막힌다.
  **같은 GachaId를 여러 시트가 함께 쓰면 한 풀에서 종류가 섞여 나온다.** 장비 풀(3 무기 · 4 장신구 · 5 보석)은 한 풀에 한 종류만 둔다(`GachaEquipSheetTest`).
- `GachaEntry`는 세 시트의 Row를 추첨에 필요한 값만으로 정규화한 것이다. `RewardType`이 `RewardTID`의 의미를 정한다 — **종류는 값이 아니라 출처가 정한다.**
- **등급은 풀에 두지 않는다.** 등급의 원본은 각 정의 테이블 하나다. 풀에 따로 적으면 정의 쪽과 독립적으로 존재하다가 조용히 어긋난다(깃허브 이슈 #9 2-3).
- 패킷 `GachaRewardInfo`가 `ItemId`·`CharacterTid`를 따로 두는 이유도 같다. 아이템 TID와 캐릭터 TID가 같은 숫자 대역을 쓸 수 있어 한 필드에 겹치면 종류를 잘못 읽었을 때 **조용히 엉뚱한 것을 그린다.**
  캐릭터 개체 PK는 DB가 발급해 이 응답보다 늦으므로 뒤이어 오는 `S_CharacterListResponse`에서 받는다.

## 4. `WeightedPicker<T>` — 가중치 추첨기

"여러 후보 중 하나를 확률로 고르는" 모든 곳(드롭·희귀도·가챠)에서 쓴다. 재화가 생기는 지점이라 **추첨은 서버에서만** 돈다(P4).

- **한 번 만들어 재사용한다.** 생성 시 누적 가중치를 쌓아 두고 추첨은 이진 탐색 O(log n). 가챠 다연차·분포 검증처럼 같은 풀을 수백만 회 굴리는 경로가 있어 매번 합을 다시 더하면 그게 그대로 비용이다.
- 생성 후 불변이라 `Pick`은 스레드 안전하다. 난수원만 주의 — 기본 `Random.Shared`는 안전하고, `Random`을 직접 넘길 때는 인스턴스를 공유하지 않는다.
- **가중치 0은 후보에서 빼고, 음수는 예외.** 0은 "당분간 안 나오게 막아 둔다"는 흔한 기획 의도라 정상 입력이지만 음수는 어떤 의도로도 해석되지 않는다. 합은 `long`으로 누적해 int 오버플로를 잡는다.
- `Pick`의 `BinarySearch`: 값을 찾으면 그 인덱스, 못 찾으면 삽입 위치의 보수(`~i`). 정확히 일치했다는 건 roll이 그 구간의 끝(= 다음 구간의 시작)이라 +1 한다.
- `GroupBy`가 있는 이유: 드롭 시트는 제너레이터 제약(단일 컬럼 키) 때문에 첫 컬럼에 고유 TID를 두고 실제 그룹 축은 일반 컬럼으로 둔다. 그래서 로드 후 서버가 그룹 인덱스를 만들어야 한다.

## 5. `EquipCatalog` — EquipTID → 행, 종류↔칸 규칙

- `Equip.xlsx`/`EquipTable`의 TID 인덱스. 장비 개체(`t_user_equip.equip_tid`)가 가리키는 정의를 찾는다.
- **종류(`EquipKind`)와 칸(`EquipSlot`)은 다른 enum이다.** 장신구는 칸이 둘(`Accessory1`·`Accessory2`)인데 매핑 테이블의 유일키가 `(character_id, slot)`이라 칸을 나눴을 뿐, 장신구 장비는 두 칸 어디든 들어간다. 그래서 테이블은 종류만 갖고 `CanEquip(kind, slot)`이 허용표를 답한다.

| `EquipKind` | 허용 `EquipSlot` |
| --- | --- |
| Weapon | Weapon |
| Accessory | Accessory1 · Accessory2 |
| Gem | Gem |

- `IsValidSlot`은 `None`·`Max`를 거른다 — 클라가 보낸 값이라 범위부터 본다.
- 장착·속도 반영 흐름은 [채취 정산](채취-정산.md) 3·5장, 설계 전체는 `docs/superpowers/specs/2026-09-17-equipment-design.md`.

## 6. `AccountLevelCatalog` — 레벨 → 필요 경험치 · 특성 포인트

- `User.xlsx`/`AccountLevelTable`. `CharacterLevelCatalog`와 같은 모양이고 **마지막 행이 만렙**이다.
- `RequiredExp`는 **long**이다 — 곡선이 캐릭터의 8배라 상위 레벨이 int를 넘는다.
- `TraitPointAt(level)` = 그 레벨에 **도달할 때** 주는 특성 포인트. 누적이 아니다 — 남은 포인트는 `t_user_account.trait_point`가 확정값으로 갖는다.
- 경험치의 출처는 캐릭터다 — `User.GrantCharacterExp`가 같은 양을 `GainAccountExp`로 넘긴다(특성 기획 3장).

## 7. `UserTraitCatalog` — 특성 노드 → 비용 · 효과

- `User.xlsx`/`UserTraitTable`. **노드 TID = `UnlockTID`** (`Ref UnlockTable.UnlockTID`) — 조건은 `UnlockCatalog`의 같은 행이 갖는다.
- `IsTraitUnlock(unlockTid)` — 특성 노드면 `User.TryUnlock`이 `TraitOnlyUnlock`으로 거절한다. 비용(특성 포인트)을 건너뛰는 뒷문을 막는다.
- `SpeedAdds` — `EffectType = SpeedAdd` 노드 목록. `User.GetTraitSpeedAdd(industry)`가 **열린 것만** 더해 슬롯 속도의 가산 항에 넣는다. `Industry = None`은 전 산업.
- `UnlockCatalog`의 미참조 경고는 특성 노드와 `IndustryLevelTable.UnlockTID`를 참조로 센다.

## 8. `CommonRewardCatalog` — 채취 공통 보상 (상자)

- `DropCommon.xlsx`/`CommonRewardTable` (산업 드롭 `Drop<산업>.xlsx` 옆 — 채취에서 나오는 것은 전부 `Drop*.xlsx`). 산업·레벨과 무관하게 **판정 1회마다 행마다 따로** 굴린다 — `Roll(judgeCount, random)`.
- 확률은 백만분율(`ChancePerMillion`). 나온 상자는 그 슬롯의 수확(`SlotHarvest.Gained`)에 얹혀 `S_GatherResultResponse`로 함께 나간다.
- 테스트 빌더는 이 카탈로그를 **비워 둔다**(실데이터를 넣지 않는다) — 난수 보상이 다른 정산 테스트를 흔들지 않게.

## 3.1 상자 풀 · 골드 구간 (2026-09-19)

- **상자 = `ItemTable.OpenGachaId`가 있는 아이템.** `GachaService.OpenBox`가 그 풀을 개수만큼 비용 없이 돈다. 지급은 `Draw`와 같은 `Grant` 경로다.
- **비용 재화가 `None`인 풀은 상자 전용이다** — `Draw`가 `InvalidGachaId`로 거절한다.
- `GachaGoldTable`은 TID가 없는 보상이라 `GachaEntry(RewardTID = 0, Count = MinAmount, MaxCount = MaxAmount)`로 정규화한다. 지급 시 `Count~MaxCount`에서 무작위.
